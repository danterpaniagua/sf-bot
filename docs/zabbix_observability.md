## SSL certificate expiration

Monitored centrally on the **`Zabbix server`** host, not per VM: one `log[]` active-check item per service, `get_ssl_enddate_<service>`, each reading `/var/log/zabbix/ssl_<name>.log`, each with its own 4 triggers tagged `cloud:Azure` / `component:SSL Cert` / `env:PROD`. Present for `webservicecg`, `webservicev2`, `website`, `smartfran`, `mobileappservice`, `fs-api`, `clubsite_ar`, `clubsite_py`. When auditing a VM for cert-expiry coverage, look at the `Zabbix server` host; absence on the VM is expected.

- **Thresholds** come from macros `{$SSL_CERT_WARN|AVERAGE|HIGH|OK}`: default 45/30/15, OK 60; contexts `:MOBI` 15/10/2, OK 30; `:FACTURASEND` 25/15/7, OK 80; `:LE` 15/10/7, OK 30. The trigger name carries the unexpanded macro, so a name can show a value that was later changed. Each cert also has `No data from SSL <x> from 2 days` (`nodata(…,{$SSL_CERT_NODATA_WINDOW})`, Average; 1 day was too tight for the log refresh: it fired ~35 times in September on Website/WebServiceV2, each open/closed within the same minute).
- **Why `:LE`:** win-acme renews inside the last ~30 days of a 90-day certificate (per `operations/docs/mobileappservice_ssl_renewal_runbook.md`, not checked against the win-acme settings), so the 45-day tier fires on every healthy cycle of an automated cert. `:LE` serves MobileAppService, ClubSite AR and Website; manual certs and the rest keep 45/30/15. Add a service to `:LE` only once its renewal is automated and a real cycle was seen. WebServiceV2 and WebServiceCG/Bot-Security are **not automated** (last local records 2026-09-13: Azure DNS zone, SP role and GoDaddy NS delegation verified, win-acme install not started; WSCG still serves the paid `*.smartfran.com` wildcard valid to 2027-03-28, blast-radius check pending). Automation state per service: `loyalty/docs/certificates.md`.
- **Tier dependencies** (all 8 services, 24 triggers): High none, Average → High, Warning → Average + High, so only the highest active tier pages. `SSL Clubsite AR … HIGH` depends on `SSL FacturaSend … AVERAGE:FACTURASEND` (copy-paste error; it should depend on Clubsite AR's own Average).
- **Delivery:** the SSL triggers carry `scope:GIT-SML` → action 8 → leaders' Chat space only (18 messages in September). All 32 carry `SVC_FRIENDLYNAME: SSL <service>` (problem-card title resolves; the recovery card reads the lowercase `friendlyname`, which these triggers lack).
- **A 0 reading is a failed read, not an expiry (`GITIN-2249`, 2026-10-15):** `get_enddate.sh` (hourly cron of the `ubuntu` user on the Zabbix server, shared by all 8 items) prints `0` when `openssl` cannot fetch the certificate (no error, no exit code), and the log is overwritten each hour (`tee`), so no history survives. MobileAppService read 0 once (10:04 UTC-3, 20 days the night before, 20 again 3 hours later) and the High tier opened; High recovers only at `{$SSL_CERT_OK:LE}` = 30 days, so it stayed open with 17 days left. The other 7 items read normally in that window, so the failure was specific to the MobileAppService path. Left unchanged by decision. Options evaluated, not applied: have the script write nothing on failure (Zabbix goes to "no data", 2-day window; covers all 8), make the trigger ignore 0 (a real expiry that day would stop paging), or lower the High recovery threshold (changes the `GITIN-2156` criterion). Same shape as `GITIN-2028` (open because recovery needs a high value) with a different cause.

## Filesystem free-space trigger on ext4 data disks (sonarqube, 2026-07-20)

The native "Disk space is low on {#FSNAME}" trigger needs `pused > {$VFS.FS.PUSED.MAX.CRIT}` AND (`free < {$VFS.FS.FREE.MIN.CRIT}` OR `timeleft(pused,1h,100) < 1d`). Zabbix's `free` includes the 5 % blocks ext4 reserves for root (about 12.5 GB on the 251 GB `/opt/ssd01` of `sfcg-sonarqube`), while an application running as non-root sees 0 available at 100 % `df`. With `{$VFS.FS.FREE.MIN.CRIT:"/opt/ssd01"}` = 5G the free clause was unreachable: the disk sat at 96-100 % with no alert. Fix applied 2026-07-20: context macro `{$VFS.FS.FREE.MIN.CRIT:"/opt/ssd01"}` = 28G (above the reserve; do not edit the generic macro). Check any other ext4 data disk the same way; `tune2fs -m` on a data-only volume would remove the gap (proposed, not done). Event: `operations/events/20260720_sonarqube_disco_lleno/`.

## IIS request-rate tiered alert pattern

The template's per-app `GET`/`POST Requests/Sec` items (`perf_counter_en["\Web Service({$IIS.APP.NAME})\...Sec", {$IIS_CURRCONN_UPDATE_INTERVAL}]`) are **visibility-only fleet-wide**: no trigger references them on any host checked (`SFCG-WSCG-01`, `SFCG-WSV2-01`). Their lack of alerting is not a per-item bug.

The actionable alert is a **custom, non-template** 3-tier trigger (Warning/Average/High) on the generic `_Total` item `IIS: Method Total requests per second` (`perf_counter_en["\Web Service(_Total)\Total Method Requests/Sec", 60]`, native, always collecting). This is a fleet convention, not stock Zabbix.

**Macros:** `{$PERF_COUNT_TRIG_WARNING|AVERAGE|HIGH|OK|TIME_NOK[:<CONTEXT>]}`, global, a base default plus optional per-service contexts. Base (unfiltered `usermacro.get`, 2026-08-30): `WARNING=9, AVERAGE=13, HIGH=15, OK=7, TIME_NOK=10m, TIME_OK=15m`. Contexts: `CLUBS` (50/75/90, OK 49), `WEBS` (15/11/20, OK 8: **`AVERAGE` < `WARNING`, misconfigured, but no trigger references it**), `WEBSCG01`. **Pitfall:** a scoped `usermacro.get` search (`search: {"macro": "PERF_COUNT_TRIG"}`) once returned empty although the macros exist: cross-check an unfiltered pull when a scoped result surprises.

```
Warning:  min(/<host>/perf_counter_en["\Web Service(_Total)\Total Method Requests/Sec", 60],{$PERF_COUNT_TRIG_TIME_NOK[:<CTX>]})>={$PERF_COUNT_TRIG_WARNING[:<CTX>]}
Recovery: max(/<host>/perf_counter_en["\Web Service(_Total)\Total Method Requests/Sec", 60],{$PERF_COUNT_TRIG_TIME_NOK[:<CTX>]})<={$PERF_COUNT_TRIG_OK[:<CTX>]}
```
Average and High follow the same pattern against their own macro. **Dependency direction:** the legacy `IIS More than N … for 10m` triggers of `SFCG-MOBI-01/02` chain Average → Warning and High → Average, which is **inverted**: a higher tier's condition always implies the lower one's, so while the Warning is open the Average/High are suppressed (September 2026: only Warning events on those hosts, even at a 10-min average of 123 req/s on MOBI-02). The lower tier should depend on the higher one (as the MOBI `IIS Spike` triggers do). Whether WSV2, CLUB, WSCG-01 and WEBS share the inversion is not checked.

## IIS request-queue triggers (`GITIN-2156`)

Template `IIS by Zabbix agent active` (id `10326`, linked by 12 hosts: CLUB-01/02, MOBI-01/02, WEBS-01/02/03, WSV2-01/02, WSIT-01, WSCG-01, SFDEV02 [disabled]) discovers one trigger per app pool from the LLD rule `wmi.getall[root\webAdministration, select Name from ApplicationPool]`. The stock macro `{$IIS.QUEUE.MAX.WARN}` ships **empty**, so `IIS: Request queue of <pool> is too large` was unsupported (`right operand "" is not a numeric value`) on every host that evaluated it (8 at review time): queue alerting did not work. A template macro overrides a global one, so the value must be set on the template.

Now three prototypes, `min(CurrentQueueSize,{$IIS.QUEUE.MAX.TIME}) > {$IIS.QUEUE.MAX.<tier>}`: Warning `16917` > `…WARN` = **10**, Average `26879` > `…AVG` = **50**, High `26866` > `…HIGH` = **200**, window `{$IIS.QUEUE.MAX.TIME}` = 5m. Dependencies: High → `16914` (app pool not Running); Average → High + `16914`; Warning → Average + High + `16914`. Routing tags: `scope:performance`, `scope:GIT-SML-OPE`, `service_group:LOYALTY`, `action:GCHAT`, `SVC_FRIENDLYNAME:IIS request queue` (action 7). Item prototype `31051` (`CurrentQueueSize`) history is 365 d. Thresholds are uncalibrated (queue was 0 on every pool over 7 days). Discovered triggers pick up changes on the next LLD run.

**How routing works:**
- A trigger notifies only if its tags satisfy an enabled action's conditions. Triggers tagged `scope:OPE`, `service_group:LOYALTY`, `action:TELE,GCHAT,MAIL` match **no** action (25 of 1,801 September problems had any notification attempt, 1 of 198 High). `TELE` and `MAIL` in the `action` tag are labels: no action checks `TELE`, and `MAIL` is not a substring of the `EMAIL` the email actions require.
- `~` is substring, `=` is exact; a trigger can carry several values per tag key. Example: `scope:GIT-SML-OPE` satisfies action 7 but not action 8 (`= GIT-SML`), which reaches the Operaciones space only.
- Media type 38 (`Script Google Chat python`, `chat-google.py`) takes `{ALERT.SENDTO}` = the per-user Chat API path (space + key + token): **never persist `sendto` or script parameters**; mask when pulling. Operaciones and leaders are different spaces. Problem card title: `Servicio {EVENT.TAGS.SVC_FRIENDLYNAME} degradado`; recovery card: `{EVENT.TAGS.friendlyname}`. So a trigger routed to Chat needs **both** tags with the same value. Seen in September: request-rate triggers (`IIS Spike`, `IIS More than N …`, `More than N IIS Method POST …`) carry only `friendlyname`; per-app-pool service triggers carry only `SVC_FRIENDLYNAME`; the generic `IIS: has been restarted`, `IIS: Port N is down`, `WAS is not running` and the `HTTP Code not 200` web checks carry neither (the card would show the macro unresolved).
- **A recipient is notified only for problems it can see** (`GITIN-2222`, 2026-10-15): the user must have read on the host's host group, and no tag filter of any of its user groups may hide the problem. Two confirmed causes of events created with the right tags and **0 notifications**: (1) user 9 had no read on the host group of the three AWS ECS hosts (`Templates/Cloud`; `Zabbix server` was readable, so the Graylog FATAL alert on it notified while the ECS alert did not); fixed by changing the host groups of the discovered hosts to `AWS` and `PEDIDOS`; (2) at 18:08:49 UTC user 9 was added to user group 14 `pedidos-read`, which carries tag filters on `Zabbix servers` (`cloud=AWS`, `cloud=Mongo Atlas`, `clud=AWS` (misspelled), `component=SmartPedidos`, `component=Amazon Simple Queue Service`); no notification from 19:04 UTC, and an A/B test (user 9 removed from group 14 at 19:33:00) produced notifications 8 s later. Supported by the test, the mechanism is not otherwise proven. Group 17 `ope-notify-read` (read on host groups 4, 30, 37, no filters) is the filter-free pattern for the `ope_notify` recipient. Check `usergroup.get` (`selectTagFilters`, `selectRights`) before blaming actions, tags or the server.
- **Discovered hosts copy macros from the discovery host:** a host macro set on `Zabbix server` (the host of the discovery rule "ECS clusters discovery", host prototype 10620) was copied by the discovery process (audit user `System`, 3 h heartbeat) to the three discovered ECS hosts, so a macro used to silence a trigger on `Zabbix server` silenced it on the production host too (`{$AWS.ECS.CLUSTER.SERVICE.RUNNING.DIP}` = 1000, `GITIN-2222`). A manual macro, trigger or change on a discovered host is rejected by the API ("No permissions to referred object"). The audit log (`auditlog.get`) is how to find who/what created an object.
- Email HTML (media `4`) uses no tags. Telegram (media `16`) has the stock placeholder token (`<PLACE YOUR TOKEN>`) on the media type, yet alerts were sent without error (action 12 above).
- **Gaps, not fixed:** the SMTP failure above; `loyalty_msg` (user 12) in a disabled group; action 9 matches nothing. **ARCA healthcheck triggers** (`service_group:CLOUD`, `scope:GIT-SML`, `GCHAT`) match neither action 7 nor 8 unless retagged; the five `ARCA*` triggers (DOWN, DEGRADADO, sin datos, WSFEv1 Latencia Alta/Crítica; ids 26730-26734) carry `scope:GIT-SML-OPE` + `SVC_FRIENDLYNAME: ARCA` and route to Operaciones through action 7 (not action 8, which needs `LOYALTY`).

## Fleet alert standards — CPU and RAM tiers (`GITIN-2250`)

For the 14 prod SFCG loyalty hosts (list and tiers in `loyalty/docs/zabbix_alert_matrix.md`), host-level triggers created through the API; the shared Windows template triggers were left unchanged. Thresholds are the user's decisions, not measurements. CPU item `system.cpu.util`; RAM item `perf_counter_en["\Memory\% Committed Bytes In Use"]` (created on the 14 hosts; it did not exist).

- Macros are global: `{$CPU.UTIL.WARN|AVG|HIGH|TIME|WARN.OK|AVG.OK|HIGH.OK}` and `{$MEM.COMMIT.WARN|AVG|HIGH|TIME|OK|OK.TIME}`. Dependencies: High none, Average → High, Warning → Average + High.
- Routing tags: `scope:performance`, `scope:GIT-SML-OPE`, `service_group:LOYALTY`, `action:GCHAT`, `SVC_FRIENDLYNAME:<CPU utilization | Memory commit>` → action 7.
- Template stock triggers (`High CPU utilization` 90 % over 5m, CPU queue, privileged, interrupt, `High memory utilization` 90 %, Pages/sec) carry only `scope:` tags and route nowhere. Stock macros: `{$CPU.UTIL.CRIT}`=90, `{$CPU.QUEUE.CRIT.MAX}`=3, `{$MEMORY.UTIL.MAX}`=90, `{$MEM.PAGE_SEC.CRIT.MAX}`=1000.
- The balancer probe (SmartLoyalty `healthcheck.ashx`) answers HTTP 400 when a 500 ms CPU sample or the commit ratio exceeds 80; Zabbix averaged tiers do not see single-sample spikes (`loyalty/docs/infrastructure.md`).
- **Required, not built (user):** disk usage tiers and a run-out-of-space forecast on every prod host, routed to Operaciones; tiers and horizon undecided. The stock "Disk space is low / critically low" triggers route nowhere.
- Web scenarios on `sfcg-monitoreo` (10610) run from proxy `10609`, which also monitors the WEBS hosts; scenario 6 (`[PROD] API POS / Gestion`) has a `Healthcheck` step (`/healthcheck.ashx` through `webservice.clubgrido.com.ar:8080`). Config changes reach a proxy on its sync interval (not read for this proxy), so new items and steps may show no data until then. Scenario reference: `docs/zabbix_web_scenarios.md`.
- Audit procedure: skill `alert-normalizer`.

## FEPE healthcheck (Peru e-invoicing providers, `operations/events/20260714_fepe_zabbix_healthcheck/`, 2026-07-14/24)

Same pattern as ARCA (`ope-zabbix` skill): `/opt/scripts/get-fepe-status.sh` (symlink `/usr/bin/get-fepe-status`) behind `UserParameter=fepe.status.raw,/usr/bin/get-fepe-status --json` in `/etc/zabbix/zabbix_agent2.d/userparameter_fepe.conf` on the `Zabbix server` host; master item `FEPE Raw Status` (text, `{$FEPE.UPDATE.INTERVAL}` = 1m), 8 dependent items (status and latency per service; `FEPE ConsultaProd Latency` deferred), macros `{$FEPE.LATENCY.WARN/HIGH}` (+ `.RECOVERY`), `{$FEPE.LATENCY.AVG.PERIOD}`, `{$FEPE.NODATA.WINDOW}` (initial values, to retune after ~2 weeks of data), 9 triggers (`FEPE DOWN`, `FEPE DEGRADADO`, `FEPE sin datos`, latency High/Critical pairs for `WsFeProd`, `WsFeTest`, `Bizlinks`) with the ARCA dependency chain, all tagged `service_group = CLOUD` (the value the ARCA events use for action 7; an earlier draft said `LOYALTY`).
- **Two providers, not one:** Xacto Peru (`api.xactoperu.com`, REST, sends the vouchers: `WsFeProd` port 8099, `WsFeTest` 3636, `ConsultaProd` 6099) and Bizlinks (`pse.bizlinks.com.pe`, SOAP, queries vouchers; added in Cloud `v2.30.00`). SmartFran Cloud does not integrate with SUNAT directly (`SmartFran.Cloud.Sales.Application/Services/WsFePeService.cs` and the `TicketProcessAsync` function's copy). Neither provider has an official dummy method: Xacto is checked by reachability, Bizlinks by a SOAP call with **deliberately invalid credentials** and an expected 401/403 "Usuario no encontrado" (so no real secret is stored in Zabbix).

A port-level block (Xacto whitelisting or a fault on those ports), not a host outage; unconfirmed which, needs a test from the real production egress (Kudu console of the Sales API App Service) or Xacto. `FEPE DOWN` fired on 2026-07-24 15:31-15:37 after 7 consecutive 1-minute polls (`WsFeProd` and `WsFeTest` `http=000`, ~8.0 s).

The agent `Timeout` is 30 (6.0 maximum) and the server `Timeout` 15. Testing as `zabbix` from a personal home directory fails with `cannot include "zabbix_agent2.d/plugins.d/*.conf": stat .: permission denied` and a false `Unknown metric`: test from `/etc/zabbix` with `-c /etc/zabbix/zabbix_agent2.conf` (see `operations/docs/zabbix_scripts_home_dir_risk.md`). Frontend triggers need every dependent item to exist first (`Incorrect item key "fepe.status.wsfetest"`): list the real items before creating triggers.
- **Open:** deployment of the delivery path beyond Chat for FEPE is not recorded; the Xacto port question above; credential exposure in the Cloud repository's `Documentation/*/release_notes.md` history found during this event (5 files with confirmed plaintext credentials including an AWS access key pair from `v1.0.6` / `v1.0.8`, the Bizlinks user/password in `v2.30.00` and a printer license key; 2 files with connection-string-shaped `FabricConnections:*` values and 2 ambiguous ones, not confirmed; 5 false positives): paths and commit ids are in the event, values must never be copied; rotation is tracked in `cloud/docs/todo.md`.

## Known Zabbix Agent 2 issues

- **`ZBX-22463`** — `Detected performance counter with negative denominator ... giving up` on Windows IIS/performance-rate counters (Agent 2); 6.0.32 predates the fix (`ZBX-20356`, ~6.2.7+). Restarting the `Zabbix Agent 2` service often only helps **temporarily**. Chronic on `SFCG-WSCG-01` (dozens of occurrences since 2026-07-20); a single blip on `SFCG-WSV2-02` that a restart cleared (`GITIN-1956`).
- **Host cloning does not guarantee item parity:** a clone can miss an item (e.g. `Get Requests/Sec`) that was not present at clone time (`SFCG-WSV2-02`). Diff a clone's item list against its source.

## API limitations and gotchas (Zabbix 6.0.32)

- **No Trends API:** `trends.get`/`trend.get` returns `-32601 Method not found` (added in 6.4+). Hourly trend aggregates are visible only in the frontend graphs; if raw History has aged out there is no API way to recover it.
- **History retention defaults inconsistently:** 7 d (vs 180 d on sibling items) was found on Mobile GET/POST items, CPU/Memory items on both Mobile hosts, and GET/POST items on `SFCG-WEBS-01/02/03` and `SFCG-WSV2-01/02`; all raised to 180 d going forward (not retroactive). Check the item's real `history` (`item.get`, `output: ["history","trends"]`) before trusting a `now-Nw` lookup. Detail: `operations/events/20260829_mobile_alerts_coverage_analysis/investigation.md`.
- **`trigger.get` with `expandExpression: true` also expands macros** (macro values then look like hardcoded literals, which produced a wrong finding). For audits pull the raw expression plus `selectFunctions` (on 6.0.32 it returns `functionid` + `parameter` only, no function name).
- **A raw `trigger.get` snapshot cannot be restored with `trigger.update`**: function ids (`{38197}>=…`) are rejected (`incorrect expression starting from "{38197}…"`). Rebuild rollbacks from explicit expression text, or snapshot with `expandExpression` and record the macros separately.
- **`trigger.update` with `tags` replaces the whole tag list**: read, modify, resend all. `trigger.status`: `0` enabled, `1` disabled.
- `alert.get` returns no `userid` unless requested in `output`; never request or persist `sendto`.
- Pulls into `events/` can contain real names and emails (`user.get`, `usergroup.get`): request only `userid`/`username`-level fields and mask media `sendto`/script parameters.
- `item.get` ignores an `httptestids` filter (use `webitems:true` + `search:{key_}`); web-scenario items need `"webitems": true` or the call returns no `web.test.*` items (which looks like "no items/triggers"), and their keys carry quoted names (`web.test.rspcode["[PROD] MobileApp",healthcheck]`). `httptest.update` replaces the whole step list (resend steps with their `httpstepid`). `usermacro.get` without `hostids` returns no template macros (use `template.get` + `selectMacros`). Check one raw object before concluding something is absent.
