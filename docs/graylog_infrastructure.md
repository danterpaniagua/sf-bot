# Graylog Infrastructure — SmartPedidos + SmartLoyalty (shared, cross-project)

Distinct from the SmartCloud-dedicated Graylog instance (separate `cloud-graylog` repo, `smartfran-graylog-pro` VM, serves only the Business/Sales App Services). This document covers the older bare-metal Docker stack that serves **SmartPedidos and SmartLoyalty**. Don't conflate the two when a ticket just says "Graylog" — hostnames are easy to confuse (`sf-monitoreo` vs `sfcloud-monitoreo`). Unresolved example: the swap-alert ticket `GITIN-2167` (`operations/events/20261005_gitin2167-graylog-swap-alert/`) reached `sf-monitoreo.smartfran.com` over SSH and found OS and OpenSearch node name `sfcloud-monitoreo` running native Graylog, Logstash, OpenSearch and MongoDB (31 GiB RAM), which matches the SmartCloud VM and not this Docker stack: either the name pointed at another VM that day or the ticket described the SmartCloud one; read the hostname before acting.

## Host

`sf-monitoreo.smartfran.com` — also runs Zabbix natively on the same box (separate LVM volume `zabbix-zabbix--01` at `/mnt/database`, unrelated to Graylog/OpenSearch storage).

## Docker stack

| Container | Image |
|---|---|
| `graylog` | `graylog/graylog:5.2.12` |
| `opensearch` | `opensearchproject/opensearch:2` (running 2.19.4) |
| `mongo` | `mongo:6.0.5-jammy` |

Compose file and related scripts live locally on the host under `~/scritps/graylog/` — **not version-controlled in any repo** (not `bots/`, not `cloud-graylog/`). `opensearch` is single-node (`discovery.type: single-node`), heap `-Xms2g -Xmx2g`. Memory configuration (`GITIN-1854`): until 2026-08-13 `bootstrap.memory_lock: true` had no matching `ulimits: memlock` block and the `deploy.resources.limits` (6G opensearch, 4G mongo) were ignored, because only Docker Swarm honors `deploy:` and the stack is started with plain `docker compose up`; OpenSearch therefore had no real memory ceiling and an unlocked heap. Fixed 2026-08-13 by copying `graylog-compose.fixed.yml` over the live file (`mem_limit` 6442450944 and `mem_reservation` 4 GB for opensearch, `mem_limit` 4 GB for mongo, `ulimits.memlock` -1/-1), verified with `docker compose config` and `docker inspect opensearch --format '{{.HostConfig.Memory}}'` (6442450944, not 0). The running containers come from `graylog-compose.yml`; the near-identical `docker-compose.yml` in the same directory is stale (weaker memory numbers, a `healthcheck` misplaced under `depends_on.mongo`, plaintext secrets instead of `${VAR}`): delete it or strip the secrets. The mongo service is `container_name: mongodb`, inspect it by that name.

**No cold/warm index storage tiering** — confirmed 2026-08-14: this stack runs the open-source `graylog/graylog:5.2.12` image (not `graylog/graylog-enterprise`), no license key or Data Tiering config anywhere in the compose environment. Data Tiering (S3-backed cold storage) is a Graylog Enterprise/Cloud feature, unlike `cloud-graylog` (SmartCloud-dedicated instance). Practical effect: the only levers on an oversized index like `graylog_299` are the field-limit fix, retention (`max_number_of_indices`), and raw disk capacity — no "move old data to cheap storage" option exists on this instance.

## Mail relay hop (SmartLoyalty)

`SFCG-SMTP-01` (`192.168.50.161`) / `SFCG-SMTP-02` (`192.168.50.162`) run hMailServer for WebServiceCG's outbound email (e.g. `AccountRecovery`). Flow: app → hMailServer (these hosts) → `smtp.sendgrid.net` → recipient. NXLog on each ships delivery log lines (tag `SF-SMTPRL`, `Cardinality` `01`/`02`) to the `TXT_UDP` input above. Confirmed 2026-08-11/12 during `GITIN-1816`. NXLog extractions added in `GITIN-1827`: `$MessageId` (generic) and `$DeliveryStatus` from `SMTPDeliverer - Message\s(\d+): ([^"]*)` (a first `(.*)` kept a trailing quote), confirmed on both hosts; a message keeps one `MessageId` across its lifecycle, so comparing the relays' own `SMTPDeliverer` event rate with what lands in Graylog is an early warning for a silent UDP gap. See `loyalty/docs/infrastructure.md`.

## Known issues and what was done (`GITIN-1827` closed, `GITIN-1854` carries on; state as last recorded 2026-08-15 to 2026-09-18)

- **Zero replicas** on every index (`rep 0`): no redundancy. `_cluster/health` was green with 998-999 active primary shards after the restarts; port `9200` is not reachable from outside the host (by design: check with `curl http://localhost:9200` over SSH, a silent external timeout is not a freeze).
- **2026-08-12 freeze (`GITIN-1827`):** `systemctl reboot` at 01:15:43 UTC began an orderly shutdown and the whole VM froze at the Docker stop step (zero log lines of any subsystem until 01:24:51); a console force-stop (`StopInstances`, `skipOsShutdown: true`, 01:20:17) and `StartInstances` (01:24:39) recovered it: about 9 minutes, confirmed by syslog and CloudTrail (not "over an hour"). The previous boot had run 205 days; `OOMKilled: false` and `RestartCount 0` after. The unbounded memory above is the leading explanation, no kernel OOM line exists. On this single-node cluster every restart makes the whole cluster unavailable during recovery, and UDP messages sent in that window are lost with no error on the sender.
- **`graylog_299` and the Default index set (`GITIN-1854`):** the Default index set rotates by size (4.17 GiB) and deletes beyond 36 indices; `graylog_299` hit the 1000-field `index.mapping.total_fields.limit` (and `sp_platform__50` too) so it never rotated again after 2026-01-31 and grew to 477.6 GB while the series sat exactly at the 36-index cap. A disk alert (89 % used, low watermark; flood-stage would force every index read-only and stop SmartPedidos and SmartLoyalty ingestion) was resolved on 2026-08-15 by deleting `graylog_299` and `graylog_264`-`graylog_298` through the raw OpenSearch API (disk 89 % → 54 %). **That broke the `graylog_deflector` alias** (it then pointed at the stale legacy `graylog_0` and raised `mapper [sc-status] cannot be changed` errors); `POST /api/system/deflector/{indexSetId}/cycle` (not `/rotate`, which 404s) created a clean `graylog_1`. Rule: never delete a Graylog-managed write index through the raw API; if unavoidable, cycle the deflector immediately. The field-limit fix on the Default index set (raise `index.mapping.total_fields.limit` through `_settings`) was still not applied when last recorded, so the next write index can stick the same way.
- **Other index sets (read 2026-08-14):** `AWS_Logs` rotates every `PT12H`, up to 720 indices; `AWS_WAFV2` `P60D`, 100 (changed by hand from size-based); `SP_Platform` `PT12H`, 1440; `SML_MobileApp` and `SML_WebService` `P2M`, 12 and 6. Index sets rotate and retire independently. Whether `AWS_WAFV2` receives live traffic was not settled (its newest documents read months old, `_doc` sort is unreliable across a wildcard pattern).
- **Duplicate indexing:** `SP_Platform`, `SML_WebService`, `SP_WAFV2` and `SML_MobileApp` had `remove_matches_from_default_stream: false`, so every message was indexed twice (confirmed for one `_id` in both an `aws_wafv2_` index and `graylog_292`); set to `true` on 2026-08-14. Historical duplicates are not removed. `SP_Concentrador` was already correct.
- **Indexer failures from application code (Dev, not applied when last checked 2026-09-18):** `log.js` `_stdout` (both services) only drops `undefined`, never sentinel strings, so numeric-mapped fields reject a whole document with `mapper_parsing_exception`: `msg_branch_id` = `"unknown"` (platforms-service, `branchId ?? 'unknown'` in every strategy and in `aws.js`; 242 of 250 failures sampled on 2026-09-18), `msg_rest_status_code` = `"unknown"` (error paths in both services with no HTTP status), `msg_rest_status` = `"error"` (one site: `concentradorService` `api/src/utils/httpClient.js:35`), and `msg_rest_platformId`. Fields come from the `rest` object flattened with the prefixes `msg_` and `rest_`. The fix is in `log.js` (both copies), plus a repo-wide sweep of `?? '<string>'` fallbacks. A Graylog pipeline rule on `SP_Concentrador` moves `msg_rest_status` = `"error"` to `msg_rest_status_raw`; simulator-validated, **not confirmed on live traffic** (failures kept appearing: the stream's routing rules were never checked, see `operations/CLAUDE.md`). A rejected document is never indexed, so it cannot be looked up afterwards.
- **PII in indexer failures:** `msg_meta_newOrder_user_id` carries a real customer email into the error text of the "Indexer failures" page: `platform.js` `validateNewOrders` logs the whole raw webhook payload (`meta: { newOrder }`, lines 648 and 661) with no redaction; the originating platform was not identified; a draft Dev email exists, not sent when last recorded.

**Diagnostic lesson:** when messages "stop arriving" in Graylog with nothing wrong visible on the sending side, check this cluster's own health (`GET _cluster/health`, `docker logs opensearch` for restart signatures) **before** spending significant time on the sender's config. A multi-hour investigation during `GITIN-1827` chased NXLog configuration changes before finding the real cause here.

## REST API query notes (SmartPedidos / SmartLoyalty stack, confirmed 2026-10-09 and 2026-10-13, GITIN-2208, GITIN-2211)

- Only `GET /api/search/universal/absolute` has answered; the histogram and terms endpoints return 404 on `graylog/graylog:5.2.12`. Count per interval with one request per interval (`limit=1`, read `total_results`).
- Time parameters: use ISO with `Z` (`2026-10-12T01:00:00.000Z`). A plain date string is read as UTC-3 and shifts the window by 3 hours.
- Queries: a single quoted phrase works (`"platforms-service"`); boolean queries and several terms combined with `OR`/`AND` returned HTTP 500 (also `Missing search type result!`); issue one request per term.
- Volume: one request per minute with `limit=3000` returned complete minutes of `platforms-service` (about 1,000-1,300 messages per minute in October 2026); `total_results` equals the messages returned when the limit is not hit.
- Message shape of `platforms-service` (JSON in `message`): `timestamp`, `service`, `level`, `category` (`PERF`, `ORDER`, `INFRA`, `INTEGRATION`), `message` and a `rest` object. `[PERF/INFO] http_response platform=<P> action=<A>` lines carry `rest.duration_ms` and `rest.status`; they are the way to measure delivery-platform latency and consumer-side activity (readyOrder, dispatchOrder, deliveryOrder, viewOrder). Raw messages can include order or account data: save them to files excluded from version control (`detail-*`).
- Retention: per-minute messages were still available 10 days back (2026-10-03).
- `ERROR` as free text also matches `[PERF/INFO] http_response` lines (INFO lines that contain the word) and IIS lines of another system (source `52.234.224.34`): filter on the JSON `level` field. A quoted phrase must match the real text: `checkOfflinePOS` returned 0 because the messages are `checkOfflinePOSpeya`/`...mercadopago`/`...rappi`, use `checkOfflinePOS*`. The startup/shutdown-word searches returned HTTP 500 even as plain words combined with a service name.
- **"ERROR spike" baseline (`GITIN-2208`, 2026-10-08/09, local UTC-3):** night baseline ~1,000 `ERROR`/h, daytime 2,700-3,400, evening peaks 4,000-6,900; the bursts are per-branch fan-outs of `concentrador-service` at the start of each half hour (500-600 `Branch OpenClose Error` messages inside one minute, one per branch id): `openClosedBranchesGrido` timeouts (`timeout of 20000ms exceeded`) were new on 2026-10-09 (08:00, 09:00, 09:30; zero the day before, cause not found), `enviarEstadoPedidosYa` HTTP 400 from 10:00 every half hour is a daily pattern (cause open), plus a constant `No authorization token was found` (40 per 5 minutes) and MercadoPago token failures (probably the `invalid_grant` wallet credentials also seen on the SmartCloud side, `GITIN-2209`). Each failing call also writes an INFO line that matches the free-text filter, doubling the apparent `ERROR` count.
