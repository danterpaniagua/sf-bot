## Full 3-day endpoint response-time table, rebuilt from raw properties JSON (bypasses the broken promotion)

Since GITIN-2034's field promotion only fixed *today onward* (see previous section), the requested 3-day table was rebuilt by pulling raw `properties` (unparsed JSON string, present on every `AppServiceHTTPLogs` message regardless of promotion status — confirmed via a raw message sample) via Graylog's CSV export endpoint (`GET /search/universal/absolute/export`, `Accept: text/csv`, `fields=timestamp,properties`, stream `6a8edd694814bcaed323f9d6`) and parsing/bucketing it locally in Python (10-min buckets × `CsUriStem`, avg/max/count of `TimeTaken`). 595,472 raw rows exported for the full `2026-09-11T18:20Z`–`2026-09-14T18:20Z` window; output: `data/sales_timetaken_by_path_3d_10m_RAW.csv` (9,066 rows). `_exists_:properties.CsUriStem` had returned 0 earlier — confirmed why via a raw sample: `properties` arrives as a single JSON **string** field, not decomposed into nested sub-fields by Elasticsearch, so it was never independently aggregable without either the (broken, pre-today) promotion step or this local-parse workaround.

**This materially changes the picture from the earlier "candidate endpoint" framing (H5) — supersedes it, doesn't just add to it:**

- **`/api/v1/Shift/GetPaginatedForReportByFilterAsync` is chronically slow (~4,000-16,000ms) across the *entire* 3-day window, including long stretches with no crash anywhere nearby** (e.g. 2026-09-11 18:20-22:40, 2026-09-12 11:20-17:50 — completely quiet daytime periods). This is a real, pre-existing, always-on performance problem, but it is **not correlated with crash timing** — it's not a spike that precedes each crash, it's just permanently slow. The earlier H5 framing ("candidate for the memory leak, 5-6s vs 10-100ms baseline") was based on only 2 ad-hoc samples and undersold how normal that latency actually is for this specific endpoint. Downgrading: still worth fixing (chronic multi-second latency on a report endpoint is its own problem), but not singled out as the OOM driver anymore.
- **What actually happens at crash onset is a system-wide request pileup across nearly every endpoint simultaneously, not one hot path.** Walking the 10-min buckets through the confirmed 2026-09-12T23:15:26Z onset: at 23:00 everything is normal (`Sale/Create` avg 88ms); by 23:10 latency starts climbing across the board (`Sale/Create` avg 535ms, max 30.8s); by 23:20 it's severe (`Sale/Create` avg 2.5s/max 258s, `WsFeAr/CaeRequest` avg 4.3s/max 256s, `PaymentMethod/GetAll` avg 11.5s/max 217s); by 23:30 it peaks (`Sale/Create` avg 7.6s/max 263s, `Shift/CreateAndOpen` avg 16.6s/max 71s, `Shift/GetLastShifts` avg 11.0s/max 122s) — literally every endpoint hit that bucket shows multi-second-to-multi-minute latency; by 23:40 it's essentially back to normal (`Sale/Create` avg 80ms), matching the worker being force-killed and restarted. Same shape confirmed independently around the 2026-09-13T23:55Z crash (23:50 bucket: `Shift/GetPaginatedForReportByFilterAsync` avg 162.9s, `Sale/Create` max 230.6s, `WsFeAr/CaeRequest` avg 11.3s/max 231s). This is the signature of the whole managed process stalling (GC thrashing under memory pressure stops all threads together), not one query starving memory on its own.
- **CONFIRMED: the ~230-second ceiling is Azure App Service's own platform-level idle-connection timeout — not application code, not configurable.** Verified against Microsoft's own troubleshooting doc ([Web request times out in Azure App Service](https://learn.microsoft.com/en-us/troubleshoot/azure/app-service/web-request-times-out-app-service), Microsoft Learn): *"Azure Load Balancer has a default idle timeout setting of four minutes... App Service returns a timeout to the client if your application doesn't return a response within approximately 240 seconds (230 seconds on a Windows app, 240 seconds on a Linux app)."* Enforced at the Azure hardware load balancer, hardcoded, cannot be changed from the app side. Sales-PRO is Windows-hosted (confirmed throughout this investigation), so 230s — not 240s — is the exact expected value, matching the data precisely: dozens of `max_ms` values cluster tightly at 229,996-230,740ms (e.g. `POSGetAll` alone: 2026-09-13T01:00, 01:20, 01:50, 02:20, 03:00, 03:10, 03:30, 03:50, 14:50 through 18:10 almost continuously, 18:30, 18:40, 18:50, 19:00, 19:40, 20:00, 20:10, 20:30, 21:00, 21:10, 23:30, plus more into 2026-09-14). This reframes the mechanism: the worker isn't necessarily "processing" a given endpoint for 230 seconds; it's fully unresponsive (GC-paused/thread-pool-starved) for that long, and whichever requests happen to be in-flight when the LB severs the idle connection get logged with `TimeTaken≈230,000ms` regardless of which endpoint they hit. The specific endpoint names captured at ~230s are therefore largely incidental (whatever was queued at that moment), not individually causal — reinforces that this is a whole-process stall, not a per-endpoint problem.
- **The degraded/thrashing periods are much longer and more frequent than the 7 discrete crashes the Azure crash detector counted.** The ~230s-ceiling pattern recurs across long, mostly-continuous stretches — roughly 2026-09-13T01:00-04:00, 14:50-21:20, and 23:30-23:55 — not just in the narrow windows immediately around each of the 7 confirmed crash timestamps (04:05, 17:30, 18:10, 18:40, 19:15, 20:30, 23:55). This is consistent with the already-established "4 instances, only 1 crashes/degrades at a time" model (only a fraction of total request volume per bucket hits the 230s ceiling — e.g. 2026-09-13T21:00: 191 `POSGetAll` requests, avg 3.7s, only enough hitting max=230s to skew the average, not all of them — matching ~1-of-4 instances being unhealthy while 3 serve normally). But it means the actual customer-impact window on 2026-09-13 was likely much broader than "7 brief crash moments" — POS terminals were probably seeing intermittent timeouts across several multi-hour stretches that day, not just briefly 7 times. Not yet reconciled instance-by-instance; flagged as a scope-of-impact correction worth carrying into any follow-up communication about this incident's actual duration/severity.

## Remediation-direction exploration (2026-09-19) — health check quality and crash-recovery mechanism

Session context: `cloud/events/20260919_gitin2073-appserviceplan-insights-onboarding/investigation.md` independently found (starting from a different symptom — the `Sales_CPU_Alert`/Autoscale discrepancy) that `SmartFran-Cloud-Sales-Plan-PRO`'s Autoscale resource has 6 profiles, several pinned to fixed capacity with no scale rules at certain hours, and that every CPU/Memory rule uses `statistic: "Average"` (Plan-wide blended value, not per-instance) — `dividePerInstance` does not fix this per Microsoft's own docs (only applies to `Sum`/`Count`-aggregated metrics); `statistic: "Max"` is the documented lever for reacting to a single saturated instance. **Directly extends this ticket's already-confirmed "autoscale ceiling" finding (line 77-83 above)** — same Autoscale resource, same underlying capacity-response gap. Cross-reference, don't duplicate further detail here.

**`Status/Health` confirmed to carry zero diagnostic value.** `Source/Services/Sales/SmartFran.Cloud.Sales.API/Controllers/v1/StatusController.cs:25-31` — the `Health()` action does nothing but `return Ok("Its alive!")`, no dependency or resource checks. Can't currently distinguish "process fine" from "about to OOM."

**Compared against SmartLoyalty's `healthcheck.ashx` pattern** (`loyalty/events/20260916_gitin2058_wsv2_lb_healthcheck/healthcheck.ashx`, also `.../20260916_gitin1228_lb_healthcheck/`) — that handler checks CPU/Memory (via `PerformanceCounter`) and DB/Redis connectivity, returning `200/400/500` with a JSON status body, letting the LB/health probe react to resource pressure before a full crash. **Not directly portable**: `.ashx`/`IHttpHandler` is an ASP.NET Framework (`System.Web`) construct; `SmartFran.Cloud.Sales.API` is ASP.NET Core, which has no `.ashx` support at all. The idiomatic Core equivalent would be a minimal `/healthz` endpoint or the built-in `Microsoft.Extensions.Diagnostics.HealthChecks` middleware — not yet built, flagged as a possible improvement, not committed to.

**Instance lifecycle clarified — important distinction for any remediation proposal:**
- **Planned stop** (deploy, Autoscale scale-in, manual restart): ANCM signals the app, `IHostApplicationLifetime.ApplicationStopping` fires, app gets `shutdownTimeLimit` (default 10s, in-process hosting) to drain in-flight requests and close connections cleanly before exit. A real, implementable "nice shutdown" — but irrelevant to the OOM crashes this ticket is about.
- **OOM crash** (what's actually happening here): the process is already failing when memory is exhausted — `ApplicationStopping` never fires, there's no graceful window, ANCM just detects the dead process and restarts it. **No app-code shutdown handler can fix this**, since by definition there's no working runtime left to run drain logic in.
- **The actually-relevant lever for this ticket:** App Service Auto-Heal rules (`Microsoft.Web/sites/config` → `autoHealRules`) can recycle the worker process proactively at a private-memory threshold, *before* full OOM — and unlike a crash, an Auto-Heal-triggered recycle is graceful (ANCM drains into a fresh process first). **Not yet checked whether Sales-PRO has any `autoHealRules` configured** — this is the concrete next step from this exploration, not a code change.
