# Investigation — Sales Serilog not sending JSON to stdout (GITIN-1811)

## Objective

Dev team reports Sales isn't sending Serilog JSON messages to standard output (unlike Business, which works fine). Cross-reference repo source, Azure config, and Graylog data to find the root cause.

## Key facts established (repo)

- **Both Sales and Business call the exact same shared bootstrap**: `SmartFran.Cloud.Provider.Logger.Core.SerilogBootstrap.Configure(builder.Configuration, "<service name>")`, defined once in `Source/Common/Providers/SmartFran.Cloud.Provider.Logger.Core/SerilogBootstrap.cs`. The application-level Serilog code is identical between the two services — this is not a per-service C# logging bug.
- That shared bootstrap's only sink (per code comment, "GSFC-LOG-1... Sin sinks heterogéneos, sin AzureBlobStorage, sin File, sin ApplicationInsights") is `loggerCfg.WriteTo.Console(new ExpressionTemplate("{ {Timestamp: @t, Level: @l, MessageTemplate: @m, Exception: @x, Properties: @p} }\n"))` — a CLEF-style JSON line written to `Console`/stdout. Both `Program.cs` files also do `builder.Logging.ClearProviders(); builder.Logging.AddSerilog(...)` identically.
- **Sales is Windows (IIS/ANCM-hosted), Business is Linux (container-hosted)** — confirmed in `cloud-graylog/CLAUDE.md`'s App Services table and by `SmartFran.Cloud.Sales.API.csproj` (`Microsoft.AspNetCore.AzureAppServices.HostingStartup` package reference — Windows-specific, absent from `SmartFran.Cloud.Business.API.csproj`).
- **No `web.config` is checked into `SmartFran.Cloud.Sales.API`'s source** — the only `web.config` found in the whole repo (`Documentation/v2.24.00/web.config`) is for the Pos Blazor WASM static site, unrelated to Sales.API. This means whatever `web.config` actually runs in production was generated by the .NET SDK at publish time with its defaults, not hand-authored/reviewed.
- No `AspNetCoreHostingModel` override in the `.csproj`, no `stdoutLogEnabled` setting found anywhere in the repo.

## CONFIRMED (2026-08-10, via C1–C4) — target was actually Sales-DEV, see correction above

Live `web.config` on `SmartFran-Cloud-Sales-DEV` (via Kudu VFS, C4):
```xml
<aspNetCore processPath="dotnet" arguments=".\SmartFran.Cloud.Sales.API.dll" stdoutLogEnabled="false" stdoutLogFile=".\logs\stdout" hostingModel="inprocess" />
```
`stdoutLogEnabled="false"` — root cause confirmed, no longer just a hypothesis. IIS/ANCM is explicitly configured to discard the process's stdout. Serilog's Console sink almost certainly writes correctly inside the process; it never leaves the worker process.

`az webapp log show` (C1) confirms Sales-DEV's `applicationLogs.fileSystem.level` is also `"Off"` — even if ANCM wrote the stdout file, the platform isn't collecting it either. Both gates closed. Business's equivalent config (C2) has everything `Off`/`false` too, yet Business's console logs reach Graylog fine — confirms Linux needs none of these Windows-only ANCM/IIS toggles, container stdout is captured natively regardless. (Note: which Business instance C2 actually targeted has the same PRO/DEV ambiguity as Sales did — the conclusion itself, Linux needing none of these toggles, holds either way since it's about the OS/hosting model, not the specific instance.) `az webapp config appsettings list` (C3) found no `ANCM_stdoutLogEnabled` override — nothing corrects this at runtime.

No `web.config` is checked into `SmartFran.Cloud.Sales.API`'s source, so `stdoutLogEnabled="false"` is just the .NET SDK's unmodified default — and since the same project builds both DEV and PRO (see the GitHub Actions section below), this default applies regardless of environment. Reads as a gap in the GSFC-LOG-1 rollout (validated on Linux/Business first, never enabled for the Windows apps that actually need this flag) rather than a regression — **Pos-DEV is also Windows-hosted and likely has the identical gap; Sales-PRO and Pos-PRO status is separately unconfirmed.**

## Working hypothesis (unconfirmed — needs Azure + Graylog data) — historical, see CONFIRMED above

**On Windows App Service, ASP.NET Core's IIS/ANCM stdout capture is disabled by default** (`stdoutLogEnabled="false"` in the SDK's default generated `web.config`) unless explicitly turned on. Linux App Service has no equivalent gate — the container's stdout/stderr is captured natively by the platform regardless of any app-level setting, which is why Business (Linux) works with the exact same C# code that (hypothetically) fails on Sales (Windows).

Under this hypothesis, Serilog's `Console` sink is writing correctly inside the Sales process, but IIS/ANCM never forwards that output to the platform's `AppServiceConsoleLogs` stream — the JSON never leaves the box. This would explain "Serilog isn't sending JSON to stdout" as reported by dev, from the *platform's* point of view, even though the app code itself isn't at fault.

**Secondary consideration:** `SmartFran.Cloud.Sales.API.csproj` still references `Microsoft.AspNetCore.AzureAppServices.HostingStartup` — the official Microsoft package that auto-wires Windows-native App Service logging providers (Blob/File logger) via `IWebHostBuilder` hosting startup. `Program.cs`'s `builder.Logging.ClearProviders()` would wipe out anything that package auto-registers, same as it wipes the default console provider. Worth checking whether this package is legacy/dead weight from a pre-GSFC-LOG-1 logging setup (see the "Logging estandarizado (GSFC-LOG-1)" comment — implies a prior, more heterogeneous logging setup existed and was consolidated) or whether it's still doing something relevant that conflicts with `ClearProviders()`.

**Not yet checked / open questions:**
1. Is "Application Logging (Filesystem)" actually enabled at the Sales App Service level? (Separate, older setting from Diagnostic Settings/Event Hub — gates whether ANCM's stdout capture, if enabled, actually reaches the platform's log category.)
2. What does the *live* `web.config` on Sales actually contain (`stdoutLogEnabled` value)? Only visible via Kudu, not the repo.
3. What hosting model is actually configured (`InProcess` is the SDK default when unset) — does that matter here, or is this purely about `stdoutLogEnabled`?
4. What does Graylog actually show for Sales right now — is `AppServiceHTTPLogs` (platform-generated, doesn't depend on app code) arriving fine while `AppServiceConsoleLogs`/`AppServiceAppLogs` (app-level output) is missing or empty? That split would strongly support the hypothesis. Note: `cloud-graylog/CLAUDE.md`'s 2026-07-02 status note says Sales was validated "for both Azure log schema shapes (`AppServiceAppLogs` and `AppServiceHTTPLogs`)" — if `AppServiceAppLogs` really was flowing back then, either something regressed since (possibly the GSFC-LOG-1 consolidation itself, which post-dates that note), or that category was reaching Graylog via a different mechanism than the current Console-only Serilog pipeline.

## GitHub Actions workflow confirms the gap (this is the actual Sales-DEV deploy pipeline)

Reviewed the actual CI/CD workflow (`Compile/Deploy Sales API (WIN) to DEV environment`, triggers on push to `dev` branch, deploys `SmartFran-Cloud-Sales-DEV`) — this is the real deploy pipeline for the app under investigation, not a hypothetical comparison. `runs-on: windows-latest`, `dotnet publish ... --no-build`, straight to `azure/webapps-deploy@v2` — no step anywhere generates, transforms, or overrides `web.config`. Confirms there's nothing in the pipeline that could counteract the SDK's `stdoutLogEnabled="false"` default; matches exactly what Kudu showed live.

`--no-build` doesn't affect the proposed fix: it skips re-running the `Build` target, not `Publish` — a `<Target AfterTargets="Publish">` MakeDir hook still fires normally under this workflow (though see ops.md — this specific hook ended up unnecessary once `%home%\LogFiles` was confirmed to pre-exist).

**Relationship to GITIN-1794:** `Sales-DEV` was one of the 8 apps onboarded to Graylog in that ticket. Its end-to-end confirmation (H9/H12) tested `AppServiceHTTPLogs` specifically (platform-generated, doesn't depend on app code) — still accurate, that part of the pipeline genuinely works. This ticket (GITIN-1811) now confirms the other half: `Sales-DEV`'s `AppServiceConsoleLogs`/`AppServiceAppLogs` do **not** reach Graylog, due to this `stdoutLogEnabled` gap — not a suspicion anymore, the actual subject of this whole investigation. `Pos-DEV` (also Windows, same onboarding batch) likely has the same gap, unconfirmed. `Sales-PRO`/`Pos-PRO` status is fully separate and unconfirmed either way. GITIN-1794 itself wasn't reopened/edited — this nuance lives here and in `cloud/docs/infrastructure.md` → "Logging (GSFC-LOG-1)" per event-scope-isolation convention.

## FINAL — platform limitation, not a config problem (2026-08-11)

All three platform gates got fixed and confirmed correct: `web.config` (`stdoutLogEnabled="true"`, path moved to `%home%\LogFiles`), `applicationLogs.fileSystem` (Off→Information), `azureBlobStorage` (Verbose/broken→Off). ANCM confirmed writing real CLEF JSON to the stdout file (Kudu Log Stream, real content pasted and verified). Yet over an hour of real business traffic (`Sale/Create`, `Sale/Close`, fiscal webservice calls) produced zero Console/CLEF-shaped content in Graylog under any category.

Checked directly against Azure rather than guessing further: `az monitor diagnostic-settings categories list`/`list` on the actual resource confirmed `AppServiceConsoleLogs` exists as a category, is `enabled: true` on the real Diagnostic Setting, and points at the correct Event Hub — config is 100% correct. Web search confirmed the actual cause: **`AppServiceConsoleLogs` is not a supported/populated category for .NET applications on Windows App Service at all — only JavaSE and Tomcat.** No amount of correct configuration can make this category receive data for this app. This is why GSFC-LOG-1's design works for the Linux apps (Business, Platform, Person, Admin, Catalog, Orders — native container stdout capture, category is supported there) but structurally cannot work for the two Windows apps (Sales, Pos).

The documented alternative (`AppServiceAppLogs` via `AzureMonitorTraceListener` + `System.Diagnostics.Trace`, not Serilog) is explicitly marked as unsupported for ASP.NET Core in the source found (a 2020 post — possibly stale, not independently re-verified). Real `AppServiceAppLogs` content *has* been observed for Sales-DEV (`"Thread was being aborted."`), but that's almost certainly from Windows Event Log capture, a separate mechanism — its presence doesn't prove the Trace-based path would carry Serilog content.

**Conclusion:** investigation is closed on the SRE side. Resolution requires a dev/architecture decision on how Windows apps deliver structured logs to Graylog — most likely a direct GELF sink in Serilog (bypassing Diagnostic Settings/Event Hub entirely — ironically the exact thing GSFC-LOG-1 removed), or validating the Trace-based `AppServiceAppLogs` path, or something else. See `ops.md` Acciones propuestas #4 for the options as presented to dev.
