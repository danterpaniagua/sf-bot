# Sales no envía logs JSON de Serilog a stdout — GITIN-1811

## Resumen

El equipo de desarrollo reportó que Sales (ambiente **DEV**) no está enviando los mensajes JSON de Serilog a la salida estándar, a diferencia de Business que funciona correctamente. El análisis cruzado de código (repo), configuración de Azure y datos de Graylog encontró y corrigió tres gates de plataforma reales (`stdoutLogEnabled`, `applicationLogs.fileSystem`, `azureBlobStorage`) — confirmados con contenido JSON real capturado en el archivo de stdout del App Service. Sin embargo, **la causa raíz final es una limitación de la plataforma, no un problema de configuración**: `AppServiceConsoleLogs`, la categoría de Diagnostic Settings que todo el pipeline GSFC-LOG-1 usa para exportar a Event Hub, **no está soportada para aplicaciones .NET en Windows** (confirmado vía documentación de Microsoft — soportada solo para JavaSE/Tomcat). Ningún ajuste de `web.config`/ANCM/Application Logging puede hacer que esa categoría reciba datos para este tipo de app. **Cierre técnico: requiere una decisión de arquitectura del equipo de desarrollo**, no un fix adicional de SRE — ver Acciones propuestas.

## Causa raíz

`stdoutLogEnabled="false"` en el `web.config` desplegado de **Sales-DEV** (confirmado vía Kudu VFS, C4) — IIS/ANCM descarta la salida estándar del proceso `dotnet` en vez de reenviarla a la plataforma. El pipeline de logging estandarizado (GSFC-LOG-1: Serilog → Console JSON → stdout → `AppServiceConsoleLogs` → Event Hub → Graylog) depende de que ANCM capture ese stdout — en Windows eso requiere `stdoutLogEnabled="true"` explícito; en Linux (Business) no existe ese requisito porque el runtime de contenedor captura stdout nativamente sin ninguna configuración adicional. No hay ningún `web.config` versionado en el proyecto `SmartFran.Cloud.Sales.API`, por lo que el valor `false` es simplemente el default del SDK de .NET sin haber sido nunca sobreescrito — no es una regresión de código, es un paso de la migración GSFC-LOG-1 que no se aplicó a las apps Windows. Confirmado vía el workflow real de CI/CD (`Compile/Deploy Sales API (WIN) to DEV environment`) que ningún paso del pipeline genera ni transforma `web.config` — el mismo proyecto, sin override, también compila el deploy de PRO, por lo que este default no depende del ambiente.

**Nota para el equipo de desarrollo — "funciona en mi máquina" no contradice esto:** al correr localmente desde Visual Studio, el proceso se lanza directo (IIS Express o perfil Kestrel) y Visual Studio captura `Console.Out` en vivo, adjuntándose directamente al proceso — ese camino nunca pasa por la redirección de stdout de IIS/ANCM. `stdoutLogEnabled` solo importa una vez que la app corre en el App Service real de Azure (IIS de producción). Que ande bien localmente es exactamente lo esperado bajo esta causa raíz, no evidencia en contra.

**Causa raíz final (H14) — limitación de plataforma, no de configuración:** con los tres gates corregidos y contenido JSON real confirmado en el archivo de stdout (H10), el contenido nunca llegó a Graylog bajo ninguna categoría reconocible como Console/CLEF, ni siquiera con tráfico de negocio real de por medio (`Sale/Create`, `Sale/Close`, llamadas fiscales) durante más de una hora. La causa: **`AppServiceConsoleLogs` no está soportada para aplicaciones .NET en Windows** — confirmado que la categoría existe y está `enabled: true` en el Diagnostic Setting real (`SmartFran.Cloud.DEV.Sales_DiagnosticSettings`), apuntando correctamente al Event Hub `app-logs`, pero la plataforma de Azure simplemente no la puebla para este tipo de aplicación (soportada solo para JavaSE/Tomcat, según documentación de Microsoft). El pipeline GSFC-LOG-1 (`Console JSON → stdout → AppServiceConsoleLogs → Event Hub → Graylog`) funciona correctamente para las apps Linux (Business, Platform, Person, Admin, Catalog, Orders) porque ahí la categoría sí está soportada (captura nativa de stdout del contenedor) — pero estructuralmente no puede funcionar para las dos apps Windows (Sales, Pos), sin importar qué tan bien esté configurado `web.config`/ANCM/Application Logging.

## Acciones propuestas

1. **(Dev)** — ~~Entregado al equipo de desarrollo.~~ **Aplicado en vivo vía FTP y confirmado (H9).** Pendiente: incorporar el mismo `web.config` al repo real (esta aplicación fue manual/directa al App Service, no versionada — sobrevive solo hasta el próximo deploy de CI/CD si no se suma al proyecto). Fix durable, versión final:
   - Agregar un `web.config` versionado al proyecto `SmartFran.Cloud.Sales.API` con `stdoutLogEnabled="true"` **y el log fuera de `wwwroot`**, usando la convención de Azure (`%home%\LogFiles`, directorio administrado por la plataforma) en vez del default relativo `.\logs\stdout` del SDK:
     ```xml
     <aspNetCore processPath="dotnet" arguments=".\SmartFran.Cloud.Sales.API.dll" stdoutLogEnabled="true" stdoutLogFile="\\?\%home%\LogFiles\stdout" hostingModel="inprocess" />
     ```
     El SDK de .NET transforma un `web.config` existente en publish (preserva atributos custom, solo actualiza `processPath`/`arguments`/`hostingModel`), por lo que este override sobrevive a futuros deploys.
   - **Confirmado (2026-08-11, vía Kudu console): `C:\home\LogFiles\` ya existe por defecto** en el App Service — no hace falta ningún target de MSBuild ni código de creación de carpeta. (Se había evaluado un target `MakeDir` para el caso `.\logs\stdout` dentro de `wwwroot`, y alternativamente un `Directory.CreateDirectory` en `Program.cs` para el caso `%home%\LogFiles` — ninguno de los dos es necesario dado que el directorio ya existe.)
   - Sigue pendiente habilitar `applicationLogs.fileSystem` (H4, hoy `"Off"`) — el path correcto por sí solo no alcanza si la plataforma no está configurada para recolectar ese directorio.
   - Validar con un publish de prueba (o el propio workflow de DEV) antes de aplicar a producción.

Requiere validación antes de descartarlo o adoptarlo.
   - Otra alternativa que el equipo de desarrollo considere (p. ej. explotar Application Insights, ya parcialmente cableado en `Program.cs`, como fuente hacia Graylog).
