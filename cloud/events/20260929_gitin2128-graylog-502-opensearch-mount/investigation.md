# Investigation — 20260929_gitin2128-graylog-502-opensearch-mount

**Jira:** [GITIN-2128](https://smartit-ar.atlassian.net/browse/GITIN-2128)

**Note on repo scope:** this is the SmartCloud-dedicated Graylog instance (`sfcloud-monitoreo.smartfran.com`, VM `smartfran-graylog-pro`), whose actual infrastructure/source lives in the separate `cloud-graylog` repo (not part of this `bots/` monorepo) — see `docs/graylog_infrastructure.md`. Tracked here per user direction ("always use bots commands and events when called from here"), following the precedent already established in `cloud-graylog`'s own `CLAUDE.md` of some tickets (e.g. GITIN-1834, GITIN-1794) being tracked in `bots/cloud/events/` rather than locally.

## Status

**Fully converged, 2026-09-29 — both root causes confirmed by direct evidence, nothing left open.** Real outage was ~4 hours (`18:00:36`-`21:54:27 UTC`). The corrupted `fstab` (confirmed via `systemd-fstab-generator`'s own error) is why the outage lasted that long once triggered. The trigger itself — an Azure-platform-initiated VM shutdown at `17:48:33Z` due to a storage-connectivity IO timeout between the host node and Azure Storage — is confirmed via Azure's own official Resource Health RCA (`vma_rca_io_timeout_nodereboot_generic_e17`), external to anything in this VM's own configuration or the `fstab` bug.

## Confirmed facts

- **Symptom**: `https://sfcloud-monitoreo.smartfran.com/graylog/` returned `502 Bad Gateway` (nginx). Reported alongside a fresh ticket, GITIN-2128.
- **nginx error log**, checked for its *full* range (`data/nginx_full_error_range_20260929.txt`, not just a tail): `connect() failed (111: Connection refused)` on `http://127.0.0.1:9000/api/`, **continuously from `18:00:36 UTC` to `21:54:27 UTC`** — 888 occurrences, ~4 hours, not the ~1 hour first assumed from a truncated `tail`.
- **`graylog-server.service`**: a native systemd unit (`ExecStart=/usr/share/graylog-server/bin/graylog-server`), not a container — corrects `cloud-graylog/docs/architecture.md`, which is stale and says "Graylog | 5.2.12 (container)".
- **Two restart cycles that day, not one**: `graylog-server`/`opensearch`/`logstash` all restarted at the same second, `18:00:21`-`18:00:22 UTC` (the real trigger, see below) — and again at `21:01:19`-`21:01:36 UTC` (a manual Azure-level `restart`, most likely a remediation attempt for the already-hours-old outage, not the original cause). Both were clean stops (`Deactivated successfully`), not app-level crashes.
- **`opensearch.service`**: failed the identical way at *both* cycles — `18:00:21` start → `18:01:51` timeout, and again `21:02:52 UTC` onward. Root cause (from `/var/log/opensearch/graylog.log`): `java.nio.file.AccessDeniedException: /var/lib/opensearch/nodes` — OpenSearch could not write to its own data directory, both times.
- **`/var/lib/opensearch`** (on the root filesystem, `/dev/root`) was owned by `root:root`, empty (`total 8`, no `nodes/` subdir), dated `Jul 1 18:35` — a placeholder, not the real data.
- **Real data volume identified**: `path.data: /var/lib/opensearch` in `/etc/opensearch/opensearch.yml` confirmed this *should* be a separate mounted XFS volume. `lsblk -f`/`blkid` confirmed the real disk exists: `nvme0n3p1`, UUID `c40ff0c4-04ca-4f94-9dc5-bf4831316fd4`, 512G, 63-64% used (~326G) — genuinely populated with months of index history, not empty.
- **`/etc/fstab`** contained four lines referencing `/var/lib/opensearch`: one with an **empty `UUID=`** (malformed), and **two duplicate entries** for the correct UUID (`c40ff0c4-...`) — one with `nofail`, one without. `nofail` is why the VM booted successfully despite the mount failing. MongoDB's own fstab entry, by contrast, is a single clean line and mounted correctly throughout.
- **Terraform (`cloud-graylog/terraform/disks.tf`) only manages the Azure disk resource and its VM attachment** (LUN 0, `ReadOnly` caching) — it does not write in-guest `fstab` entries. The corruption was not produced by a `terraform apply` directly.
- Once the volume was remounted (exact mechanism/actor not confirmed — see Open questions) and `opensearch.service` restarted against the correctly-owned data, the cluster came up (`yellow`, 117/133 active shards, recovering normally for a single-node cluster with likely-nonzero configured replicas). Graylog self-healed on its own retry loop — no restart of `graylog-server.service` was needed. Both `http://127.0.0.1:9000/api/` and the public URL confirmed `HTTP 200`.

## Current working theory

Sometime around `17:42`-`18:00 UTC`, someone (likely SSHed directly into the box, given no Azure Activity Log trail) stopped Logstash cleanly and rebooted the guest OS — this is the real trigger, plausibly the same maintenance session where the `fstab` entries got duplicated (H7). On that boot, `/var/lib/opensearch` failed to mount (the corrupted `fstab`), leaving an empty, root-owned directory in its place; `opensearch.service` failed immediately on every start attempt (`AccessDeniedException` trying to create `nodes/` in a directory it doesn't own), reported by `systemd` as a `timeout`. `graylog-server.service` restarted fine at the process level but could never finish initializing (never opened port 9000) because it depends on OpenSearch — producing the `502` from `18:00:36 UTC` onward. The outage then simply sat broken for ~3 hours. At `21:00:50`-`21:01:28 UTC`, an engineer issued a manual Azure `restart` — very plausibly an attempt to fix the already-ongoing outage — but since the same corrupted `fstab` was still in place, `opensearch.service` failed the identical way again (`21:02:52 UTC`), and the `502` continued. The actual fix (this session) came later: the volume got correctly mounted and OpenSearch restarted against real, correctly-owned data, recovering without data loss and ending the outage at `21:54:27 UTC`.

## Ruled out

- **Container-based deployment** — `docs/architecture.md`'s "Graylog (container)" claim is stale; confirmed via the actual systemd unit file that it's a native process.
- **A slow-startup/resource-exhaustion timeout** (the initial hypothesis, based on the documented historical `memlock`/heap-pressure issue for this system) — ruled out once the actual `graylog.log` showed an immediate `AccessDeniedException`, not a genuine slow start. The historical OOM/memlock issue is real (confirmed in `cloud-graylog/CLAUDE.md` and this VM's own `journalctl` history, e.g. `2026-07-16`) but is **not** what happened today.
- **Terraform apply as the direct cause of the fstab corruption** — `disks.tf` doesn't touch in-guest fstab; ruled out as the *direct* mechanism, though a terraform-driven disk resize/reattach at some point in the past remains a plausible indirect trigger for why someone manually touched the mount config (unconfirmed).

## Open questions / next steps

- **MAJOR CORRECTION, 2026-09-29 — the real outage started ~3 hours earlier than documented, via a second, previously-unaccounted-for restart cycle.** Confirmed directly (`data/nginx_full_error_range_20260929.txt`): the `502`/`Connection refused` pattern actually ran continuously from **`18:00:36 UTC` to `21:54:27 UTC`** (888 occurrences) — not just from `21:11` as first assumed (that was only what a `tail` happened to show). Tracing back (`data/opensearch_earlier_check_20260929.txt`, `data/logstash_status_and_log_20260929.txt`): `graylog-server`, `opensearch`, and `logstash` all restarted at the same second, **`18:00:21`-`18:00:22 UTC`** — a full reboot. `opensearch.service` failed the exact same way then (`18:00:21` start → `18:01:51` timeout) as it did later — meaning the `fstab` corruption (H4/H7) was already present and already broken by `18:00`, not first triggered at `21:01`.
- **This earlier reboot (`~18:00:21`) has no Azure Activity Log trail at all** — queried `17:30`-`18:10 UTC`, empty result (`data/az_activity_log_graylog_vm_earlier_20260929.txt`). Since Azure's Activity Log only captures ARM-level (Portal/CLI/API) actions, an empty result for a moment that clearly *was* a full reboot (three services restarting at the identical second) points to an **in-guest reboot** — someone SSHed in and ran `reboot` directly, bypassing Azure's control plane entirely. Also found: Logstash received a clean shutdown signal at `17:42:57`-`17:44:38 UTC` (all 4 Event Hub partition pumps stopped "as per the request") — ~16 minutes before the reboot, consistent with a deliberate maintenance action (stop services → reboot) rather than a crash.
- ~~Why did the VM reboot at `21:01 UTC`?~~ — the `21:00:50`-`21:01:28 UTC` restart **is** confirmed via Azure Activity Log as a deliberate manual `Microsoft.Compute/virtualMachines/restart/action` (`data/az_activity_log_graylog_vm_20260929.txt`, caller redacted to role label). But given the outage had already been running for 3 hours by then, **this second restart is much more plausibly a remediation attempt for the already-ongoing outage** (someone trying "turn it off and on again" on a system that had been broken since `18:00`) than the original trigger. It didn't fix anything, since the underlying `fstab` corruption survived both boots.
- **The real open question is now: what happened at `17:42`-`18:00 UTC`** — who/what stopped Logstash and rebooted the guest, and why. User recollection (see H7) ties a `terraform apply` + manual `fstab` edit to this general timeframe — worth confirming whether that maintenance session is exactly this one. **Two candidate mechanisms checked and ruled out** (`data/update_and_login_check_20260929.txt`): (1) an automatic OS update — `unattended-upgrades`' last run that day was `06:04:28 UTC` (11+ hours earlier), upgraded only non-kernel packages, no `/var/run/reboot-required` flag present, `apt/history.log` empty for `15:00-18:59 UTC`; (2) an SSH login session — `last -F` shows **no login recorded for `2026-09-29` at all**, including around `17:42-18:00 UTC`. This second result isn't fully conclusive (could reflect `wtmp` rotation/reset rather than genuinely no session), but as things stand, **the trigger for this reboot is unexplained** — not an update, and no recorded interactive login. Worth checking Azure Run Command history or serial console logs if this needs to be pinned down further; not done in this session.

- **MAJOR NEW EVIDENCE, 2026-09-29 (user asked to check `syslog`/kernel for a system error) — this boot was troubled, not a clean reboot, and directly confirms the fstab bug in the system's own words** (`data/kernel_syslog_check_20260929.txt`, `journalctl -k` + full-system `-p warning` for `17:20`-`18:10Z`):
  - **`17:56:45Z`** — kernel starts initializing hardware (earliest boot-stage messages: `PCI: System does not support PCI`, NVMe/multipath device discovery) — this is the actual boot start, ~12 minutes after Logstash's clean shutdown at `17:44:38Z`.
  - **Same moment**: `systemd-fstab-generator[159]: Failed to create unit file '/run/systemd/generator/var-lib-opensearch.mount', as it already exists. Duplicate entry in '/etc/fstab'?` — **the exact root cause (H4/H7), confirmed directly by the system itself at the moment of failure**, not just inferred from `cat /etc/fstab` after the fact.
  - **`17:56:46Z`** — `systemd-journald`: *"File ... corrupted or uncleanly shut down, renaming and replacing."* This boot followed an **unclean** shutdown — contradicts the earlier characterization of this cycle as a simple clean reboot. Whatever ended the prior session was not a graceful `reboot`.
  - **`17:57:39Z`** — `Timed out waiting for device dev-disk-by-uuid.device` → `Dependency failed for var-lib-opensearch.mount` — the mount failure cascading through systemd's dependency graph, consistent with (not separate from) the fstab-generator error above.
  - **`17:59:45Z`-`18:00:19Z`** — **`systemd-journald` itself missed its own 3-minute watchdog and was killed** (`Main process exited, code=killed, status=6/ABRT`, `Failed with result 'watchdog'`) — a core system daemon failing its own liveness check is a strong signal of severe, system-wide stall (I/O contention or scheduling starvation), not a targeted OpenSearch-only problem.
  - **`18:00:19Z`-`18:03:21Z`** — a cascade of **unrelated** services all timing out on start: `networkd-dispatcher`, `dmesg.service`, `snapd`, `udisks2`, `ModemManager`, and `opensearch` among them. The whole boot was stalled broadly, not just the OpenSearch mount path.
  - **Revised theory**: this reframes the incident. It's not "a clean reboot happened to expose a pre-existing fstab bug" — it looks more like the VM came back from an **unclean** stop/crash and then had a genuinely troubled boot (something blocking I/O or scheduling severely enough to starve `journald`'s own watchdog for 3+ minutes). The fstab bug is confirmed as a real, independent contributing cause (explicit generator error), but it may not be the *whole* story for why this particular boot was so degraded. **What caused the unclean shutdown in the first place, and what caused the broader boot-time stall, are now the two real open questions** — bigger than just "why did fstab have duplicate entries."

- **CPU/disk metrics pulled for the window** (`data/az_vm_metrics_20260929.json`, `data/az_vm_disk_throttle_metrics_20260929.json`), user's own follow-up to check for resource exhaustion:
  - **CPU**: stayed low throughout (1-4%, one 20% blip at `18:04` during recovery) — not a CPU-exhaustion story.
  - **`Available Memory Bytes` has a real gap**: no data `17:50Z`-`17:54Z`, then a literal `0.0` reading at `17:55Z`, then jumps to `~33GB` at `17:56Z` (the post-boot baseline, before any JVM heaps have allocated — not a "recovery," just what a freshly-booted box with nothing running yet looks like, versus the pre-incident steady-state of `~10.6GB` free with Graylog/OpenSearch/Logstash's combined JVM heaps loaded). The gap+zero is consistent with the guest/monitoring agent itself being unresponsive during that window, not just individual services being slow.
  - **`OS Disk Queue Depth` spiked hard twice**: `67` at `17:47Z` (right as Logstash was shutting down) and `56` at `17:59Z`-`18:00Z` (during the boot stall) — normal is near `0`. `Data Disk Queue Depth` also elevated in the same windows, less extreme.
  - **Disk throttling ruled out directly**: `OS/Data Disk IOPS Consumed Percentage` and `...Bandwidth Consumed Percentage` never exceeded ~16% in this whole window — nowhere near the provisioned cap. So the queue buildup was **not** because the VM was demanding more I/O than its disk SKU allows.
  - **Read as a whole**: high queue depth *without* high IOPS/bandwidth consumption points toward the underlying **Azure Storage backend itself responding slowly** (a platform-side latency event) rather than a guest-side or human-triggered cause — consistent with everything else ruled out here (no Activity Log trace, no OS update, no recorded SSH login).

- **DEFINITIVELY CONFIRMED, 2026-09-29 — Azure's own Resource Health / official RCA** (`data/az_resource_health_events_vm_20260929.json`), checked at the user's request. This is not inference — Microsoft's own root-cause document for this exact VM and window:
  - **`17:48:33Z` — `VirtualMachineStorageOffline`**: *"The Virtual Machine is currently stopped due to a temporary loss of access to disk."*
  - **Official RCA, event `vma_rca_io_timeout_nodereboot_generic_e17`, `platformInitiated: true`**: *"This unexpected occurrence was caused by an Azure initiated VM shutdown triggered by detection of temporary IO transaction timeouts between the physical host node where your VM was running, and the Azure Storage services where your Virtual Hard Disks (VHDs) reside. Azure platform continuously monitors reads and writes (IO transactions) from your VMs to Azure Storage. If transactions do not complete successfully within 180 seconds (inclusive of retries), the connectivity is considered to be lost and a temporary VM shutdown is initiated to preserve data integrity and prevent corruption of your VM. After the platform detects that the storage service connectivity is restored, the VM is automatically restarted."* Resolution note: *"VM was restored following reboot of the host node."*
  - **`17:54:35Z`** — `impactMitigationTime`, storage connectivity restored (~6 minutes after `17:48:33Z`) — the guest kernel then began booting at `17:56:45Z`, ~2 minutes later, consistent with the host-level reboot process completing first.
  - **`21:01:17.117Z` — `VirtualMachineRebootInitiatedByControlPlane`, title "Rebooted by user"** — independently re-confirms the second cycle via a completely different Azure system (Resource Health, not just Activity Log), matching what was already found.
  - **This resolves H9 completely and explains every piece of evidence gathered**: no Activity Log trace for the first cycle (this was an Azure-automated protective action, not a user/API call — Resource Health captures platform-initiated events that Activity Log's ARM-action log doesn't); the "uncleanly shut down" journal marker (Azure force-stopped the VM to prevent VHD corruption, not a graceful shutdown); the disk queue spike with near-zero IOPS/bandwidth consumption (the storage was genuinely *unreachable*, not merely slow — no transactions could complete to register as "consumed"); low CPU throughout (the VM was blocked waiting on I/O, not computing); and the cascading service-start timeouts during the `17:59-18:03Z` boot (recovering from a forced host-level reboot, with multiple services racing to reconnect to disks/network simultaneously).
  - **Genuinely nothing left to root-cause further here** — this was a transient Azure platform/host-storage connectivity issue, external to anything in this VM's own configuration, Terraform, or the fstab bug. The fstab bug (H4/H7/H8) is what turned this normally-transient, auto-recovering platform event into a ~4-hour application outage — without it, OpenSearch/Graylog would very likely have come back cleanly on their own once the host rebooted, the same way MongoDB did.
