**Tags:** SmartCloud, Graylog

## Resumen

`sfcloud-monitoreo.smartfran.com` (Graylog dedicado de SmartCloud, VM `smartfran-graylog-pro`) devolvió `502 Bad Gateway` el 2026-09-29, de forma continua **desde las `18:00:36 UTC` hasta las `21:54:27 UTC`** (~4 horas, confirmado por el log completo de nginx, no solo la muestra inicial revisada).

La VM tuvo **dos ciclos de reinicio ese día**. El primero — el disparador real del incidente — fue un **apagado protector automático de Azure**: a las `17:48:33 UTC` la plataforma detectó una pérdida temporal de conectividad de I/O entre el host físico y Azure Storage, y detuvo la VM para evitar corrupción de datos (conectividad restaurada a las `17:54:35 UTC`, kernel reiniciado a las `17:56:45 UTC`) — confirmado oficialmente por el RCA de Azure Resource Health, evento externo a esta VM. El segundo, `21:00:50`-`21:01:28 UTC`, fue una acción manual de `restart` vía Azure — muy probablemente un intento de remediación sobre un incidente que ya llevaba tres horas, no la causa original.

En ambos reinicios, el volumen de datos de OpenSearch (`/var/lib/opensearch`, disco XFS dedicado de 512G) no logró montarse por entradas corruptas en `/etc/fstab` (una con UUID vacío, y dos entradas duplicadas para el mismo UUID real) — por eso el segundo reinicio tampoco resolvió nada. OpenSearch no pudo iniciar sobre un directorio vacío propiedad de `root`, y Graylog — dependiente de OpenSearch — nunca terminó de inicializar, dejando el puerto 9000 sin escuchar y produciendo el 502 en nginx durante toda la ventana.

## Causa raíz

El volumen dedicado de OpenSearch (`/var/lib/opensearch`, disco `nvme0n3p1`, UUID `c40ff0c4-04ca-4f94-9dc5-bf4831316fd4`, 512G) no se montó en **ninguno de los dos reinicios** de la VM porque `/etc/fstab` contiene cuatro entradas conflictivas para ese punto de montaje: una con `UUID=` vacío (malformada) y dos entradas duplicadas para el UUID correcto (una con `nofail`, otra sin esa opción). La opción `nofail` es la razón por la que la VM arrancó igualmente pese a la falla de montaje, ambas veces. Sin el volumen real montado, `/var/lib/opensearch` quedó como un directorio vacío propiedad de `root:root` en el filesystem raíz — OpenSearch, que corre como usuario `opensearch`, no pudo crear su directorio `nodes/` ahí (`AccessDeniedException`) y falló en cada intento de arranque, en ambos ciclos. `graylog-server.service` sí arrancaba a nivel de proceso, pero nunca terminaba de inicializar (nunca abría el puerto 9000) por depender de OpenSearch.

**El reinicio real que disparó el incidente fue el primero (`18:00:21`-`18:00:22 UTC`), no el segundo — y fue más grave que un simple reinicio.** Ese primer arranque (kernel iniciando a las `17:56:45 UTC`) no dejó rastro en el Activity Log de Azure (consultado `17:30`-`18:10 UTC`, sin resultados), y **`systemd-journald` registró que el sistema venía de un apagado no-limpio**. El propio arranque estuvo severamente saturado: entre `17:59:45` y `18:03:21 UTC`, múltiples servicios sin relación entre sí (`networkd-dispatcher`, `dmesg.service`, `snapd`, `udisks2`, `ModemManager`, además de `opensearch`) fallaron por timeout al iniciar, y `systemd-journald` mismo fue matado por su propio watchdog de 3 minutos (H8) — un patrón consistente con saturación de I/O o scheduling generalizada, no un problema aislado de OpenSearch. En ese mismo arranque, el `systemd-fstab-generator` registró explícitamente el error de entrada duplicada en `/etc/fstab` (H8), confirmando H4 con las palabras del propio sistema. Quince minutos antes del arranque, Logstash había recibido una señal de apagado limpia (`17:42:57`-`17:44:38 UTC`) — consistente con el inicio de una sesión de mantenimiento, aunque lo que vino después (apagado no-limpio, arranque saturado) no encaja con un simple `reboot` planificado. El segundo reinicio (`21:00:50`-`21:01:28 UTC`) sí está confirmado como una acción manual de `restart` vía Azure — muy probablemente un intento de remediación sobre el incidente que ya llevaba tres horas en curso, que no resolvió nada porque el `fstab` seguía corrupto.

**Causa raíz del primer reinicio — confirmada oficialmente por Azure (H9).** A las `17:48:33 UTC`, Azure detectó una pérdida de conectividad de I/O entre el nodo físico de la VM y el servicio de Azure Storage (donde residen los discos), e inició un apagado protector automático para evitar corrupción de datos — política estándar de la plataforma si las transacciones de I/O no completan en 180 segundos. Conectividad restaurada a las `17:54:35 UTC`; la VM reinició su kernel a las `17:56:45 UTC`. Este fue un evento transitorio de la plataforma de Azure, externo a la configuración de esta VM, a Terraform, o al bug de `fstab`. **El bug de `fstab` es lo que convirtió este evento normalmente transitorio y auto-recuperable en una interrupción de ~4 horas** — sin él, OpenSearch/Graylog probablemente se habrían recuperado solos al reiniciar el host, tal como lo hizo MongoDB.

Terraform (`cloud-graylog/terraform/disks.tf`) gestiona el disco de Azure y su adjunto a la VM, pero no escribe el `fstab` dentro del sistema operativo — la corrupción de esas entradas no fue producida directamente por un `terraform apply`.
