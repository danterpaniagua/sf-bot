## Work done

1. **Terraform: added the 6 new apps** to `terraform/app_services.tf` (`data` + `azurerm_monitor_diagnostic_setting` pairs, OS-aware, matching the existing Sales/Business pattern). `fmt`/`validate`/targeted `plan` all passed ("6 to add, 0 to change, 0 to destroy"). **Applied successfully:** "Apply complete! 2. **Orders confirmed flowing end-to-end**, real Graylog document with `resourceId` → `SMARTFRAN-CLOUD-ORDERS-PRO`, correctly parsed. Confirmed at very high volume (7443 msgs in a 15-min sample — more than Business).
3. **Regression found and fixed: applying the Terraform for Pos, Platform, Admin, Catalog silently overwrote their pre-existing Log Analytics Diagnostic Settings.** Root cause: Azure Diagnostic Settings are a full-replace PUT keyed by `name`, not additive. Our new resources reused the same name convention (`SmartFran.Cloud.PRO.{App}_DiagnosticSettings`) the original out-of-band Log Analytics settings already used, so `apply` replaced them outright with Event-Hub-only objects. `terraform plan` couldn't have warned about this — the pre-existing objects were never in Terraform state (created out-of-band).
   - Person was the only one of the 5 pre-existing apps that survived, and only by accident: its original setting's `name` has a stray leading space (`" SmartFran.Cloud.PRO.Person_DiagnosticSettings"`), making it a technically distinct string from ours, so Azure didn't collide them. This gave a real reference for what the originals looked like: **all 9 log categories enabled**, not just the 4 our Terraform manages.
   - **Fix:** consolidated both destinations into the existing Terraform-managed resources (rather than creating a separate temporary object, which risked double-ingestion into Log Analytics) — added `log_analytics_workspace_id` and the 5 missing categories to the `pos`/`platform`/`admin`/`catalog` resources in `app_services.tf`, plus a new `local.log_analytics_workspace_id` in `main.tf`.
   - **First attempt used the wrong workspace subscription.** Person's surviving object listed `workspaceId` in subscription `d6ab1add-4bc8-40b0-8cf8-e7291f7171b0` — apply failed with `404 ResourceNotFound`, and `az resource show`/`az account show` against that subscription returned `SubscriptionNotFound` (doesn't resolve at all, tenant-wide — not a permissions gap). That reference was simply stale/wrong on whatever originally created Person's setting; Azure doesn't validate `workspaceId` on read, only on write. `az monitor log-analytics workspace show --subscription 85c76dea...` confirmed the real workspace (`customerId 76536d4a-5616-44ae-bee4-0aa6963b5d28`, matching what `cloud-graylog/CLAUDE.md` already documented). Corrected the local to `85c76dea...` and re-applied.
   - **Re-applied successfully:** "Apply complete! Resources: 0 added, 4 changed, 0 destroyed." **Independently re-verified** via `diagnostic-settings list`: all 4 apps show one object each, both `eventHub` and `workspaceId` populated correctly. **This regression is closed.**

## Volume spike after onboarding — Catalog identified as the source

Fleet-wide Graylog throughput jumped from ~15k to ~200k messages after this ticket's onboarding (user observation). Per the item-2 delivery check (15-min window, 72,485 total docs), **Catalog is the source: 62,809 of 72,485 messages (86.7% of all traffic)**, far above every other app including Business (812) and Orders (4,472), and far above Catalog's pre-ticket ranking (20.6% of fleet, second only to Business). **Broken down by category (15-min window `17:07:32`–`17:22:32Z`, 45,184 total): `AppServiceConsoleLogs` 44,904 vs `AppServiceHTTPLogs` 280 — a 160:1 ratio.** Confirms this is console log verbosity, not real traffic — Catalog received only ~280 actual HTTP requests in the window (~0.3/sec, unremarkable) but emitted ~45,000 console log lines in the same window (~50/sec), decoupled from request volume. Points to something like debug-level logging left enabled in production, or a background loop logging repeatedly, on the Catalog app itself — not a Graylog/Terraform/pipeline issue. Worth a separate follow-up with whoever owns Catalog's codebase/config to check its logging level; out of scope for this ticket to fix (this ticket's job was onboarding the log pipeline, not app-level logging hygiene), but worth flagging since it's now driving the large majority of fleet-wide Graylog ingestion volume and cost.

   **User requirement (2026-08-12): all 6 new streams must be visible to "Everyone" at "Viewer" level — DONE, verified.** `GET` isn't allowed on `/api/authz/shares/entities/{grn}` (405, only `POST`/`OPTIONS`) — the same endpoint doubles as both read and write via `POST`. Learned the grant shape from Sales's stream (`grn::::builtin-team:everyone` = Everyone, `view` = Viewer capability) and applied `{"selected_grantee_capabilities": {"grn::::builtin-team:everyone": "view"}}` to all 6 new streams, all HTTP 200.

   **Important API behavior discovered (worth remembering): this endpoint is not a safe read.** POSTing an empty `{}` body — assumed to be a harmless "just check current state" call — actually **replaced** the grant set with nothing, clearing the just-applied Catalog share. Confirmed by re-sending the full desired payload, which showed `active_shares` populated again immediately after. The correct way to "check" this endpoint is to always POST the full desired `selected_grantee_capabilities`, never an empty one — it's idempotent when the payload matches the target state, but destructive if it doesn't. Only Catalog was affected (the only one re-checked with `{}`); the other 5 were never re-touched after their original grant call. **Final confirmation pass (all 6, using the safe non-empty pattern): every stream shows exactly 1 active share (Everyone: Viewer).** This item is fully done.
