## Working hypotheses (unverified)
1. Write bursts (OpenSearch segment merges / bulk indexing / snapshot / `fstrim`) hit the disk's IOPS/throughput cap -> write await 63 ms. Supported by: the alert is write-side only (63 ms vs 2 ms) and lasted ~5 min after a 15 min window.
2. Azure-side throttling (disk or VM-level uncached IOPS/bandwidth cap) -> check `Disk IOPS Consumed Percentage` / `VM Uncached IOPS Consumed Percentage` metrics for the window.
3. Retention/index deletion or rotation job at ~08:00 (heavy delete + merge) — check Graylog rotation schedule and OpenSearch task list.
4. Zabbix item artifact: the trigger averages/uses `iostat`-style await; a single short burst can push a 15 min window — check item history granularity.

## Alternative (user's idea): isolate in a new disk
Candidate designs, to evaluate once the cause is known:
- Move only the hot write path (OpenSearch translog / Graylog journal `/var/lib/graylog-server/journal`) to a separate disk, keep indices on `nvme0n3`.
- New larger/faster data disk (Premium SSD v2 or higher-tier P30/P40) and migrate indices (rsync with OpenSearch stopped, or add as a second `path.data` — note OpenSearch 2.x multi-path data is deprecated/removed in later versions; verify).
- Do not decide before C1–C3: if the cause is the SKU cap, a disk resize/tier change is cheaper than a second disk; if the cause is a one-off job, no change is needed.
