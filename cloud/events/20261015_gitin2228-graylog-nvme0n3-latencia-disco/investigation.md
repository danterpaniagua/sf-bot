# Investigation — 20261015_gitin2228-graylog-nvme0n3-latencia-disco

**Status:** in progress (C1 VM, C2 Zabbix, C3 Azure and C4 VM done; cause not established). Findings: Azure shows no throttling (C3); the OpenSearch disk (P30, host caching ReadOnly) has high per-I/O latency regardless of load (write await 63-67 ms at 13-40 writes/s, 200 ms at idle in one sar sample), while the MongoDB disk of the same VM (P6, ReadWrite) has 1.5-12 ms; the 64 MB read-ahead has no known origin; the read-burst producer is not identified. Next: decide whether to test the host caching setting (state change, needs the user's decision and a window) or to capture a burst live.

## Trigger
- Zabbix alert, Operations: 08:33:01 PROBLEM → 08:38:04 RESOLVED (5m 3s), host "Cloud Graylog", trigger `nvme0n3: Disk read/write request responses are too high (read > 20 ms for 15m or write > 20 ms for 15m)`. Values shown in the alert: "2 ms, 63.0535 ms" (read, write — order and which one tripped the threshold are inferred from the trigger name, to be confirmed in C2). Time zone of the alert times not stated (assumed local -03:00).
- Jira ticket: GITIN-2228 (https://smartit-ar.atlassian.net/browse/GITIN-2228), "[OPE] Graylog: nvme0n3. Alta latencia".

## Confirmed facts (from earlier events, not re-verified today)
- `nvme0n3` is the OpenSearch data disk of the SmartCloud Graylog VM: partition `nvme0n3p1` (512G XFS) mounted on `/var/lib/opensearch`; the disk is 768G after the user added 256 GB (GITIN-2209, `cloud/events/20261009_gitin2209-graylog-poco-espacio-disco/investigation.md`). The mapping host = `smartfran-graylog-pro` is an inference from layout and sizes, not confirmed (same file).
- 2026-10-09: `/var/lib/opensearch` 89 % used (456G of 512G).
- Azure disk size/SKU/billing for the 768 GB size was not checked (GITIN-2209). Disk tier determines the IOPS/throughput cap (P20 ≈ 2300 IOPS / 150 MB/s; P30 ≈ 5000 IOPS / 200 MB/s — Azure documentation values from memory, to verify for the actual SKU).

## Working hypotheses (unverified)
1. Write bursts (OpenSearch segment merges / bulk indexing / snapshot / `fstrim`) hit the disk's IOPS/throughput cap -> write await 63 ms. Supported by: the alert is write-side only (63 ms vs 2 ms) and lasted ~5 min after a 15 min window.
2. Azure-side throttling (disk or VM-level uncached IOPS/bandwidth cap) -> check `Disk IOPS Consumed Percentage` / `VM Uncached IOPS Consumed Percentage` metrics for the window.
3. Retention/index deletion or rotation job at ~08:00 (heavy delete + merge) — check Graylog rotation schedule and OpenSearch task list.
4. Zabbix item artifact: the trigger averages/uses `iostat`-style await; a single short burst can push a 15 min window — check item history granularity.

## Alternative (user's idea): isolate in a new disk
Candidate designs, to evaluate once the cause is known:
- Move only the hot write path (OpenSearch translog / Graylog journal `/var/lib/graylog-server/journal`) to a separate disk, keep indices on `nvme0n3`.
- New larger/faster data disk (Premium SSD v2 or higher-tier P30/P40) and migrate indices (rsync with OpenSearch stopped, or add as a second `path.data` — note OpenSearch 2.x multi-path data is deprecated/removed in later versions; verify).
- Do not decide before C1–C3: if the cause is the SKU cap, a disk resize/tier change is cheaper than a second disk; if the cause is a one-off job, no change is needed.

- Not established: the cause. Candidates (none verified): per-I/O latency of the disk itself (tier, caching, throttling or a noisy neighbour), small synchronous writes (OpenSearch translog or Graylog journal fsync) at a low rate, background merges, or memory pressure. C1 (iostat per device, kernel errors, OpenSearch merges/tasks, fstrim timers) and C3 (disk SKU, size, IOPS and MB/s caps, `Disk IOPS Consumed Percentage`, VM-level caps) are the next reads.

## C4 result (2026-10-16, `scripts/scripts-c4.sh` on the VM; read 15:44 UTC; file `data/c4-vm-20261016T154408Z.txt`)
- **The first file, `data/c4-vm-20261016T154336Z.txt` (15:43 UTC), is from the wrong machine**: its hostname line says `sf-monitoreo` (the SmartPedidos/SmartLoyalty Graylog host, four NVMe devices, `read_ahead_kb` 128); it is not evidence for this ticket and was not used. The second file says `sfcloud-monitoreo`, the VM of this ticket.
- `read_ahead_kb` = **65,536 on all three NVMe devices of this VM** (OS disk `nvme0n1`, MongoDB `nvme0n2`, OpenSearch `nvme0n3`); the search of udev rules, tuned, systemd, `rc.local`, sysctl and `cron.d` found **no definition** (tuned is not installed), so where the value comes from is not known (it may be a default of this kernel/driver on this VM size; the other Graylog host has 128). Not shown to matter: no read bursts occurred during the sample.
- Per-process I/O in a 30 s `pidstat` sample (all quiet, reads about 0): OpenSearch (`opensearch`) writes about 1.5 MB/s on average (+ 0.75 MB/s of cancelled writes); Graylog about 90 kB/s; MongoDB about 28 kB/s; Logstash nothing. So the steady write load of the OpenSearch disk is about 1.5 MB/s, far from the provisioned 200 MB/s (consistent with C3).
- **Per-I/O latency, same VM, same moment (3 iostat samples of 5 s)**: `nvme0n3` (OpenSearch, P30, host caching `ReadOnly`) writes with **w_await 63-67 ms** at 13-40 writes/s (write sizes 30-100 kB, queue 0-15, %util 8-21 %) and reads with r_await **30-280 ms** at 13-76 reads/s; `nvme0n2` (MongoDB, P6, host caching `ReadWrite`; the mount-to-device mapping is in the C1 `lsblk`) at similar small rates shows w_await **1.5-12 ms** and r_await 0.3-0.5 ms. Both disks sit behind the same VM and the same limits.
- `sar -d` (host UTC, today 00:00-15:44, 10-minute averages, only periods with await above 100 ms): 01:50 (121 ms, 4.3 MB/s read and 4.8 MB/s write), 02:20 (119 ms, same load), **10:10 (200 ms with 132 kB/s written, 10 transfers/s)**, 12:10 (173 ms, 253 kB/s), 14:10 (131 ms). The 10:10 sample is write latency of 200 ms with almost no load and a queue of 2.
- OpenSearch merges (`_nodes/stats/indices/merge`): none running at the read; cumulative since the node started 16,119 merges, 4,475 s of merge time in total (about 75 minutes), 71 GB merged. Not a constant load and not shown to coincide with any episode (no timestamps). Largest indices `business__13` to `__19` (18-37 GB, one with 61 segments, the rest 2).
- Reading: the disk of this ticket answers each request slowly (tens of milliseconds for writes, up to hundreds for reads) **regardless of load** (idle samples, 200 ms at 10 transfers/s), while the other disk of the VM does not. The differences between the two disks are tier (P30 vs P6), host caching (`ReadOnly` vs `ReadWrite`), size and usage (768 GB at 79 % vs 64 GB at 16 %) and workload; which one matters was not tested. Host caching `ReadOnly` on a write-heavy disk is the first candidate (the Azure guidance that write-heavy disks should use `None`, and the effect of changing it, are not verified: check the documentation first). The read bursts of C1/C3 (up to about 400 reads/s with queues up to 2,270) are real but their producer was not seen: nothing was reading during this sample.
- Not established: the cause of either pattern. A change of the host caching setting would be a state change on production (the disk is detached and attached again to apply it by Azure's documentation as I recall it, which interrupts the data path; not verified) and is not proposed before the decision of the user.
