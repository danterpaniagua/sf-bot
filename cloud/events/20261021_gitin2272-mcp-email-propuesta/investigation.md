## User postulates, validated
1. **"Claude session limit" — confirmed.** Anthropic's Help Center: Pro and Max have a five-hour session limit and a weekly limit, shared across Claude and Claude Code. `claude -p` (headless) also draws from the subscription limits per the Help Center page "Use the Claude Agent SDK with your Claude plan": a change that would have moved it to a separate credit was announced for 2026-06-15 and is now marked "paused", with no end date and not described as cancelled, so it can come back. The monthly API credits that page mentions (October 7 update) are for Max and Team; none stated for Pro.
2. **"Per-chat ingest cost" — confirmed as a problem of scale; read here as the volume of log data a Claude session would have to take in (user pointed to GITIN-2228/2209 for the ingest figures; "ingest" meaning not otherwise stated).** On a Pro subscription there is no per-token charge: the cost is consumption of the 5-hour/weekly limit, which is token-driven (third-party sources say large tool output uses a large share; no source found on how MCP output is counted); with `ANTHROPIC_API_KEY` set, Claude Code bills at API rates (Help Center). Figures from the SmartCloud Graylog (GITIN-2209 / GITIN-2228, read-only API/VM checks, not re-run today):
   - Stored: 583 GB on 2026-10-21 (571 GB, 113.5M documents on 2026-10-14); the 8 business applications hold 78,991,098 documents / 445.8 GB; Business + Orders are 60 %.
   - Rate: 37-52 GB/day on 8-12 Oct (estimate from index size, not raw ingest), 9-12 GB/day on 1-6 Oct; the 24 h count by `name:` was 2,738,074 messages for the 8 services but undercounts (Business: ~355k by `name` against 37.5M documents in its set; unresolved, C14 would give the daily rate). From documents / retention (30-40 days) my arithmetic gives about 2 to 2.6 million documents per day (not measured).
   - Composition: `Information` is about 96 % of application documents (67.3M of 79.0M); in the 24 h count `Warning`+`Error`+`Fatal` are 2.6 % (69,867) and `Unknown` (HTTP access records) 36.5 %.
   - Size per message: two figures that do not agree: 350 bytes per event (June sizing, cloud-graylog) and about 5 KB per document stored (my division of 571 GB by 113.5M; includes index overhead and all promoted fields, so it is not the size of a returned message). Neither is the size of a message as returned by the API or the MCP, which was not measured.
   - Order of magnitude (my estimate, assuming roughly 4 characters per token): at 350 bytes a message is about 90 tokens, at 5 KB about 1,250 tokens, so 100 raw messages are somewhere between ~9k and ~125k tokens, and one day of logs (about 2 million messages) cannot be read by a session in either case (hundreds of millions of tokens). Even the `Warning`+ messages of one day (about 70k by the undercounting count) are too many to read raw. Conclusion for the proposal: the AI never reads raw messages; it has to get aggregates (counts per stream/level/error signature, deltas against the previous period) and a few examples. The real tokens per query have to be measured with the actual MCP or REST output.
3. **"Logs not AI-friendly" — not verifiable on the web; supported by this repo's own records, not re-checked today.** `cloud/CLAUDE.md` records: the `-http` index sets hold Azure HTTP access records with a constant 18-character `message` (keyword search proves nothing there); numeric GELF `Level` is `6` on almost everything (use `AppLevel`, which has a real `Unknown` value); a `Service:<X>` field-filtered query never confirmed to return results (GITIN-2068); field promotion gaps are tracked in `cloud/docs/graylog-log-fields.md`. Volume: Business about 355k messages/day by `name`. What "AI-friendly" requires (compact, structured, aggregated output) is a proposal input, not a finding.
4. **"Graylog MCP in early test stage" — confirmed for the official one.** The Graylog docs page labels MCP "an experimental feature" (behaviour, tools and responses may change without notice), says Graylog does not fully support MCP issues, and says to use it only in controlled, non-production environments; the 7.2 betas still fix MCP bugs (tool-argument validation; output schemas that made schema-validating clients reject `search_messages`, `aggregate_messages` and `list_fields` responses). Graylog's blog, by contrast, presents it without that label. SmartCloud is already on >= 7.0, so the version is not a blocker (if 7.1.3 is right).

## Implications of $20 accounts (analysis, not measured)
- An interactive MCP session spends the same pool as the person's normal Claude use; a search returning many raw messages can consume a large part of a session. Aggregations and narrow queries (streams, fields, short ranges) are cheaper in tokens than raw message retrieval.
- A scheduled `claude -p` report competes with that person's interactive use for the same limits, and a Pro account is per person (not pooled). Anthropic's page recommends API-key billing for shared production automation (stated there for Team/Enterprise).
- A February 2026 blog claims subscription OAuth tokens may not be used outside official tools; not verified against Anthropic's terms. `claude -p` is the official CLI, but whether unattended cron use on a personal Pro account is acceptable was not confirmed: check before proposing it.
- Possible design to evaluate (proposal, not tested): a script queries the Graylog REST API without any LLM (counts, top errors per stream, deltas), and `claude -p` only reads that small digest to write the report; this keeps tokens low and does not depend on the experimental MCP.

## Option (user, 2026-10-21): feed the AI only levels above INFO, after GITIN-2228 is applied
- Idea: restrict every AI query to `AppLevel` in (`Warning`, `Error`, `Fatal`) (the level field to use is `AppLevel`; the numeric GELF `Level` is `6` on almost everything). Combined with the GITIN-2228 retention (options A/B: `Information` kept 7 days, `Warning` and above 30 days), the data the AI works on is the small part of the store that is kept longest.
- Status of the dependency: GITIN-2228 retention is **not applied** (options A and B pending the PM's answer; only the search limits of 60 s and 15 days were applied). The option does not need the retention change to work: the filter is a query, so it can be used now; the retention only changes what is still there at day 8 and later.
- Size, from the 2228 data (not re-run): `Warning`+`Error`+`Fatal` are 2.6 % (69,867) of the 24 h count of 2,738,074 messages (count by `name:`, which undercounts), against `Information` 60.9 % and `Unknown` (HTTP records, in the `-http` sets) 36.5 %. In the stored documents of the 8 services, 11.7M of 79.0M are not `Information` (my subtraction of C16 totals: 78,991,098 - 67,336,115); what those 11.7M are besides Warning/Error/Fatal was not looked at. By my estimate (tokens as above) 70k messages a day is still about 6M-87M tokens raw: it cuts the volume by about 97 %, but the AI still needs grouping (counts per error signature, new signatures against yesterday, a few examples), which is cheap with `aggregate_messages` or the REST aggregation.

- **C21 result (2026-10-21, run by the user from 16:28Z; script `scripts/top-patterns-warning.sh`, file `data/c21-top-patterns.tsv`; no `ERR`).** Top patterns of `Warning`/`Error`/`Fatal` in Platform, Person and Pos, last 24 h. Together that is about 65.9k messages, about 88 % of the 75,004 `Warning`+ messages of C15 (my arithmetic, assuming the sample represents the day; a pattern below about 0.3 % would not show in a sample of this size). The code behind it is described in the next bullet.
  - **Code check (2026-10-21, `cloud/repo/SmartFran.Cloud`; first read with local `main` at `d969856fa`, 2026-09-30, then re-read after `git fetch` and `git pull --ff-only origin main`, now `main` at `e00e8c467`, 2026-10-14, equal to `origin/main`; `main` is the production branch of the cloud repo (user-stated, 2026-10-21), so this is the code read for the PROD question, with the deployed build itself not checked; the Platform and Person middleware files are identical in `origin/dev` `5fa19aaa9`, 2026-10-20; the warning logic below is unchanged by the pull):** `RequestHandlingMiddleware.cs` exists in Platform, Person, Orders, Catalog, Sales, Business and two Function Apps, with the same text. In `InvokeAsync` it reads `_config["LogOriginalRequest"]`; if the setting is `True`, it logs the body, sanitized headers and query string at `Information` for PUT, POST and DELETE requests only; **otherwise (setting missing, or `False`) it logs the `Warning` "The setting: \"LogOriginalRequest\" is missing or is set to \"False\". Request info about the PUT, POST and DELETE actions is not being logged."** The `else` branch is outside the method check, so the warning is written **on every request of any method**, not only on PUT/POST/DELETE. Inference, not measured: the 58,986 and 6,922 warnings a day are then about the daily request counts of those two APIs.
  - **Settings in the repo** (read as key and value only): the DEV and TEST settings files of Platform do not define `LogOriginalRequest` at all; Person has `True` in DEV and `False` in TEST; Sales and Catalog have `True`; Business has `False` in DEV and TEST. No PROD settings file is in the repo, so the PROD values were read from Azure (C22, below).
  - **C22 result (2026-10-21, run by the user at 18:01Z; script `scripts/logoriginalrequest-prod.sh`, file `data/c22-logoriginalrequest-prod.tsv`; subscription SmartIT Cloud, RG `SmartFran.Cloud.PRO`; only the `LogOriginalRequest` key was kept):** `SmartFran-Cloud-Platform-PRO` = `False`, `SmartFran-Cloud-Person-PRO` = `False`; Business, Catalog, Sales and Orders = `True`. This matches the C15/C21 data: the two apps with `False` produce the warning on every request (58,986 and 6,922 a day), the four with `True` do not (Orders 0 `Warning`, Sales 39, Catalog 32). Assumption for the deployed code: `main` has GitHub Actions deploying it, so `main` @ `e00e8c467` is taken as the deployed build (user-stated, the deployed version was not checked in Azure). The remaining question is only whether the `False` is intentional (for example to avoid logging request bodies); that was not asked.
  - **Possible fixes (proposals, none decided or tested; the decision is the dev team's):** (a) set `LogOriginalRequest` to `True` in PROD for Platform and Person: it removes the warning but starts logging every PUT/POST/DELETE body at `Information` (more volume). In Platform the code sanitizes headers only, not the body; in Person the body goes through `SanitizeRequestBody` (added in commit `7ee776ee2`, 2026-06-08, "protect PII in request logs"; what it masks was not read). Correction: an earlier version of this line said the body is unsanitized for Person too; I had read only the Platform file; (b) change the code so the missing-setting warning is written once at startup, or at `Debug`; (c) drop that message in a Graylog or Logstash pipeline rule. For the AI proposal the cheapest immediate step is to exclude it in the query (`NOT message:"LogOriginalRequest"`), which needs no change to the applications (not tested against the nested-JSON `message`).
  - **The message field holds a nested JSON event** in these two streams: that is a concrete case of "logs not AI-friendly" (level and template are inside the text, not only in fields).
  - **Without those two streams** `Warning`+ is 9,052 messages a day (C15: 75,004 - 59,023 - 6,929); by my token estimate that is still 0.8M to 11M tokens raw, so grouping is still needed, but the volume is about one eighth.
  - **Pos (5,916 in 24 h):** the top 15 patterns cover about 92 % of its sample (704 of 762). Largest: "Failed to send business log" with `UnprocessableEntity` / "Log validation failed" (`Phases[N].Steps`) 30.7 %; "showBusinessMessage: message is not ErrorApiException JSON" 18.4 %; `MainApp.ProcessException (BusinessException)` with user-facing business messages (member not found, card not activated, card number must be read with the scanner) about 15 % together; client-side failures (`Failed to fetch` on heartbeat and favourites, `unhandledrejection` for the service worker and the JSPrintManager client) about 17 %; HTTP "responded N" lines logged at warning/error level 8.9 % and 1.4 %. Some of these are business or client conditions, not server faults; classifying them was not done.
- The 15-day search range limit of GITIN-2228 does not matter for this option (user, 2026-10-21): the AI is not meant to read 15 days of logs; its queries cover short windows (the proposal's reports and sessions work on recent periods), so that limit was removed from the list below.
- Limits to check before proposing it: (a) context is lost, because the `Information` lines around an error are not seen (and after retention B they are gone after 7 days); (b) errors that the applications log as `Information`, if any, would be invisible: not checked; (c) the `Warning`+ volume is concentrated: Platform, Person and Pos hold 95.8 % of it (C15), so a report on "everything above INFO" would be mostly about those three; (d) C15 is a single day: the daily variation of `Warning`+ was not measured.
