# Investigation — 20260825_wholesale-service-infra-proposal

**Jira:** GITIN-1938
**Status:** in progress

## Context

A new service for a wholesaler client is being planned, launched from SmartFran Cloud, possibly with new business rules distinct from retail (POS/Admin). An architecture proposal (DeepL-translated, author unknown) was shared for review, describing risk of coupling the new service to current retail infrastructure and a two-phase decoupling plan.

## Confirmed facts

- Retail App Services are already split into 8 separately-deployed services, each on its own Server Farm/App Service Plan (`SmartFran-Cloud-{Pos,Admin,Business,Sales,Orders,Platform,Person,Catalog}-PRO`), per `cloud/docs/infrastructure.md`. Retail is not one monolith.
- **Corrected 2026-08-25:** WAF and Azure APIM are **not** pre-existing shared retail infrastructure — this was a wrong assumption carried from an early read of the proposal doc, and `cloud/docs/infrastructure.md` never actually lists a WAF or APIM component (its "Core Shared Services" table has neither). Confirmed by re-reading the proposal text itself: Phase Two is explicitly what "connects WAF to the entire cloud infrastructure" — meaning WAF/APIM are **net-new infrastructure this proposal introduces**, not something retail already sits behind. Today (Stage 0), retail is reached directly via its per-tenant hostnames bound straight to the App Service (the SNI pattern already documented), no WAF/APIM in the path at all — same as the wholesale dev endpoints (see Stage 0 note below).
- Multi-tenant resolution for existing retail tenants runs through a single App Configuration key (`organizations`) and `TenantHandlingMiddleware`, with per-tenant SQL/CosmosDB provisioned per the existing franchise pattern.
- User has confirmed the new wholesale service **will share current infrastructure** — exact endpoints/services involved are not yet known, and per user this doesn't change the core risk assessment (shared infra risk holds regardless of how many/which services are involved).
- Confirmed 2026-08-25: the new wholesale AppService (Phase 1/Phase 2 target) will be provisioned on a **new, dedicated App Service Plan** — not shared compute with an existing retail plan. Resolves the App Service Plan open question below.
- Confirmed 2026-08-25: the new wholesale apps will use their **own dedicated Auth0 application**, not shared with SmartFran Cloud's existing Auth0 tenant/Organizations setup used by retail. Identity-layer coupling is not a risk here — partially resolves the tenant-resolution open question (auth side); data-layer isolation (DB/CosmosDB) is still open.

## Current working theory

**Stage 0 (confirmed 2026-08-25, current/active — precedes Phase 1):** developers are already implementing the new wholesale APIs directly inside the current, shared App Service Plan — not merely "will share infrastructure" as a Phase 1 design choice, but active development happening now in the same deployment unit as retail. The proposal's Phase 1 (new client routed through WAF→APIM→current AppServices) implies a routing layer that doesn't exist yet at Stage 0 — Stage 0 is more coupled than the proposal's own Phase 1, since there isn't even separate APIM onboarding for the wholesale client yet, just shared code/deploy.

**Corrected 2026-08-25:** at Stage 0 there is currently **no WAF and no APIM at all, for retail or wholesale** — both are reached directly, not just the wholesale dev endpoints as first assumed. This is a security exposure on top of the deployment-coupling risk already noted (H1) — worth stating explicitly since it's a distinct risk category, not just "the same risk, earlier." It also means the proposal's Phase 1/Phase 2 WAF+APIM aren't isolating anything pre-existing — they're introducing gateway infrastructure for the first time, initially scoped to the wholesale client only (Phase 1: "the new client accesses the service behind WAF↔APIM↔current AppServices" — retail isn't mentioned as moving onto this path), and only in Phase 2 does WAF explicitly get "connected to the entire cloud infrastructure" (i.e., retail joins WAF's scope for the first time then, per the proposal's own wording). APIM, per the proposal, stays reconfigured to point only at the new dedicated wholesale App Service in Phase 2 — it's never described as fronting retail at any point.

**Reframes H4 entirely:** the real open question isn't "does WAF/APIM stay shared" (there was nothing pre-existing to share) — it's **whether WAF should extend to cover retail in Phase 2 as literally proposed** (introducing a new, first-time coupling point between retail and wholesale ingress security, in exchange for retail finally getting WAF protection it doesn't have today) **or stay wholesale-exclusive indefinitely** (no new coupling, but retail's lack of WAF protection remains unaddressed — a separate, likely out-of-scope-for-this-ticket security gap worth flagging on its own). APIM is not part of this trade-off either way — the proposal already keeps it wholesale-only.

The proposal's core diagnosis is sound: coupling new wholesale endpoints to shared retail infrastructure risks a wholesale deploy bug triggering a rollback that impacts retail. The proposed two-phase plan (Phase 1: new client routed through new WAF→APIM→current AppServices, wholesale-exclusive; Phase 2: dedicated App Service, APIM reconfigured, WAF extended to "the entire cloud infrastructure") is directionally correct on compute isolation but incomplete, and now understated given Stage 0:

- **Phase 1 mitigates nothing on the compute-coupling risk (H3), and Stage 0 already carries the full risk today** — Phase 1 only stands up a new wholesale-exclusive WAF+APIM path; the AppService it forwards to is still the same shared App Service Plan retail uses. Full compute-coupling risk persists for however long Phase 1 lasts, and is already live at Stage 0 with real developers committing to the shared App Service Plan. No exit trigger/date is specified in the proposal for either Stage 0 → Phase 1 or Phase 1 → Phase 2.
- **WAF/APIM were never pre-existing shared infrastructure — see the correction above.** The live question isn't "are they shared," it's whether Phase 2's WAF extension to "the entire cloud infrastructure" (bringing retail onto the same WAF as wholesale for the first time) is the right call, addressed under H4 below.
- **CI/CD pipeline separation was missing from the original proposal** — added to Phase 2 per user request 2026-08-25: the new service must build/release through its own pipeline, independent from retail's, so a wholesale deploy failure can't block/roll back a retail release and vice versa.
- Data-layer isolation (shared vs. dedicated DB/CosmosDB for the wholesaler) is a confirmed deferral, not addressed by the original proposal — see the shared-database finding under Open questions below.
- Original proposal's architecture diagrams read top-down as `New Service → APIM → WAF`, reversed from actual request flow (client → WAF → APIM → backend) — likely a translation/formatting artifact, not a design intent.

Three Mermaid diagrams (Current / Fase 1 / Fase 2) were produced in Spanish reflecting this understanding — see `ops.md` once drafted, or regenerate from this file's working theory if needed.

## Ruled out

- Scoping the review down to "which specific App Service(s) will host the new endpoints" as a blocking question — user confirmed this doesn't change the risk (shared-infra coupling risk holds whether it's 1 service or 10).

## Open questions / next steps

- Confirmed 2026-08-25: in a first instance, persistence for the wholesale service will be handled as-is — no dedicated DB/CosmosDB, reuses the existing shared data layer without change. This is the **shared-database anti-pattern** (a "distributed monolith" at the data layer, per user's framing): compute (App Service Plan, H7) and identity (Auth0) are genuinely decoupled, but a single shared database reintroduces the same coupling isolation at those layers was meant to remove — schema coupling between wholesale/retail migrations, capacity contention (DTU/vCore or RU/s), lock/corruption blast radius, and coupled backup/PITR. No code-level rollback undoes a data-layer incident. Elevated to Alto risk in `ops.md` (H6) given this reasoning — deliberate deferral, not a resolution, and worth monitoring once wholesale traffic volume becomes significant.
- Exit criteria/target date for Stage 0 → Phase 1, and Phase 1 → Phase 2 — currently unstated in the proposal.
- Whether Stage 0 development is happening on a separate branch/deploy slot within the current App Service, or directly against the same deployment path retail already ships through — determines how immediate the rollback-coupling risk actually is right now.
- **Corrected 2026-08-25** — H4 options reframed now that WAF/APIM are known to be net-new, not pre-existing shared infra. APIM, per the proposal itself, is already wholesale-exclusive (never fronts retail) — that's not actually a live trade-off. The real open question is WAF's scope:
  - **A — Proposal as literally written**: dedicated APIM (wholesale-only) + WAF extended to "the entire cloud infrastructure" in Phase 2, i.e. WAF becomes the first shared component between retail and wholesale ingress. Gives retail WAF protection it doesn't have today, at the cost of a new shared/coupled component. Cost of the APIM instance not yet estimated.
  - **B — DNS direct (no APIM) + WAF still extended to retail**: removes the APIM cost/complexity, keeps the same WAF-becomes-shared trade-off as Option A. Loses gateway-level rate limiting/quota, subscription-key governance, facade/versioning abstraction (same losses as previously described for "Option B"), but WAF rate-limit custom rules (product/tier unconfirmed — Application Gateway WAF_v2 vs Front Door Premium — see `cloud/docs/infrastructure.md`, which lists neither) still give retail and wholesale some IP/geo-based volumetric protection.
  - **C — Wholesale-exclusive WAF, never extended to retail**: no new coupling introduced at all — full isolation from retail's ingress at every layer. Retail's current lack of WAF protection remains unaddressed (separate, likely out-of-scope security gap for this ticket). Whether APIM is included (dedicated) or skipped (DNS-direct) is independent of this choice.
  - Confirmed 2026-08-25: whichever option includes WAF/APIM, the cost estimate must cover **two full sets, not one** — PROD and non-prod (per `cloud/docs/infrastructure.md`, non-prod App Services already live in a separate subscription, DEV/DEV2/STG/TEST/POC) — needed to test WAF/APIM config changes before applying them to PROD, same as already done for App Services.
