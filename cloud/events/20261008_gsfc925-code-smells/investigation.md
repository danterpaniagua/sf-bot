## What the change does

A PIN (4 digits, unique per franchisee) identifies the approver for discounts/surcharges that require authorization. The POS calls `Authorize`, which resolves the franchisee of the local, checks the rule requires approval, checks a failure lock, finds the approver by comparing the PIN against every PIN hash of that franchisee, and stores a 5-minute single-use "grant" in the shared Redis; `Consume` redeems it. The PIN hash is ASP.NET Identity's `PasswordHasher` (PBKDF2, per-record salt). Lockout counters live in Redis keyed by tenant, franchisee and sale-point code.

## Findings (risks)

1. Success resets the lockout counters. `AuthorizationAttemptLimiter.RegisterSuccessAsync` (L93-97) removes both the sale-point and franchisee counters, and `DiscountSurchargeAuthorizationService.AuthorizeAsync` calls it on every match. Anyone who holds one valid PIN and can reach `Authorize` can alternate four wrong guesses with one valid PIN and never reach the 5 / 15 thresholds, which removes the bound the class comment relies on ("what makes the mechanism safe"). Impact: guessing another approver's PIN so that approvals are attributed to them. Confirmed by reading the code; whether it matters depends on the threat model (an insider who is already an approver or knows one PIN).
2. Counter increments are read-then-write (`IncrementAsync` L122-130) and the lock check runs before the comparison. A burst of concurrent requests that all read the same count are all admitted, so the effective bound is "number of concurrent requests per counter step", not "one extra attempt" as the comment at L104-121 says. Plausible, not tested.
3. The failure counter key uses `cmd.SalePointCode`, a value in the request body, and `FranchiseId` also comes from the body (`AuthorizeAsync` step 1). The controller (`DiscountSurchargeAuthorizationController`) is `[Authorize]` only and has unused `using System.Security.Claims;` and `using SmartFran.Cloud.Provider.Authorization;`, which suggests a caller-to-franchise check was planned and not written. If nothing else in the pipeline ties the caller to that franchise and sale point, an authenticated user can vary `SalePointCode` to avoid the per-POS counter (leaving only the 15-per-franchisee counter), target another franchisee's approvers, and lock all approvals of a franchisee for 15 minutes by sending 15 wrong PINs. Plausible; the tenant/franchise scoping outside these files was not checked.
4. `ConsumeGrantAsync` reads the grant and then removes it (non-atomic): two concurrent `Consume` calls with the same grant id can both succeed, so "single use" is not guaranteed. A mismatching call also burns the grant before `Covers` is evaluated. Plausible.
5. `FindApproverByPinAsync` (L105-129) runs one PBKDF2 verification per approver of the franchisee for every attempt and for every PIN change (`EnsurePinIsFreeInFranchiseeAsync`, L148-171); latency grows with the number of approvers in a franchisee. The PIN-set endpoint is admin-gated (`ResolvePinTargetAsync`); its exact rules were not read.

## Code smells

- Comment density: 21% to 57% of lines in the new service files (limiter 47%, hasher 57%, grant 54%, authorization service 26%, PIN service 21%) against about 11% in `FranchiseeService.cs` / `FranchiseService.cs` on `origin/dev`. The comments carry a decision log with spec item ids ("A3", "A4", "A10", "13.4 del spec funcional"), dates and roles ("decision del Tech Lead", "2026-10-05"); that belongs in the spec or an ADR and will go stale in the code.
- `DiscountSurchargeAuthorizationService` has 8 constructor dependencies and mixes rule resolution, PIN lookup, lock handling and grant storage in the cache.
- `AuthorizationPinService` takes `IAuthorizationPinNotifier? notifier = null`: if the notifier is not registered, PIN-change emails are silently skipped.
- `AuthorizationPinHasher.Verify` catches `Exception` (justified in its comment, but it swallows everything); `PasswordHasher<AuthorizationPinHasher>` passes the hasher itself as the type parameter.
- Unused usings in the controller (see finding 3).
- Commit hygiene: 8174d7344 is 99 files / 7,294 insertions ("Facturacion + ajustes del ladol del admin", mixing billing, admin UI, domain, openspec docs); Obsidian `workspace.json` and pasted images were committed and then removed in 5155a38da ("Eliminar archivos inesesarios", 4,667 deletions); messages such as "Ajustes PIN" / "Ajustes en el pin" carry no information.

## What is good (for balance)

PBKDF2 with per-record salt through the framework hasher instead of a custom one; PINs are never logged and rejections are uniform; tenant id is in every Redis key; server-side re-check that the rule requires approval before issuing a grant; grants are bound to rule, value, sale point and (for fixed amounts) sale total; a substantial unit-test set exists for the new classes.
