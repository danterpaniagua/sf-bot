## Findings from source (`repo/SmartFran.Cloud/`, `origin/dev`, fetched 2026-09-22)

### 1. Health-check infrastructure — a route already exists, but it's a no-op

**Correction to this investigation's own earlier read**: a health endpoint *does* already exist — `Source/Services/Sales/SmartFran.Cloud.Sales.API/Controllers/v1/StatusController.cs:25-31`, route `GET api/v1/Status/Health` (`[HttpGet("Health", Name = "Health")]` on a controller routed `api/v1/[controller]`), `[Authorize]` already commented out (anonymous today). It does nothing: `return Ok("Its alive!")` — no dependency or resource checks, can't distinguish "fine" from "about to OOM." Same `StatusController` shape (`Health`/`Status`, plus `SimulateCpuLoad`/`SimulateMemoryLoad` actions seen in other services' specs) is a shared convention across at least Business/Catalog/Person/Platform (`Source/Services/Sales/SmartFran.Cloud.Sales.Application/Specs/*.json`, cached OpenAPI specs of those services) — **this design should extend the existing `api/v1/Status/Health` route, not invent a new `/api/health` path.** (Note: the file's `namespace SmartFran.Cloud.Catalog.API.Controllers.v1` doesn't match where it actually lives, `Sales.API` — looks like a copy-paste artifact from scaffolding this controller across services; cosmetic, not a functional issue, flagged for whoever touches this file next.)

- No `Microsoft.Extensions.Diagnostics.HealthChecks` usage anywhere (`grep` across `Source/`) — the existing endpoint is hand-rolled, not built on the framework's health-check middleware.
- No `AspNetCore.HealthChecks.*` community packages referenced in any `.csproj`.
- `TenantHandlingMiddleware.cs` (Sales.API and others) has `if (path.StartsWith("/api/") && !path.Contains("/health"))` — already correctly bypasses `api/v1/Status/Health` (lowercased path contains `/health`) from tenant resolution. Same pattern duplicated in `SmartFran.Cloud.Functions.Sales.TicketProcessAsync/Extensions/TenantHandling.cs` and `SmartFran.Cloud.Functions.Business.CodeGenerator.LiteEdition/Extensions/TenantHandling.cs`.
- Confirmed precedent for the exact CPU/RAM/DB/Redis pattern this ticket wants, elsewhere in the org: SmartLoyalty's `healthcheck.ashx` (`loyalty/events/20260916_gitin2058_wsv2_lb_healthcheck/`, `.../20260916_gitin1228_lb_healthcheck/`) checks CPU/Memory (`PerformanceCounter`) and DB/Redis connectivity, returns `200/400/500` with a JSON body. Not directly portable (`.ashx`/`IHttpHandler` is ASP.NET Framework, `System.Web` — Sales.API is ASP.NET Core, no `.ashx` support), but confirms this is an established pattern, not a novel design.
- Found via the sibling investigation `cloud/events/20260913_pos-net-http-timeout/investigation.md` (2026-09-19 exploration), which reached this exact same conclusion independently (different ticket, "remediation-direction exploration" section) — cross-check, not duplicated derivation.

### 2. Sales.API pipeline order matters for where a health endpoint can sit

`Program.cs` (Sales.API), pipeline order: `UseCors` → `UseSmartFranLogEnrichment` → `UseExceptionHandler` → `UseRequestHandlingMiddleware`/`UseExceptionHandlingMiddleware` → `UseSwagger[UI]` → Hub mappings → `UseHttpsRedirection` → `UseAuthentication` → `UseAuthorization` → `UseUserIdEnricher` → `UseTenantHandlingMiddleware` → `UseAzureAppConfiguration` → `MapControllers`.

A health endpoint mapped as a normal `[ApiController]` route would hit `UseAuthentication`/`UseAuthorization` — LB/Zabbix probes won't carry an Auth0 JWT. **Must be explicitly `[AllowAnonymous]`** (or mapped via `app.MapHealthChecks(...)` with `RequireAuthorization()` never called) to work at all. This is a correctness requirement, not a nice-to-have — an unauthenticated health probe will otherwise get a 401, indistinguishable from a real outage to whoever's polling it.

### 3. CosmosDB — genuinely per-tenant, no single "the Cosmos connection" to check

Confirmed via `docs/infrastructure.md` (Tenant resolution mechanism section) and `CosmosClientPool.cs`:
- Each onboarded franchise has its **own dedicated CosmosDB account** (`smartfran-cloud-cosmos-<tenantId>`), separate from the shared platform account (`smartfran-cloud-cosmos-platform-pro`).
- `CosmosClientPool` (`Source/Services/Sales/SmartFran.Cloud.Sales.Infrastructure/Repositories/Domain/CosmosSDK/CosmosClientPool.cs`) lazily creates and caches one `CosmosClient` per `tenantId` in a `ConcurrentDictionary`, resolved from `ITenantProvider` — which itself is only populated per-request, via `TenantHandlingMiddleware`, from the caller's JWT `org_id` claim or a `TenantId` header. **There is no tenant context outside an actual API request.** A health-check endpoint invoked by an infra prober (no JWT, no `TenantId` header) has no tenant to resolve — it cannot naturally call `CosmosClientPool.GetOrCreateClient(tenantProvider)` the way normal request handlers do.
- **Design decision (2026-09-22): loop all onboarded tenants, one response per tenant** — option (b) below, chosen over the cheaper single-reference-tenant option because it's the only one that actually delivers per-franchise SLA visibility, which is the ticket's stated goal. Trade-off accepted: N Cosmos round-trips per health-check call (currently 4 tenants: GRIDO, WEISS, `lodejacinto`, `ultracai`), mitigated by running them in parallel (`Task.WhenAll`) rather than serially. A single tenant's Cosmos outage now reports as `Degraded` at the aggregate level, not `Unhealthy` — the load balancer shouldn't fail Sales.API entirely over one franchise's dependency being down. Full code sketch in `ops.md` §3. Communicated to Dev via `email_dev.md`, pending their confirmation before implementation starts (also need to confirm `ITenantConfigurationResolver` already exposes a "list all tenants" method, or whether one needs to be added).
  - Options considered: (a) a fixed reference/canary tenant (e.g. GRIDO) — cheaper, single client, but only proves that one account is reachable, rejected as insufficient for SLA measurement. (c) the shared platform Cosmos account (`smartfran-cloud-cosmos-platform-pro`) — doesn't apply, Sales has no client for it (`CosmosClientPool`/`SaleContext` only expose per-tenant settings).
- The actual check itself, once a target client is chosen, should be `CosmosClient.ReadAccountAsync()` — an account-level metadata call, no RU cost against any container/database, cheap and low-latency. Confirmed available on the SDK version already referenced (`Microsoft.Azure.Cosmos`, used throughout `CosmosClientPool`/`SaleContext`).

### 5. CPU/RAM — self-reported from within the process

No existing pattern in this codebase for this (Application Insights captures some of this passively, but that's a pull-based external view, not something the app itself exposes via HTTP). Options:
- `System.Diagnostics.Process.GetCurrentProcess().WorkingSet64` for RAM (straightforward, matches what Azure App Service itself reports per-instance).
- CPU is harder to get as an instant percentage — `Process.TotalProcessorTime` is a cumulative counter, not a rate; computing a real "CPU %" needs two samples separated by a time window (e.g. a short `Task.Delay` inside the check, adding latency to every call) or a background sampler that updates a shared gauge the health check just reads (no added per-call latency, but needs a small hosted background service). **Recommend the background-sampler approach** — cheap to add, avoids making every health-check call artificially slower, and is the more standard pattern for this exact problem in .NET.

## Graceful shutdown per instance (added 2026-09-22, tied to this ticket)

User flagged this as a related issue to fold into the same design. It genuinely ties into the health endpoint, not just topically adjacent: **the health endpoint is the mechanism the load balancer uses to know an instance is draining**, so shutdown handling and the healthcheck design are two ends of the same lever.

**Real evidence this isn't hypothetical** — `cloud/events/20260913_pos-net-http-timeout/investigation.md` (confirmed, not this session's finding, cross-referenced): Sales-PRO's Windows Event Log shows clean shutdowns (Event ID 1033) through 2026-09-12 daytime, then **Event ID 1005 ("Failed to gracefully shutdown application ... Process Id: N") starts appearing 2026-09-12T23:15:26Z** — a forced kill after the graceful-shutdown grace period expired, i.e. the worker was still doing something (or hung) when the timer ran out, not just a clean scheduled recycle. Frequency escalated through 2026-09-13 (recycles every 10-90 min for most of the day). That investigation's own scope was OOM/timeout diagnosis, not shutdown-code remediation — it flagged the mechanism but didn't propose a fix. This ticket now does.

**Confirmed mechanism** (same source investigation, verified against ASP.NET Core/ANCM docs at the time): on a **planned stop** (deploy, Autoscale scale-in, manual restart — as opposed to a crash), IIS ANCM (AspNetCore Module V2) signals the app, `IHostApplicationLifetime.ApplicationStopping` fires, and the app gets a fixed `shutdownTimeLimit` (**default 10 seconds** for in-process hosting, which is what Sales.API uses) to drain in-flight requests and close connections before ANCM force-kills it. **OOM crashes bypass this entirely** — the process is already failing, there's no working runtime left to run drain logic in, `ApplicationStopping` never fires. Shutdown code only helps the *planned-stop* path (deploys, scale-in, restarts) — it cannot and does not address GITIN-2075's OOM crash-loop, a separate, already-tracked issue.

**Existing precedent in this codebase**: `Source/Common/Functions/SmartFran.Cloud.Pos.Wasm.Relay/Program.cs:102-106` already registers a shutdown hook —

```csharp
var lifetime = host.Services.GetRequiredService<IHostApplicationLifetime>();
lifetime.ApplicationStopping.Register(() =>
{
    Log.CloseAndFlush();
});
```

— for flushing the Serilog logger cleanly before exit. Real, working pattern in this repo to extend, not something to invent from scratch.

**Design implication for the health endpoint**: the health check should consult an `IsShuttingDown` flag (flipped by an `ApplicationStopping.Register` hook, same pattern as above) *before* evaluating CPU/RAM/Cosmos/Redis, and return unhealthy/503 immediately once shutdown starts — regardless of whether the actual dependencies are still fine. This makes the health endpoint double as the shutdown signal for whatever's routing traffic (Azure App Service's built-in instance health-check feature, if `healthCheckPath` gets configured — not currently set, per `docs/infrastructure.md`; not independently re-confirmed this session — or the internal load balancer named in the ticket), so new requests stop being routed to an instance the moment it starts draining, not only once it actually exits.

**Also worth proposing, not yet confirmed as necessary**: whether the default 10s `shutdownTimeLimit` is actually sufficient for Sales.API's real in-flight work (SignalR hub connections — 5 hubs mapped in `Program.cs` — plus any in-flight Cosmos/Redis calls). The Event ID 1005 pattern is circumstantial evidence 10s might be too short under load, but that's not confirmed — could equally be a hung/deadlocked request that would never finish draining regardless of the limit. Extending `shutdownTimeLimit` (`WEBSITE_SHUTDOWN_TIME_LIMIT` app setting external to the app, or `HostOptions.ShutdownTimeout` in-process) is a real lever, but should follow evidence of actual drain-time need, not be bumped speculatively.

**Resolved (2026-09-22, refined shutdown spec from user/Dev)**: yes, `CosmosClientPool` and `IConnectionMultiplexer` should be disposed explicitly on a graceful stop — mapped onto a concrete 4-step sequence (close ports / drain in-flight / close DB-Redis connections / PKILL as the existing ANCM safety net, not new code). **Sequencing correction caught while designing this**: an earlier draft of this same design proposed disposing Cosmos/Redis in the same `ApplicationStopping.Register` callback that flips the shutdown flag — wrong, since that fires immediately, before in-flight requests have drained, and would rip dependencies out from under requests still using them. Corrected: the shutdown flag flips on `ApplicationStopping` (step 1, immediate — so health reporting reacts right away), disposal happens on `ApplicationStopped` (step 3, fires only after the host finishes draining). Full detail: `ops.md` §6.

## Refined design received (2026-09-22) — instance vs. per-tenant split

User (relaying either their own design or Dev feedback — not specified which) provided a concrete refinement of the whole approach, reasoning from the multi-tenant architecture directly: if the instance itself goes down, it affects every tenant, so scaling/routing decisions make sense — but if Cosmos or Redis goes down for one tenant, scaling the instance does nothing, the impact is tenant-scoped. This splits the design into two independent layers:

1. **HTTP status code** — reflects instance health only: CPU%, RAM%, HTTP Queue length. This is the signal a load balancer/autoscaler can actually act on.
2. **JSON body** — per-tenant breakdown of Cosmos/Redis, 3-level status (OK/WARN/PROBLEM) each with response time. This is the signal an SLA measurement tool needs — the load balancer has no use for it (it can't fix one tenant's Cosmos outage by routing traffic differently).

Single endpoint (`/healthcheck`, given explicitly, at root level rather than the existing `api/v1/Status/Health` — see caveat in `ops.md` §1 about this diverging from the shared `StatusController` convention across the 8 App Services). Thresholds as App Service configuration variables, not hardcoded.

This is a materially different design from the first cut earlier in this investigation (which tied a single binary Healthy/Unhealthy status to *all* checks combined). Full v2 design, all code sketches, and the open implementation questions (RAM% denominator) are in `ops.md` — not duplicated here to avoid the two files drifting.

**Correction (2026-09-22): Sales.API runs .NET 10, not .NET 7.** `SmartFran.Cloud.Sales.API.csproj` has `<TargetFramework>net10.0</TargetFramework>` — confirmed, also independently corroborated live via `cloud/events/20260920_sales-oom-48h/investigation.md`'s `az webapp config show` output ("running .NET v10.0"). An earlier pass of this same investigation wrongly inferred .NET 7 from NuGet package version numbers (`Microsoft.AspNetCore.Authentication.JwtBearer Version="7.0.13"`, etc.) — package version numbers don't track `TargetFramework`, and I should have cross-checked the `.csproj` directly (or the already-available `az webapp config show` output from a sibling investigation) instead of inferring from package versions. With .NET 10 confirmed, the HTTP Queue metric question (flagged earlier as needing an `EventListener`) resolves cleanly: Kestrel exposes `kestrel.queued_requests` via the modern `System.Diagnostics.Metrics` API (`Microsoft.AspNetCore.Server.Kestrel` Meter, stable since .NET 8) — a `MeterListener` (BCL, no new NuGet) is enough, no custom EventCounters plumbing needed. Full code in `ops.md` §2.

## Response shape finalized (2026-09-23)

Reworked twice after the route change: first dropped `REDIS` from the response entirely (Sales has no such dependency — user's call), then restored it at **root level** rather than per-tenant, on the observation that Redis is instance-wide, not tenant-scoped, unlike Cosmos — repeating the identical result inside every tenant block added nothing. Final shape:

```json
{
  "CPU": 12.4,
  "RAM": 45.2,
  "HTTP_QUEUE": 0,
  "GENERAL_STATUS": "OK",
  "REDIS": { "STATUS": "N/A", "RESPONSE_TIME": null },
  "grido": { "STATUS": "OK", "COSMOS": { "STATUS": "OK", "RESPONSE_TIME": 18 } }
}
```

`CPU`/`RAM`/`HTTP_QUEUE` are now exposed as raw values in the body (previously only used internally to compute the binary 200/503 decision), and `GENERAL_STATUS` gives them a proper 3-level status (`OK`/`WARN`/`PROBLEM`, not `ERROR` — user's explicit correction) computed the same way as Cosmos/Redis: each metric against its own Warn/Problem threshold pair (already present in `HealthCheckThresholds` but previously only the Problem thresholds were used), reduced to a single worst-of-three result via `DependencyStatusExtensions.WorstOf`. HTTP status is still 503 only on `PROBLEM` (or shutdown) — `WARN` still returns 200, since a balancer shouldn't pull an instance for something the SLA tool should flag instead.

**Churn on `DependencyStatusExtensions`/`RedisHealthCheck`**: deleted when `REDIS` was dropped (no caller left), then rewritten when it came back — `WorstOf` gained an `IEnumerable<DependencyStatus>` overload to reduce the three instance metrics, not just the original two-argument Cosmos/Redis case. Worth remembering if this file gets touched again: it's had two full delete/recreate cycles in one day, driven entirely by response-shape decisions, not bugs.

**Implementation status (2026-09-23, mid-change)**: user asked to pause code/Docker work while the ticket text (`ops.md`) settles — `InstanceHealthEvaluator`, `InstanceHealthResult`, `RedisHealthCheck`, and `DependencyStatusExtensions` are updated to match this final shape, but `StatusController.HealthCheck()` and `Program.cs` still reflect an earlier version (per-tenant `REDIS`, binary `IsHealthy` without `GeneralStatus`). **Not yet rebuilt or retested against this shape** — do that before trusting the code compiles. `ops.md` is current; the code is not.

## Access-control scope for `/healthcheck` (2026-09-29) — new angle, not yet in `ops.md`

Separate from the functional design above: the endpoint needs to be restricted to a handful of legitimate consumers, since it exposes both instance-level scaling signals and per-tenant health signals (confirmed real, matches the finalized response shape above) — an open endpoint could leak operational data or be used to force load.

**Corrected (2026-09-29): Auth0, token auth, and rate-limiting were proposed by the operations team, not ruled out as a technical/architectural constraint.** Management rejected these three options — not a technical finding either from this investigation or from the team's own proposal, an organizational decision. Reason not specified here (not confirmed, not this investigation's place to speculate). Don't treat "ruled out" as a technical conclusion by anyone if this file is read later — it's a rejected proposal, full stop.

**Confirmed (general Azure architecture fact, not investigation-specific):** Azure RBAC operates at the resource level (whole App Service, via ARM) — there's no native mechanism to grant access to a specific route/endpoint within an app's own code.

**Proposed direction: WAF-level access restriction.** Per `cloud/docs/infrastructure.md` (WAF/APIM section, confirmed 2026-08-25, GITIN-1938): **no WAF or API gateway exists in front of any retail App Service today**, including Sales.API. This means the proposal is to *introduce* a WAF, not add a rule to something already running — materially bigger scope (new infrastructure + cost, see `cloud/events/20260915_gitin2042-waf-cost-estimate/` for the relevant cost-estimation precedent) than the original framing implied. Corrected in `email_pm.md` before sending.

**Checked and ruled out, 2026-09-29 — Azure App Service Access Restrictions.** Confirmed via Microsoft's own documentation (`learn.microsoft.com/en-us/azure/app-service/app-service-ip-restrictions`): rules filter by source IP/VNet subnet/service tag/HTTP header, enforced at the App Service front-end **for the entire app** — the only path-like distinction available at all is a fixed "main site vs. SCM/advanced-tools site" split, not general path-based scoping. **No mechanism to restrict just `/healthcheck` while leaving the rest of Sales.API's routes open.** Since Sales.API must stay reachable for normal business traffic on its other routes, this doesn't solve the actual requirement — it's a whole-app IP allowlist, not a per-route control. Rules out this lighter-weight alternative; the original WAF-introduction proposal is the correct direction for a per-route requirement, not just the only remaining option by elimination.

**Scope clarification (2026-09-29): a code-level fix (IP/shared-secret check inside Sales.API itself) was raised and explicitly ruled out as out of scope, not overlooked.** The task is scoped to an operations/infrastructure-layer solution — "from an operations perspective," per the original task framing. A code change belongs to Dev (modifying Sales.API), not something this ticket's scope covers. WAF-introduction stands as the correct direction within that scope, not merely the last option after exhausting alternatives.
