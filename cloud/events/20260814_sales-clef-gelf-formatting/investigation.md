# Investigation — 20260814_sales-clef-gelf-formatting (GITIN-1835)

**Status:** closed. Fix deployed, connected, and confirmed end-to-end against **real live traffic** (not just the simulator) — `_id: 4e564600-97f3-11f1-8f28-7c1e52beabec`, a genuine production message (`Sale.Close.StockMovement.Failed`, indexed in `sales__4`), shows `message`/`full_message`/`name`/`resource_group`/`resource_path`/`subscription`/`type`/`source` all resolved correctly, and `streams` contains both `6a47c5c94b3c88a95fad7a7a` (`PROD-Sales-AppServicePlan`) and `000000000000000000000001` (Default Stream) — direct proof `route_to_stream()` works in production, not just simulation.

## Objective

GITIN-1835: format the new log shape arriving in Cloud Graylog from Sales (SignalR disconnect warnings, unhandled application exceptions) — messages show `message`/`full_message` as the literal string `"log entry"`, `source` as the literal unresolved string `"%{resource_path}"`, and a `tags: "event_original_guard_skipped"` value of unknown origin.

## Root cause — confirmed, ties to a prior closed ticket (GITIN-1811)

`cloud/events/20260810_sales-serilog-console-logs/` (GITIN-1811, closed 2026-08-11) already established: **`AppServiceConsoleLogs` is structurally unsupported for .NET applications on Windows App Service** (Microsoft-confirmed — only JavaSE/Tomcat are supported). Sales and Pos are the only two Windows-hosted apps in this fleet; every other app is Linux and unaffected. That investigation's closing recommendation (`ops.md` Acción #4) was: **a direct Serilog→GELF sink, bypassing Diagnostic Settings/Event Hub entirely** — "probablemente la opción más simple." This ticket (GITIN-1835) picks up after that architecture decision was implemented.

Confirmed via two real Graylog messages compared side-by-side (2026-08-14):
- A well-formed `AppServiceHTTPLogs` message (health-check, `_id: 4276b6d0-97e4-11f1-8f28-7c1e52beabec`) — its `event_original` is Azure's standard `{"records": [{...resourceId, category, properties...}]}` envelope. This one goes through Event Hub → Logstash (`cloud-graylog/docs/azure-eventhub-to-graylog.conf`) correctly, unaffected by anything in this investigation.
- The broken messages (SignalR warning `fa6dc324-97dd-11f1-8f28-7c1e52beabec`, application exception `d0465850-978d-11f1-8f28-7c1e52beabec`) — their `event_original` is a **bare Serilog CLEF line** (`{"Timestamp":...,"Level":"Error","MessageTemplate":...,"Properties":{...}}`), no `records`/`resourceId` envelope at all. Both share the same `gl2_source_input` and `facility: "gelf-rb"` as the HTTP-log example, meaning they land on the same Graylog GELF input (port 12201) — consistent with a direct Serilog GELF sink hitting Graylog directly, not routed through Logstash.

**Self-correction, twice, on the same point — final answer confirmed 2026-08-14 evening.** Initially assumed these bare-CLEF messages still passed through the Logstash `azure-eventhub-to-graylog.conf` pipeline (since `%{resource_path}` — that pipeline's own `gelf output` `sender` config — appears verbatim in `source`), and edited that file accordingly. Reverted that edit after finding GITIN-1811's conclusion that Diagnostic-Settings-based `AppServiceConsoleLogs` is structurally incapable for .NET on Windows — reasoning a `records`-less event therefore can't have come through Event Hub at all. **That reversal was itself wrong.** GITIN-1811's ops.md only *speculated* which fix dev would choose ("Sink GELF directo... probablemente la opción más simple") — it never confirmed which was actually implemented, and I treated that speculation as settled fact.

**Confirmed via the actual live file content** (pulled from the VM into `docs/azure-eventhub-to-graylog.conf` on 2026-08-14, after discovering the repo copy had drifted from what's actually deployed — see below): the pipeline's `else` branch (fires whenever `record.is_a?(Hash)` is false, i.e. no `records` wrapper) contains `event.tag("event_original_guard_skipped")` — the **exact, confirmed source** of the previously-unexplained tag on every Sales CLEF message. Since this branch only exists inside the Event Hub input's filter chain, Sales' bare-CLEF messages must be arriving **on the Event Hub itself**, not via a separate direct-to-Graylog-GELF path. The real producer is `Serilog.Sinks.AzureEventHub` (writes directly to Event Hub, bypassing only Azure Diagnostic Settings' `records`-wrapping) — not `Serilog.Sinks.Graylog` (bypasses Event Hub entirely) as previously documented here and in `ops.md`. Not independently confirmed at the application-code level (would need to check Sales' actual Serilog sink config), but confirmed at the infrastructure level via the pipeline's own tagging code, which is stronger evidence than the earlier guess.

This also fully explains, via the *same* mechanism, everything previously attributed to "probably a copy-paste artifact": `source: "%{resource_path}"` (this pipeline's own `gelf output` sender template, unresolved because `resourceId`/`resource_path` are never set for a `records`-less event) and `message: "log entry"` (this pipeline's own message-building fallback chain, all of whose fields are absent on a bare CLEF event). None of this changes the fix itself — the Graylog Pipeline Rules (Stage 0/Stage 1) run downstream of Logstash regardless of producer mechanism, and are already confirmed working against real production traffic. It only corrects which upstream component is actually responsible.

**Separate finding, same session: the repo's `docs/azure-eventhub-to-graylog.conf` had drifted from the live deployed file** (`/etc/logstash/conf.d/azure-eventhub-to-graylog.conf` on the Logstash VM) — the live version has the `else`/tagging branch above, a truncation safety net for both `event_original` and `[event][original]`, and live credentials in the `input` block, none of which were reflected in the repo copy. Pulled the real content into the repo file directly from the VM to fix this drift — same class of problem as the stale `docker-compose.yml` duplicate documented elsewhere in this repo (near-identical filename/content causing real confusion). **Live credentials note:** the pulled-in content includes a real Event Hub SAS connection string and storage account key in plaintext — per this repo's secret-handling rule, these must not be referenced by value in any ticket/doc output; already true here, but flagging since the file itself (not a doc) now holds them and should be handled with the same care as any other credential-bearing file in this repo.

## Fix — Graylog Pipeline Rules (not Logstash)

Since these messages bypass Logstash, the fix lives entirely in Graylog: `cloud-graylog/docs/sales-direct-gelf-clef-format.rule` — 5 separate rules (Graylog's rule language has no `if`/`then`/`else` at all, confirmed against official docs after two failed attempts assuming otherwise; conditional branches must be separate rules with more specific `when` clauses), wrapped in pipeline **"GITIN-1835 Sales CLEF formatting"**, connected to **Default Stream** (where these messages land — confirmed via `"streams": ["000000000000000000000001"]` on both broken examples).

All 5 rules gate on `has_field("MessageTemplate")` — Serilog's own CLEF field, never present on Azure Diagnostic Settings records — making them structurally unable to match (and therefore unable to alter) anything already formatted correctly, like the HTTP logs.

Rules:
1. `GITIN-1835: CLEF message` — `message` = `$message.MessageTemplate`
2. `GITIN-1835: CLEF full_message with exception` — `full_message` = template + `"\n\n"` + exception (`when has_field("Exception")`)
3. `GITIN-1835: CLEF full_message without exception` — `full_message` = template (`when NOT has_field("Exception")`)
4. `GITIN-1835: CLEF source from Properties.Service` — `source` = `$message.Properties_Service` (`when has_field("Properties_Service")`)
5. `GITIN-1835: CLEF source fallback` — `source` = `"unknown-service"` (`when NOT has_field("Properties_Service")`)

**Syntax lessons learned (real trial-and-error against the live rule validator, not guessed):**
- No `if`/`then`/`else` in any form — neither as a statement with multi-statement blocks, nor as a value-producing expression assigned via `let`. Confirmed against `go2docs.graylog.org/current/making_sense_of_your_log_data/rules.html` after two failed attempts. Branching must be separate rules.
- `set_field(field, $message.OtherField)` works fine with a raw field reference (no explicit type coercion needed) — confirmed via rule #1's simulator test.
- `concat()` appears to require explicitly string-typed arguments — removing `to_string()` from rule #2 caused the *update* (not create) to fail with an opaque `Bad Request` via the UI. Reverted to `to_string()`-wrapped arguments for the `concat()` call specifically; kept plain field references everywhere `set_field` is used directly (rules #1, #4). Not fully root-caused (never got a detailed error for the `concat()` case — the UI's rule-update endpoint returns only a generic `Bad Request`, unlike rule creation, which returns a detailed syntax-error array), but the working pattern is confirmed empirically.
- The UI's rule-*update* flow returned an opaque `Bad Request` with no detail even for since-confirmed-valid syntax; going through the REST API directly (`PUT /api/system/pipelines/rule/{id}`) for the same content succeeded cleanly (`"errors": null`). If the UI update path errors opaquely again, prefer the direct API call — same auth pattern as rule creation (`GRAYLOG_API_KEY`, `X-Requested-By: cli` header required or Graylog returns a CSRF error).
- This Graylog instance (7.1.3) has no legacy `/api/search/universal/relative` endpoint — returns a bare `null` body, not an error. Must use the 3-step async Views Search API (`POST /views/search` → `POST /views/search/{id}/execute` → poll `GET /views/search/status/{job_id}`), same pattern already established in `cloud/events/20260812_prod-full-onboarding/scripts.sh`.

## Reference schema — expected shape for any direct-GELF Serilog message

Confirmed via real Sales-PROD output (`_id: 457d6b80-9802-11f1-8f28-7c1e52beabec`) as the target shape for any future service adopting this same direct-GELF sink pattern (e.g. if Pos ever does):

- **`Level`** (PascalCase, top-level) — must be present. Comes directly from Serilog's own CLEF output template (`SerilogBootstrap.cs`'s `ExpressionTemplate`); not something this pipeline builds. Distinct from GELF's own standard lowercase `level` (severity number), which is always present on every GELF message regardless of source.
- **`Properties_*`** (flattened) — automatic. Any nested `Properties` object gets GELF-flattened into `Properties_<Key>` fields by Graylog's own GELF output handling, with no rule needed to build this — already true for Sales without any of the 6 rules in this ticket touching it. If a future service's `Properties` object *isn't* flattening this way, that's a GELF/ingestion-level issue, not something to patch with a pipeline rule.
- **`message`/`full_message`/`name`/`resource_group`/`resource_path`/`subscription`/`type`/`source`** — NOT automatic. These are exactly what this ticket's 6 rules build (Stage 0 for the first two, Stage 1 for the rest, scoped to `Properties_Service`+`Properties_Environment`). A new service adopting this sink pattern needs its own Stage 1 rule (or equivalent), following the same confirm-the-real-resource-name-first approach used for Sales — not a guessed naming pattern.

**Confirmed universal (2026-08-14):** searched `_exists_:Properties` (the literal unflattened field, not `Properties_*`) across all 10 streams accessible in this Graylog instance, last 7 days — `total_results: 0`. No message anywhere ever kept an unflattened `Properties` object; GELF's flattening is instance-wide behavior, not Sales-specific and not something this ticket's rules needed to build.

## AppLevel fix — deployed and confirmed at scale (2026-08-14, same session)

Devs asked to filter by severity across services beyond Sales. Investigated `AppServiceAppLogs`/`AppServiceConsoleLogs` messages directly (Sales-DEV, Pos-DEV, Business, Person, Platform) and confirmed Azure's own record-level `level` string (e.g. `"Error"`, `"Informational"`) was being silently lost: `record.each { |k, v| event.set(k, v) }` in `azure-eventhub-to-graylog.conf` promotes it to Logstash's internal `level` field, but the `gelf` output requires a numeric syslog severity there, so it gets overwritten by output time — the string only survived buried in the stringified `properties` blob or `event_original`, never as a filterable field.

**Fix:** capture `record["level"]` into a new field `AppLevel` before the generic promotion can overwrite it — added to the live `record.each` ruby block in `azure-eventhub-to-graylog.conf`, immediately after `event.set("event_original", ...)`.

**Deployment (separate from the Graylog Pipeline Rules deployment above — this is a Logstash config change, not a Graylog rule):**
- Discovered the repo copy (`cloud-graylog/docs/azure-eventhub-to-graylog.conf`) had drifted from the live file on the VM (`/etc/logstash/conf.d/azure-eventhub-to-graylog.conf`) — pulled real content in to fix this, and in the process found (then immediately redacted) real Event Hub SAS/storage credentials that had briefly landed in the repo file — fixed before commit, file has zero prior commit history so nothing leaked into git history.
- Manual edit on the VM hit the exact known corruption pattern documented in `20260701_logstash-deployment` (H9) — the `input {}` block's closing brace was lost during editing, causing three consecutive `logstash -t` failures (`Expected one of [ \t\r\n], "#", "=>" at line 12`) before being caught and fixed.
- `logstash -t` clean (`Configuration OK`) after the fix, `sudo systemctl restart logstash` succeeded, service reconnected to Event Hub partitions cleanly.
- **Confirmed on live traffic:** `_exists_:AppLevel` returned `total_results: 4233` within 30 minutes of restart, across multiple services (Person, Platform confirmed directly), each with a real `AppLevel` value (e.g. `"Informational"`) alongside GELF's untouched numeric `level: 6`.

## Scope confirmation (2026-08-14)

`_exists_:Level` (Serilog's own PascalCase CLEF field, distinct from GELF's standard lowercase `level`) returns hits in `PROD-Sales-AppServicePlan` but zero in `PROD-Business-AppServicePlan` — confirms Business isn't sending any bare-CLEF direct-GELF messages at all, consistent with GITIN-1811: Business is Linux, where `AppServiceConsoleLogs` is supported, so it never needed the direct-GELF workaround Sales required. The fix's scope (Sales only) is correctly limited, not silently missing an equivalent Business-side gap.
