# Investigation — 20260908_gitin2014-sonar-masked-asterisks

**Status:** converged — ticket written and closed (`ops.md`, `Resuelto: Sí`). Both files' triggers identified; remaining items (persistence-mechanism curiosity, stale hostname doc fix, Toque credential remediation) are follow-up, not blocking.

**Jira:** [GITIN-2014](https://smartit-ar.atlassian.net/browse/GITIN-2014) "[OPE] Contenido de archivos en sonar 'Masked' con *"

## Purpose

SonarQube's UI shows the source code of certain files (`DEVELOP.SmartPedidos.Concentrador:src/config/env/development.js`, `DEVELOP.SmartPedidos.Concentrador:src/controllers/branch.js`) entirely replaced with asterisks in code snippets and the source viewer. Determine whether this is a bug, a display/rendering artifact, or expected behavior — and if expected, what triggers it.

## Confirmed facts

- **Host:** `sfcg-sonarqube` (Azure VM), reverse-proxied by nginx at `https://sfcg-sonarqube.smartfran.com` (the actual live hostname per `sonar.core.serverBaseURL` in `api/system/info` — the operations runbook, `operations/docs/sonarqube_upgrade_runbook.md`, documents a different/stale hostname `sf-sonarqube.smartfran.com`; nginx's own vhost config still uses that stale name too, worth reconciling as a doc-accuracy follow-up, not blocking this ticket).
- **SonarQube version: 26.9.0.129388**, Community Edition — confirmed via `api/system/info`. Upgraded/restarted 2026-09-05 (`sonar.core.startTime`, and the `es.log` startup sequence timestamp) — 3 days before this investigation.
- **Root cause confirmed via SonarSource's own release notes** ([SonarQube Community Build release notes](https://docs.sonarsource.com/sonarqube-community-build/server-update-and-maintenance/release-notes)): version 26.9.0.129388 shipped a new feature — *"Secret values found by secret detection are now masked in Web API responses. The reported range is replaced with `*` characters in source, code viewer, and snippet responses, preserving the length of the source. When a safe location cannot be determined, the affected line or the whole file is masked."* This is **not a bug** — it's the tool refusing to display files it believes contain secrets, working as newly designed. It first appeared with the exact version this instance was upgraded to 3 days before the report — consistent with the user's own observation that "with the earlier version this were not happen."
- **Confirmed this is server-side, not a browser rendering artifact.** Direct `GET /api/sources/raw` calls (with a properly-scoped **User Token** — a **Global/Analysis Token** returns `403`, since that token type only carries "Execute Analysis" permission, not "Browse"/"See Source Code") return the masked (asterisk) content directly from the API for both files — confirmed via `data`-equivalent output files (not committed here, contain redacted structure only, see Comandos ejecutados in `ops.md`).
- **Ruled out, in order:**
  - Not a large-file browser-rendering/virtualization artifact — initially suspected for `branch.js` (6,256 lines, far larger than any sibling controller file) since the earlier UI-copy-paste of its issue list came through asterisked while a later paste of just the issue list (no code snippet) came through clean. Ruled out once the raw API itself was confirmed to also return masked content for this file — a rendering-only theory can't explain a masked API response.
  - Not a project-wide blanket masking setting — `DEVELOP.SmartPedidos.Concentrador:src/controllers/country.js` (small, no secrets) returned clean, real code via the same raw API call.
  - Not a Security Hotspot — `api/hotspots/search` for `branch.js` returned 0 results.
  - Not a Vulnerability-type Issue — `api/issues/search?types=VULNERABILITY` for `branch.js` returned 0 results. (Confirms the masking pipeline is independent of the classic Issues/Hotspots system entirely — consistent with the release note's description of a distinct "secret detection" mechanism.)
  - Not an nginx/proxy-layer content filter — `/etc/nginx/conf.d/sonar.conf` is a plain reverse proxy (`proxy_pass http://127.0.0.1:9000`), no `sub_filter`/WAF/DLP directive of any kind.
- **`development.js` is fully explained**: it's already a known, tracked finding — `smartpedidos/events/20260720_credenciales-mongodb-hardcodeadas/` documents real hardcoded MongoDB Atlas credentials, an AWS ID/secret pair, and a shared static token in this exact file (row #4, `development.js:20-21`, plus row #15 for `tokenStatic`). SonarQube detecting this and refusing to display it is consistent and expected.
- **`branch.js`'s specific trigger located (2026-09-08).** `api/src/controllers/branch.js:3755` and `:3776` (duplicated inside the error-logging block for the same call) hardcode a Basic Auth credential pair (`{ username: ..., password: ... }`) passed directly to `httpClient.post()` to authenticate against the "Toque" delivery-platform integration (`baseUrlToque` + `CancelarPedido`, `case 11` of the platform switch in `branchRejectOrder`). Both fields are the literal platform name — weak/guessable, but still a real embedded credential, and exactly the object-literal shape secret scanners are built to catch. Value not repeated here, consistent with how `development.js`'s secrets were handled. Still unconfirmed via Hotspots/Vulnerabilities API (neither surfaced it) — the masking engine clearly detected it independently of that pipeline, consistent with the "separate mechanism" read established earlier.

## Current working theory

Not a bug — the tool is correctly protecting files it detects contain secrets. `development.js`'s trigger is already fully explained by an existing, independently-confirmed finding. `branch.js`'s specific trigger is unconfirmed but plausible given the file handles `branchSecret`, multiple third-party client secrets (Rappi, MercadoPago), and a recently-merged commit that logs `req.body?.branchSecret[0]` — any secret-shaped literal anywhere in the file (even in a comment, a fallback default, or old dead code) could be enough to trigger whole-file masking under this feature's stated fallback behavior.

## Ruled out

See "Confirmed facts" above — five separate hypotheses tested and eliminated in sequence before reaching the actual (sourced, documented) cause.

## Open questions / next steps

1. **Locate the exact secret-shaped literal in `branch.js`.** Since it doesn't surface via Hotspots/Vulnerabilities, this likely needs either: a manual grep of the local read-only clone for API-key/token-shaped literal strings (regex-based, not just `new CustomError`/`new Error` searches already done for the unrelated Bug-type findings in this same file), or asking SonarSource support what specifically triggered it, or waiting for a SonarQube UI/API surface that exposes secret-detection findings directly (not found in this session — may not exist in Community Edition, or may need a different endpoint not tried here).
2. **Reconcile the stale hostname** in `operations/docs/sonarqube_upgrade_runbook.md` (`sf-sonarqube.smartfran.com`) and in nginx's own vhost config (same stale name) against the live, correct hostname (`sfcg-sonarqube.smartfran.com`, confirmed via `sonar.core.serverBaseURL`) — tangential to this ticket, but worth a doc fix since it caused a real `HTTP_STATUS:000` dead-end during this investigation.
3. **No action needed on the masking itself** — it's correct, intended behavior. The only real remediation path is removing the actual secrets, which for `development.js` is already tracked (SEC-103, SEC-114 in the credentials ticket). For `branch.js`, remediation can't be scoped until item 1 is resolved.
4. **Test actually run (2026-09-08) — negative result, theory partially retracted.** `sonar.text.activate` was genuinely set to `false` globally via the Web API (confirmed `HTTP_STATUS:204`), then `concentrador-service`'s pipeline was re-run. `api/sources/raw` for `development.js` afterward still returned `HTTP_STATUS:200` with fully masked (asterisk) content, byte-for-byte the same shape as before the setting change. **This means `sonar.text.activate` does not control this masking behavior in a way a re-analysis clears** — retracting the earlier assumption that disabling secrets detection would resolve it.
   - **Leading hypothesis, not confirmed:** SonarQube's incremental analysis may skip re-processing/re-storing a file's source blob when its content hash is unchanged since the last scan — meaning the already-masked blob persisted from the *original* analysis (while detection was active) simply never got reprocessed, regardless of the current setting. Testing this properly would require an actual content change to the file (forcing reprocessing) followed by a re-scan — not attempted, out of scope for this ticket without modifying real source.
   - **Setting reverted, confirmed** (`api/settings/reset`, `HTTP_STATUS:204`) — secrets detection is back to its default (active) instance-wide. No benefit was demonstrated to leaving it off, so it wasn't left disabled.
   - **Ticket closes with this open technical question unresolved**: the masking is confirmed real, version-tied (26.9.0.129388), and expected/intentional per SonarSource's release notes — but the exact trigger/persistence mechanism for *why a re-scan doesn't clear it* is beyond what internal testing in this session could determine. Further investigation would need either a real content-change test or SonarSource support.
5. **Checked whether the masking can be disabled (2026-09-08):** no dedicated toggle exists for "detect but don't mask" — that's not separable per SonarSource's own docs. The only lever is `sonar.text.activate=false`, which disables secrets detection entirely (project or global). **Not recommended** — this repo has a real, already-tracked hardcoded-credentials problem; turning off detection would lose the actual security signal, not just the cosmetic symptom. The other documented knobs (`sonar.secrets.disableEntropyFilter`, `sonar.secrets.disableKnownFakeSecretFilter`, `sonar.secrets.excluded.file.suffixes`) only tune detection sensitivity/scope, none control masking once something's flagged. The masking resolves on its own once the real secrets are removed from source.
