# Investigation — 20260812_graylog_messages_not_arriving

**Status:** closed. Root cause mechanism and full timeline are precisely evidenced (freeze during Docker's graceful stop of an unbounded-memory OpenSearch container; ~9 min freeze-to-reboot confirmed via two independent sources). All continuing work — the OpenSearch memory-config fix, and the `msg_rest_status`/`msg_branch_id` indexer-failure findings below — carries forward to `operations/events/20260813_platform-service-branch-id-unknown-mapping-error/` (GITIN-1854). This folder remains as historical record only; do not add new findings here.

## Confirmed facts
- Trigger: while adding a `$MessageId` field extraction to the NXLog config on the hMailServer relay VMs (`SFCG-SMTP-01`/`SFCG-SMTP-02`, `192.168.50.161`/`.162`, service `SF-SMTPRL`), messages stopped arriving in Graylog.
- Extensive review of the NXLog config on both VMs (drop rules, `*.log` wildcard, `w3c_parser_mobile` CSV extension, `Output`/`Route`) found nothing wrong — the config was structurally correct in every version tried, including the original/unedited one, which also went silent independently. This ruled out NXLog config as the cause (C1-C4 in scripts.ps1/scripts.sh, see ops.md for the full chain).
- A manual raw UDP test packet sent directly from `SFCG-SMTP-01` to Graylog's `TXT_UDP` input (port 1514) arrived within ~1 second — network path confirmed healthy (C10, scripts.ps1).
- Root filesystem on the Graylog/OpenSearch/MongoDB Docker host (`sf-monitoreo.smartfran.com`) is healthy (20% used) — ruled out disk pressure as an active cause on that mount (C1, scripts.sh).
- `docker logs opensearch` shows the OpenSearch container process restarted: `Cluster is not recovered yet` followed by `recovered [257] indices into cluster_state` at `2026-08-12 01:25:21 UTC` (C4, scripts.sh).
- `docker inspect opensearch` confirms `StartedAt: 2026-08-12T01:24:54Z`, `OOMKilled: false` — rules out a cgroup/Docker memory-limit kill specifically, does not rule out a JVM-internal `OutOfMemoryError` or other cause of the process exiting.
- **Correction — this was not a self-resolving container restart.** `last reboot -F` confirms the current VM boot is `Wed Aug 12 01:24:46 2026` — the same moment, not a coincidence. The Docker services (`graylog`/`opensearch`/`mongo`) stopped responding to a normal restart and required a **forced reboot of the entire VM**, done manually, to recover. The previous boot ran uninterrupted for 205 days (`Jan 19 2026` → `Aug 12 2026`) and shows as a dangling second `"still running"` entry in `last reboot` rather than a clean completed range — consistent with the transition being a hard power-cycle, not a graceful shutdown. Long uninterrupted uptime on a Docker host running this much data (`graylog_299` alone at 472.8GB) is a plausible contributing factor to why normal Docker-level restarts stopped working, but not confirmed as the specific trigger. Confirmed via `docker inspect --format '{{.RestartCount}}'`: `opensearch` and `graylog` both show `RestartCount=0`, `StartedAt` ~`2026-08-12T01:24:54-55Z` — a single clean start immediately after the VM reboot, not a Docker-level crash-restart loop. (Note: the `mongo` compose service sets `container_name: mongodb` — inspect it by that name, not `mongo`.)
- `_cluster/health` (checked shortly after the restart) shows `green`, `998`/`998` active primary shards, `100%` — the cluster is a single node (`discovery.type: single-node`), so during the recovery window after any restart, all indices briefly go `red` (unassigned shards) while reinitializing, which was directly observed via `_cat/indices` mid-recovery (C5-C7, scripts.sh).
- `_cluster/allocation/explain` on a specific shard (`aws_wafv2__189`) during the healthy window confirmed it was genuinely `started`, not corrupted — supports "transient recovery," not persistent shard loss.
- Separate, real finding: `graylog_299` (Default Stream index, 472.8GB / ~1.45B docs — anomalously large vs. peer indices at ~3-4GB each) and `sp_platform__50` (SmartPedidos platform-service) are both at OpenSearch's default `index.mapping.total_fields.limit` of 1000 fields, confirmed via `_mapping` field count and via the indexer-failures list (`Limit of total fields [1000] has been exceeded`, 32,448 failures in 24h, 177,356 accumulated). This blocks creating new indices in either rotation series and rejects any message introducing a field name not already mapped — independent of the restart, but likely related to why `graylog_299` never rotated normally.
- Every index in this cluster shows `rep 0` — zero replicas, no redundancy.
- New indexer-failure type found (177,953 accumulated, up from 177,356 — actively ongoing): `aws_logs_51` rejecting documents with `mapper_parsing_exception` — field `msg_rest_status` is mapped as `long`, but some documents send the literal string `"error"` for it, causing `illegal_argument_exception, reason=For input string: "error"` and rejecting the whole document. Distinct mechanism from the field-count-limit issue (this is a type conflict on one field, not too many distinct fields).
- A fourth indexer-failure type was found here (2026-08-13, same mechanism as `msg_rest_status` above) but **split out to its own ticket**: `operations/events/20260813_platform-service-branch-id-unknown-mapping-error/` (GITIN-1854) — root cause confirmed as an application-level bug in `platforms-service`, unrelated to this ticket's OpenSearch restart/silent-UDP-loss scope.
- After identifying the above, `$MessageId` extraction was redeployed on both relay VMs and confirmed shipping correctly to Graylog (`MessageId: 5677615` from `SFCG-SMTP-01`, `MessageId: 126952` from `SFCG-SMTP-02`), no processing errors.

## Current working theory
N/A — converged. The OpenSearch container restarting (cause unconfirmed) leaves the single-node cluster unavailable during recovery; any message sent during that window is lost silently (UDP, no delivery confirmation on the sending side) with zero error on the NXLog side. This explains the full night's intermittent symptom independent of any NXLog configuration. The field-mapping-limit issue is a second, independent problem on the same cluster, not caused by tonight's changes.

## Ruled out
- NXLog configuration on either VM (drop rules, wildcard file count, CSV parser schema, Output host/DNS) — reviewed exhaustively across many iterations; the original unedited config also went silent independently, which is what ruled this out.
- Network reachability from the sending VMs to Graylog — confirmed healthy via direct UDP test.
- Disk pressure on the Graylog host's root filesystem — confirmed healthy (20% used); a 19-day-old Elasticsearch low-watermark alert referenced during the investigation does not reflect the current state of this mount (OpenSearch's actual data volume was not directly isolated to a specific device, but the root filesystem where Docker's default data-root lives is not under pressure).
- A cgroup/Docker-level OOM kill as the specific restart trigger (`OOMKilled: false`) — though the actual trigger remains unconfirmed.

## Open questions / next steps
- **NXLog `$DeliveryStatus` enhancement deployed and confirmed on both relay VMs (2026-08-13).** `if $raw_event =~ /SMTPDeliverer - Message\s(\d+): (.*)/ { $DeliveryStatus = $2; }`, independent of the existing generic `$MessageId` extraction. Confirmed via real Graylog documents from both `SFCG-SMTP-01` (`Cardinality: "01"`, `192.168.50.161`) and `SFCG-SMTP-02` (`Cardinality: "02"`, `192.168.50.162`) — `MessageId`/`DeliveryStatus` correctly decoupled (same `MessageId` value across a message's lifecycle, e.g. `129685`: `"Delivering message from info@clubgrido.com.ar to mladdario@hotmail.com. File: ...eml"` → `"Message delivery thread completed."`). Purpose: early-warning detection for a future recurrence of this incident's root cause (silent UDP loss during OpenSearch cluster unavailability) — comparing hMailServer's own SMTPDeliverer status-event rate against what actually lands in Graylog would surface a gap faster than discovering it after the fact, as happened this time.
- **Trailing-quote bug fixed and confirmed resolved on both relay VMs (2026-08-13).** `(.*)` → `([^"]*)` deployed to `SFCG-SMTP-01` and `SFCG-SMTP-02`, independently confirmed clean on both via real Graylog documents (`"Message delivery thread completed."` and `"...{GUID}.eml"`, no stray `"` on either VM).
- **Confirmed from the real compose file (2026-08-13):** `bootstrap.memory_lock: true` is set on `opensearch` with no matching `ulimits: memlock` block — the memory lock silently fails to take effect (previously suspected, now confirmed present in the actual config). Separately, `deploy.resources.limits` (`memory: 6G` on `opensearch`, `4G` on `mongo`) only takes effect under Docker Swarm (`docker stack deploy`) — confirmed this stack is launched via plain `docker compose up`, which silently ignores the entire `deploy:` block. **Net effect: OpenSearch had no real Docker-enforced memory ceiling at all**, and its JVM heap wasn't lock-protected either. This meaningfully strengthens the OOM theory and explains two previously-puzzling facts: `docker inspect OOMKilled: false` only reflects container-cgroup kills, not host-level ones, and a host-level OOM event killing critical processes would plausibly explain why `systemctl reboot` hung and required a forced AWS console reboot. Not yet independently confirmed via kernel logs — next step below.
- **Compose file identity confirmed (2026-08-13):** the running containers were created from `/home/ubuntu/scritps/graylog/graylog/graylog-compose.yml` (confirmed via `docker inspect opensearch --format '{{index .Config.Labels "com.docker.compose.project.config_files"}}'`), not the similarly-named `docker-compose.yml` in the same directory — that one is stale/unused (different, weaker memory numbers, a real YAML bug of its own: a misplaced `healthcheck` block landed under `depends_on.mongo` instead of the `opensearch` service, and hardcoded plaintext secrets instead of `${VAR}` substitution). `graylog-compose.yml`'s content matches everything documented in the bullet above (`Xms2g/Xmx2g`, `6G`/`4G` `deploy.resources.limits`) — confirmed accurate against the true source, no correction needed. Recommend deleting or at least stripping secrets from the stale `docker-compose.yml` — its near-identical filename caused real confusion during this investigation and is a risk for the next person too.
- **Precise shutdown-sequence finding (2026-08-13), from the actual host's `/var/log/syslog` and `kern.log.1`:** at `01:15:43 UTC`, systemd began a normal, orderly shutdown (`systemctl reboot`) — dozens of services/timers stopped cleanly in sequence, including `unattended-upgrades.service`, and `dockerd[859]` received `Processing signal 'terminated'` as part of `Stopping Docker Application Container Engine...`. Confirmed via `sed` range extraction: **zero log entries of any kind** — not just Docker-related — exist between `Stopping PackageKit Daemon...` (`01:15:43`) and the new boot's first kernel line (`01:24:51`, ~9 minutes later). Total logging silence across every subsystem, not one service failing to report while others continue, points to the whole system freezing at that instant — coinciding with the shutdown reaching the Docker stop step, which has to gracefully close the `opensearch` container's 472.8GB index with no real Docker memory ceiling and an unlocked JVM heap (both independently confirmed above). No literal kernel OOM-killer log line exists (nothing was logged during the freeze itself), but this is a precise, coherent mechanism, not just circumstantial support anymore.
- **Discrepancy resolved (2026-08-13) via AWS CloudTrail — corrects a prior inaccurate claim.** `ops-events.md` previously recorded the `systemctl reboot` as having hung "más de una hora" before an AWS console force-reboot. CloudTrail shows this is not accurate: `StopInstances` (`i-0d38e3a088f7c4893`, user `dpaniagua`, console) fired at `01:20:17 UTC` with `skipOsShutdown: true` (an explicit force-stop, skipping graceful OS shutdown entirely) — only ~4.5 minutes after the `01:15:43` freeze. `StartInstances` succeeded at `01:24:39 UTC` (`previousState: stopped`, confirming the force-stop had completed), matching the new boot's `01:24:51` kernel line. Total elapsed time from freeze onset to new boot: **~9 minutes**, confirmed by two fully independent sources (syslog/journald boot timestamps, and CloudTrail API call timestamps) — not "more than an hour." No `RebootInstances` event exists at all — the recovery was a force-stop/start cycle via console, not a reboot API call.
