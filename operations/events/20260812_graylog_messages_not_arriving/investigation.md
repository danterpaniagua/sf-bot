# Investigation — 20260812_graylog_messages_not_arriving

**Status:** in progress — core cause converged (OpenSearch restart), new secondary indexer-failure type found 2026-08-12 later, not yet closed

## Confirmed facts
- Trigger: while adding a `$MessageId` field extraction to the NXLog config on the hMailServer relay VMs (`SFCG-SMTP-01`/`SFCG-SMTP-02`, `192.168.50.161`/`.162`, service `SF-SMTPRL`), messages stopped arriving in Graylog.
- Extensive review of the NXLog config on both VMs (drop rules, `*.log` wildcard, `w3c_parser_mobile` CSV extension, `Output`/`Route`) found nothing wrong — the config was structurally correct in every version tried, including the original/unedited one, which also went silent independently. This ruled out NXLog config as the cause (C1-C4 in scripts.ps1/scripts.sh, see ops.md for the full chain).
- A manual raw UDP test packet sent directly from `SFCG-SMTP-01` to Graylog's `TXT_UDP` input (port 1514) arrived within ~1 second — network path confirmed healthy (C10, scripts.ps1).
- Root filesystem on the Graylog/OpenSearch/MongoDB Docker host (`sf-monitoreo.smartfran.com`) is healthy (20% used) — ruled out disk pressure as an active cause on that mount (C1, scripts.sh).
- `docker logs opensearch` shows the OpenSearch container process restarted: `Cluster is not recovered yet` followed by `recovered [257] indices into cluster_state` at `2026-08-12 01:25:21 UTC` (C4, scripts.sh).
- `docker inspect opensearch` confirms `StartedAt: 2026-08-12T01:24:54Z`, `OOMKilled: false` — rules out a cgroup/Docker memory-limit kill specifically, does not rule out a JVM-internal `OutOfMemoryError` or other cause of the process exiting.
- **Correction — this was not a self-resolving container restart.** `last reboot -F` confirms the current VM boot is `Wed Aug 12 01:24:46 2026` — the same moment, not a coincidence. The Docker services (`graylog`/`opensearch`/`mongo`) stopped responding to a normal restart and required a **forced reboot of the entire VM**, done manually, to recover. The previous boot ran uninterrupted for 205 days (`Jan 19 2026` → `Aug 12 2026`) and shows as a dangling second `"still running"` entry in `last reboot` rather than a clean completed range — consistent with the transition being a hard power-cycle, not a graceful shutdown. Long uninterrupted uptime on a Docker host running this much data (`graylog_299` alone at 472.8GB) is a plausible contributing factor to why normal Docker-level restarts stopped working, but not confirmed as the specific trigger. Confirmed via `docker inspect --format '{{.RestartCount}}'`: `opensearch` and `graylog` both show `RestartCount=0`, `StartedAt` ~`2026-08-12T01:24:54-55Z` — a single clean start immediately after the VM reboot, not a Docker-level crash-restart loop. (Note: the `mongo` compose service sets `container_name: mongodb` — inspect it by that name, not `mongo`.)
- `_cluster/health` (checked shortly after the restart) shows `green`, `998`/`998` active primary shards, `100%` — the cluster is a single node (`discovery.type: single-node`), so during the recovery window after any restart, all indices briefly go `red` (unassigned shards) while reinitializing, which was directly observed via `_cat/indices` mid-recovery (C5-C7, scripts.sh).
- `_cluster/allocation/explain` on a specific shard (`aws_wafv2__189`) during the healthy window confirmed it was genuinely `started`, not corrupted — supports "transient recovery," not persistent shard loss.
- Separate, real finding: `graylog_299` (Default Stream index, 472.8GB / ~1.45B docs — anomalously large vs. peer indices at ~3-4GB each) and `sp_platform__50` (SmartPedidos platform-service) are both at OpenSearch's default `index.mapping.total_fields.limit` of 1000 fields, confirmed via `_mapping` field count and via the indexer-failures list (`Limit of total fields [1000] has been exceeded`, 32,448 failures in 24h, 177,356 accumulated). This blocks creating new indices in either rotation series and rejects any message introducing a field name not already mapped — independent of the restart, but likely related to why `graylog_299` never rotated normally.
- Every index in this cluster shows `rep 0` — zero replicas, no redundancy.
- New indexer-failure type found (177,953 accumulated, up from 177,356 — actively ongoing): `aws_logs_51` rejecting documents with `mapper_parsing_exception` — field `msg_rest_status` is mapped as `long`, but some documents send the literal string `"error"` for it, causing `illegal_argument_exception, reason=For input string: "error"` and rejecting the whole document. Distinct mechanism from the field-count-limit issue (this is a type conflict on one field, not too many distinct fields). Source service not yet identified — grepped SmartPedidos source clones (`concentradorService`/`platformsService`) for `rest_status`/`restStatus`, no hits; likely either a different field name at the source with Graylog-side extraction naming it `msg_rest_status`, or a service not yet checked. `aws_logs_*` indices are fed by one of the Kinesis inputs (`concentrador-service` or `platform-service`) per `operations/CLAUDE.md`'s documented input list — not confirmed which one.
- After identifying the above, `$MessageId` extraction was redeployed on both relay VMs and confirmed shipping correctly to Graylog (`MessageId: 5677615` from `SFCG-SMTP-01`, `MessageId: 126952` from `SFCG-SMTP-02`), no processing errors.

## Current working theory
N/A — converged. The OpenSearch container restarting (cause unconfirmed) leaves the single-node cluster unavailable during recovery; any message sent during that window is lost silently (UDP, no delivery confirmation on the sending side) with zero error on the NXLog side. This explains the full night's intermittent symptom independent of any NXLog configuration. The field-mapping-limit issue is a second, independent problem on the same cluster, not caused by tonight's changes.

## Ruled out
- NXLog configuration on either VM (drop rules, wildcard file count, CSV parser schema, Output host/DNS) — reviewed exhaustively across many iterations; the original unedited config also went silent independently, which is what ruled this out.
- Network reachability from the sending VMs to Graylog — confirmed healthy via direct UDP test.
- Disk pressure on the Graylog host's root filesystem — confirmed healthy (20% used); a 19-day-old Elasticsearch low-watermark alert referenced during the investigation does not reflect the current state of this mount (OpenSearch's actual data volume was not directly isolated to a specific device, but the root filesystem where Docker's default data-root lives is not under pressure).
- A cgroup/Docker-level OOM kill as the specific restart trigger (`OOMKilled: false`) — though the actual trigger remains unconfirmed.

## Open questions / next steps
- Confirm the exact trigger for the OpenSearch process restart (JVM-internal OOM suspected, given the known `bootstrap.memory_lock: true` / missing `ulimits: memlock` misconfiguration and heap usage already reported near the container's memory limit — not confirmed).
- Decide whether to raise `index.mapping.total_fields.limit` on `graylog_299`/`sp_platform__50` (and check for other affected indices) — drafted but not executed, since it touches indices shared with other services.
- Investigate why `graylog_299` grew to ~150x the size of its peer indices instead of rotating normally.
- Consider adding replicas if host resources allow — currently zero redundancy cluster-wide.
