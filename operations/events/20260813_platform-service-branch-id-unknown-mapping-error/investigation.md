# Investigation — 20260813_platform-service-branch-id-unknown-mapping-error

**Status:** in progress — OpenSearch memory fix applied and confirmed (2026-08-13). `msg_branch_id` and `msg_rest_status`/`msg_rest_status_code` root causes both confirmed, both affecting `platforms-service` and (for `rest_status`/`rest_status_code`) `concentrador-service` too. `(Dev)` code fixes not yet applied to either service.

**Ticket:** GITIN-1854 — **scope: Graylog indexer failures and the OpenSearch instability behind them, broadly.** `operations/events/20260812_graylog_messages_not_arriving/` (GITIN-1827) is **closed** — all continuing work from that investigation (the OpenSearch freeze root cause, the compose-file fix, the still-open `msg_rest_status` finding) carries forward here rather than reopening a closed ticket. That folder remains as historical record of the original NXLog/`$MessageId` incident and initial investigation steps; this ticket is the active one.

## Confirmed facts — `msg_branch_id` (platforms-service application bug)

- OpenSearch indexer failures on `sp_platform__50` and `graylog_299` (same document IDs in both — expected, Default Stream is a superset): `mapper_parsing_exception` on field `msg_branch_id` (mapped `long`) receiving the literal string `"unknown"` → `illegal_argument_exception, reason=For input string: "unknown"`, rejecting the whole document. First spotted while investigating GITIN-1827 (OpenSearch restart/silent-UDP-loss incident) — distinct, unrelated application-level cause.
- Root cause confirmed in `platforms-service` source (local read-only clone, `smartpedidos/repos/dev-scr-smartPedidos-platformsService/`):
  - `api/src/utils/log.js`'s `_stdout` method (lines 20-37) only omits the `branch_id` field when it is `undefined` — it does not filter the sentinel string `'unknown'`, so that string passes straight through into the JSON log line and gets indexed into `msg_branch_id`.
  - The fallback pattern `branchId ?? 'unknown'` is used across every `Log.save('ERROR'/'WARN', ...)` call in the order-strategy and SQS-provider code:
    - `api/src/platforms/management/strategies/newsTypeStrategy.js` (base class inherited by every `orderStrategy/*` subclass) — lines 36, 70, 93, 143, 168, 203. Triggers when neither `this.savedNew.branchId` nor `this.newToSet.branchId` is set yet at the point an error is logged (an error occurring early in the strategy's lifecycle, before branchId has been populated on the instance). Line 203 is a simpler variant inside `requestLastMile`: `order?.branchId ?? 'unknown'`.
    - Every `orderStrategy/*` subclass inherits this same fallback in its own `catch` block: `viewStrategy.js:53`, `branchRejectStrategy.js:45,58,96`, `platformRejectStrategy.js:97`, `retriveDriverStrategy.js:32,73`, `dispatchStrategy.js:47`, `receiveStrategy.js:39,65`, `confirmStrategy.js:36`, `readyStrategy.js:36,72`.
    - `api/src/platforms/provider/aws.js:50` (`pushNewToQueue`, SQS producer) — triggers if `newOrder` lacks `branchId` when an SQS send fails. Note: line 40 dereferences `newOrder.branchId.toString()` unguarded just above, in the same `try` — a related but distinct minor risk (unguarded call could itself throw if `branchId` is null/undefined), not yet investigated further.
    - `api/src/platforms/provider/aws.js:380` (`pushAutoReplyToQueue`) — triggers when the `branchId` parameter wasn't available when an auto-reply SQS push failed.

## Confirmed facts — OpenSearch memory config / freeze root cause (carried forward from GITIN-1827)

- Compose file identity: running containers created from `/home/ubuntu/scritps/graylog/graylog/graylog-compose.yml` (confirmed via `docker inspect opensearch --format '{{index .Config.Labels "com.docker.compose.project.config_files"}}'`) — copy saved to `config/graylog-compose.yml`. A similarly-named `docker-compose.yml` in the same directory is stale/unused (weaker memory numbers, a misplaced-`healthcheck`-under-`depends_on.mongo` YAML bug, hardcoded plaintext secrets) — recommend deleting it or stripping its secrets; its near-identical name caused real confusion during this investigation.
- `graylog-compose.yml`: `bootstrap.memory_lock: true` set on `opensearch` with no matching `ulimits: memlock` block (no-op). `deploy.resources.limits` (`6G` opensearch, `4G` mongo) only applies under Docker Swarm — this stack runs plain `docker compose up`, so those limits were never enforced. Net effect: `opensearch` had no real Docker-enforced memory ceiling and an unlocked JVM heap.
- Incident timeline (2026-08-12), confirmed via two independent sources (host syslog/journald, AWS CloudTrail):
  - `01:15:43 UTC` — `systemctl reboot` begins an orderly shutdown; freezes completely — zero log entries of any kind (not just Docker) between `01:15:43` and `01:24:51`, coinciding exactly with the shutdown reaching `Stopping Docker Application Container Engine...` (which has to gracefully close `opensearch`'s 472.8GB index under the unbounded-memory condition above).
  - `01:20:17 UTC` — `StopInstances` (`i-0d38e3a088f7c4893`, console, `skipOsShutdown: true`) — a force-stop, ~4.5 min after the freeze.
  - `01:24:39 UTC` — `StartInstances` succeeds (`previousState: stopped`), matching the new boot's `01:24:51` kernel line.
  - Total freeze-to-reboot: **~9 minutes** — corrects a prior claim in GITIN-1827's record of "hung more than an hour," which CloudTrail does not support. No `RebootInstances` event exists — recovery was a force-stop/start cycle, not a reboot API call.
- **Fix applied and confirmed (2026-08-13).** `config/graylog-compose.fixed.yml` content copied over the live `graylog-compose.yml`, containers recreated (`docker compose up -d opensearch mongo`). Verified at both levels: `docker compose config` resolves `mem_limit: 4294967296` (mongo, 4GB), `mem_limit: 6442450944`/`mem_reservation: 4294967296` (opensearch, 6GB/4GB), `ulimits.memlock: -1/-1`; and the *running* container confirms it via `docker inspect opensearch --format '{{.HostConfig.Memory}}'` → `6442450944` (not `0`/unlimited). OpenSearch now has a real Docker-enforced memory ceiling and a working memory lock.

- **Related field found (2026-08-13):** `msg_rest_status_code`, same index (`aws_logs_51`), same mechanism, receiving `"unknown"` this time instead of `"error"` — likely the same underlying source as `msg_rest_status` (a `_code`-suffixed sibling field), or a closely related call site.

  - `msg_rest_status_code` = `"unknown"`: confirmed at 7 call sites, both services — `platformsService/api/src/platforms/provider/aws.js:174,184,325,342`, `api/src/utils/tokensCloud.js:78`, `api/src/controllers/uberEats.js:76`; `concentradorService/api/src/controllers/branch.js` (8 sites: 5228,5268,5288,5301,5314,5327,5352,5402,5407). All `status_code: error.statusCode ?? 'unknown'` or `error?.response?.status ?? 'unknown'` inside `Log.saveError`, triggered when an outbound call fails with no usable HTTP status (network error/timeout/DNS failure).
  - `msg_rest_status` = `"error"`: confirmed at exactly one call site — `concentradorService/api/src/utils/httpClient.js:35`, the shared axios response-error interceptor: `status: error.response?.status ?? 'error'`. Repo-wide grep for `?? 'error'`/`?? "error"` across both services confirms this is the only such fallback — the field name is shared with other (unaffected) call sites like the PedidosYa example above, but the string-sentinel defect itself is isolated to this one site.
  - Same underlying defect as `msg_branch_id`: `log.js` only filters `undefined`, never sentinel strings, before emitting a field.
- **Confirmed still actively ongoing on 2026-08-14** — a fresh sample of 10 `msg_rest_status`/`"error"` indexer failures on `aws_logs_51`, spanning roughly the 8 hours before this check (overnight `2026-08-13`→`2026-08-14`), consistent with `httpClient.js:35` not yet being fixed. ## Confirmed facts — `msg_rest_platformId` (2026-08-15, new field, same defect class)

- User-pasted Graylog indexer-failure list (2026-08-15) showed two things: (1) 5 more `msg_branch_id: "unknown"` failures on `sp_platform__52` — confirms H1 is still active, `(Dev)` fix on `log.js` still not applied; (2) a field not yet documented in this investigation, `msg_rest_platformId`, failing on `aws_logs_52` with value `a24d12527267ecfd0b946390` (24-hex-char string — Mongo `ObjectId` shape) instead of a number.
- **Correction (2026-08-15) — initial source attribution was wrong, corrected before propagating further.** First pass identified `platformsService/api/src/platforms/management/platform.js:565-573` (`getBranchPlatform`) as the source, based on a source-code grep match alone, and that was written into `ops.md` (H8) without first checking stream routing. Running the H7-style stream-routing diagnostic (finally executed, see below) proved this wrong: the failing document could only have reached `aws_logs_52` by matching `SP_Concentrador` — the *only* stream connected to the `AWS_Logs` index set — whose sole rule requires `ServiceName == "ConcentradorService"` exactly. `platform.js:572` lives in `platforms-service`, which cannot produce that tag. `ops.md` (H8) has been corrected in place; see below for the real source.
- **Root cause confirmed via source (`concentrador-service`, same read-only-clone pattern).** `api/src/controllers/branch.js:2819-2851`, function `sendClosedToPlatformsAfterRejectClosed(branchId)`:
  ```js
  async function sendClosedToPlatformsAfterRejectClosed(branchId) {
    try {
      const branch = await model.findOne({ branchId: branchId }).populate('chain');
      if (!branch) return;
      const activePlatforms = branch.platforms?.filter(p => p.isActive) || [];
      await Promise.allSettled(activePlatforms.map(async (platform) => {
        const platformId = platform.platform?.toString();
        try {
          // ... dispatch to closeBranchPeya/Rappi/Uber/PediGrido/MercadoPago by platformId
        } catch (error) {
          Log.saveError(error, {
            message: `Error cerrando branch ${branchId} en plataforma ${platformId}`,
            branchId: branchId,
            platformId: platformId
          });
        }
      }));
    } catch (error) { /* ... */ }
  }
  ```
  When one of the per-platform `closeBranch*` calls throws inside the `Promise.allSettled` map, the inner `catch` logs both `branchId` and `platformId` under **camelCase** keys. `concentradorService/api/src/utils/log.js`'s `_stdout` only destructures `branch_id`/`platform_id` (snake_case) by name — neither camelCase key matches, so **both** fall into the `rest: {...}` catch-all (same mechanism as H3), flattened by Graylog to `msg_rest_branchId` **and** `msg_rest_platformId`. `platformId` here is `platform.platform?.toString()` — already a string (Mongo `ObjectId.toString()`), matching the observed 24-hex-char value exactly. `msg_rest_branchId` hasn't been observed failing yet but is exposed to the exact same risk and is worth watching.
  - Same underlying gap in `log.js` as `msg_branch_id`/`msg_rest_status`: no sentinel/type filtering on `rest: {...}` contents before emitting. Different trigger shape from the sentinel-fallback cases: this field is *never* numeric when the catch fires (always a real `ObjectId` string), not a missing-value fallback into a normally-numeric field.
- Covered by the existing `(Dev)` action item (row 4/#4 in `ops.md`, generic `log.js` fix for the `rest: {...}` catch-all, **both services' copies**) — no new `(Dev)` action item needed beyond noting `msg_rest_branchId` as an additional at-risk field.
- **Pipeline mitigation added, then corrected (2026-08-15).** A second rule (`GITIN-1854: sanitize msg_rest_platformId ObjectId value` — `has_field("msg_rest_platformId")` → `set_field("msg_rest_platformId_raw", to_string(...))` + `remove_field("msg_rest_platformId")`) was first added as **Stage 1** of the existing `SP_Concentrador`-connected pipeline, behind **Stage 0**'s `msg_rest_status` rule. Caught before deploying further: Graylog only advances a message to the next stage if it satisfied at least one rule in the current stage — `msg_rest_platformId` failures don't set `msg_rest_status` (different call site, `sendClosedToPlatformsAfterRejectClosed` vs `httpClient.js:35`), so they'd never have satisfied Stage 0 and would never have reached Stage 1's sanitization at all. Fixed by consolidating both rules into a single **Stage 0** (`match either`) via the pipeline's raw source editor — confirmed via the UI afterward: "Stage 0, Contains 2 rules, no further stages," both rules now evaluated independently per message. **Not yet validated in the Simulator or against live traffic** — same confirmation gap as H7 originally had; do that before considering this closed.
- **Resolves the H7 diagnostic gap, with a caveat.** `SP_Concentrador` is confirmed (not inferred) to be the only stream feeding `AWS_Logs`, so the mitigation pipeline for `msg_rest_status` (H7) was attached to the right stream after all. **Open question this raises:** H3 confirmed call sites for `msg_rest_status_code` in `platformsService/aws.js`, `tokensCloud.js`, `uberEats.js` — all `platforms-service` files — as present in `aws_logs_51`. If `SP_Concentrador`'s `ServiceName == "ConcentradorService"` rule is truly the only path into `AWS_Logs`, `platforms-service`-authored log lines shouldn't be able to reach it. Not yet reconciled: either `ServiceName` is an infrastructure-level tag (e.g. shared CloudWatch log group/ECS service name) applied uniformly regardless of which service's code actually ran, rather than derived from the app's own `SERVICE_NAME` env var — or H3's file attribution has the same unverified-routing gap this section just corrected. Needs a direct check: pull one raw `aws_logs_52` message confirmed to originate from `platforms-service` code and inspect its actual `ServiceName` field value.

## Current working theory

N/A — converged on both independent findings above. `msg_branch_id`: any error-logging call site across `platforms-service`'s order-strategy/SQS-provider code that hasn't yet resolved a branch ID falls back to the string `'unknown'`, which `log.js` doesn't filter before emitting `branch_id` — OpenSearch rejects the whole document since `msg_branch_id` is mapped `long`. This is a document-loss bug, not just cosmetic — it specifically hits the error-path observability that matters most (branch-lookup failures, early strategy errors are exactly what gets silently dropped). ## Confirmed facts — `graylog_299` rotation/retention config (2026-08-14)

- Fetched `GET /api/system/indices/index_sets` for all index sets on this cluster. Confirms the Default index set (`index_prefix: graylog`, where `graylog_299` lives) and `AWS_WAFV2` (`index_prefix: aws_wafv2_`) are fully independent — separate `rotation_strategy`/`retention_strategy`, each scoped only to indices matching its own prefix. A user-initiated change to `AWS_WAFV2`'s rotation strategy (size-based → `TimeBasedRotationStrategyConfig`, `P60D`) cannot affect `graylog_` indices — no shared code path for rotation/retention between index sets.
- **This upgrades the previous "likely related" language to confirmed:** Default index set's `rotation_strategy` is `SizeBasedRotationStrategyConfig`, `max_size: 4473741824` bytes (≈4.17 GiB per index). `graylog_299` is 472.8GB — ~113x its own configured rotation threshold, directly confirming rotation has been blocked (consistent with the known `index.mapping.total_fields.limit` issue preventing a new `graylog_300` from being created).
- **New risk identified, not yet acted on:** Default index set's `retention_strategy` is `DeletionRetentionStrategyConfig`, `max_number_of_indices: 36` — a hard delete (not close/archive) once the `graylog_` series exceeds 36 indices. Once the field-limit fix unblocks rotation, `graylog_299` will likely rotate rapidly to catch up on ~113 rotations' worth of backlog; if that burst pushes the series past 36 total indices, Graylog deletes the oldest ones immediately. Needs deliberate sequencing (e.g. temporarily raising `max_number_of_indices`, or throttling the catch-up) rather than just lifting the field limit and letting rotation run unattended.
- Other index sets' retention for reference: `AWS_Logs` (`aws_logs`) — `PT12H` rotation, 720 max indices (~360 days); `AWS_WAFV2` (`aws_wafv2_`) — now `P60D` rotation, 100 max indices (~16.4 years, effectively unbounded by rotation cadence); `SP_Platform` (`sp_platform_`) — `PT12H` rotation, 1440 max indices (~720 days); `SML_MobileApp`/`SML_WebService` — `P2M` rotation, 12/6 max indices respectively; `Graylog Events`/`Graylog System Events` — Graylog's own internal indices, unrelated to application traffic.

## Disk emergency — root cause confirmed, resolved via deletion (2026-08-15)

**Trigger:** Graylog alert "Elasticsearch nodes disk usage above low watermark" on node `172.21.0.2` — confirmed via `_cat/allocation` at **89%** used (174.9GB free of 1.6TB), between OpenSearch's default low (85%) and high (90%) watermarks, with flood-stage (95%, forces every index with a shard on this node read-only cluster-wide — SmartPedidos + SmartLoyalty ingestion outage) only ~96GB away.

**Root cause, fully confirmed via `_cat/indices/graylog_*` sorted by creation date:** the `graylog_` series had **exactly 36 indices** (`graylog_264` through `graylog_299`) — sitting precisely at the Default index set's `max_number_of_indices: 36` retention cap. `graylog_264`–`graylog_298` each covered roughly half a day to a day of data (~3–4GB each, confirming normal rotation worked correctly through 2026-01-31). `graylog_299` (created 2026-01-31) never rotated again after that — six-plus months as the sole write target, growing to **477.6GB** (confirmed via `_cat/indices` sorted by size, nearly 30% of total disk, ~3x the next-largest index on the cluster) — consistent with the already-documented field-mapping-limit block, compounded by the message-duplication issue (4 streams double-indexing into Default Stream, only fixed 2026-08-14).

**Key realization that changed the remediation plan:** raising `index.mapping.total_fields.limit` (the fix already drafted in this file) would only let a *new* `graylog_300` start — it would **not** shrink or free `graylog_299` itself, and the previously-assumed "retention will clean this up" theory doesn't hold at the needed timescale: with the series already at the 36-index cap, `graylog_299` would only get deleted by retention once it aged out to position 36, roughly 3–5 weeks out at the historical rotation cadence. That's too slow against a ~96GB flood-stage margin at current growth.

**Remediation executed (2026-08-15), by explicit user decision given the immediate risk:**
1. Deleted `graylog_299` directly (`DELETE http://localhost:9200/graylog_299`, confirmed `{"acknowledged":true}`) — freed 477.6GB, disk usage dropped 89% → 61%. A real, unknown-but-likely-significant fraction of this index's content was duplicate data from the 4 streams that were mis-configured until 2026-08-14 (not purely unique history).
2. Deleted the entire remaining series, `graylog_264` through `graylog_298` (35 indices, ~120GB combined), as a follow-up cleanup once the immediate crisis was resolved — user's stated reasoning: same duplication concern likely applies across this window too. Not independently spot-checked for duplication ratio the way `graylog_299` was (via a real `_id` cross-reference) — done on the user's explicit call given the by-then-non-urgent, discretionary nature of this second batch, not an emergency action.
3. Final state confirmed via `_cat/allocation`: **54%** disk usage, 774.5GB free — comfortably clear of both watermarks. Only `graylog_0` (526.8KB, an old legacy artifact far outside the recent rotation numbering) remains in the `graylog_*` series.

**Net effect:** the field-mapping-limit fix (still drafted, not yet applied) is now lower-urgency — the disk emergency that made its retention-sequencing risk moot is resolved, but the underlying rotation-block bug on any *future* Default Stream index still needs fixing, or this will recur. The retention-sequencing concern itself (§ below, now historical) no longer applies to the deleted series, but would still apply the next time a `graylog_*` index gets stuck and the 36-index cap is approached again.

## Deflector broken by the disk-emergency deletion, then fixed (2026-08-15, same day)

**Self-inflicted follow-on problem from the disk-emergency remediation above.** Deleting `graylog_299` directly via OpenSearch's raw `DELETE` API (not through Graylog's own index-management) left Graylog's `graylog_deflector` alias — which always points at the current Default Stream write index — dangling, pointing at a now-nonexistent index. Confirmed via indexer failures (`index_not_found_exception, reason=no such index [graylog_deflector]`) and directly via `GET localhost:9200/_alias/graylog_deflector`. Every new message destined for Default Stream failed to write during this window.

Graylog appears to have self-healed the alias by pointing it at *some* existing `graylog_*` index it could find — `graylog_0`, an old legacy artifact (526.8KB, pre-dating the 264–299 rotation series) with stale/incompatible field mappings — rather than creating a fresh one. This caused a new wave of `mapper_parsing_exception` errors (`mapper [sc-status] cannot be changed from type [keyword] to [long]`) on top of the original deflector break.

**Fix:** Graylog's own REST API for forcing a proper index cycle — `POST /api/system/deflector/{indexSetId}/cycle` (not `/rotate`, which 404s; confirmed via [Graylog Community](https://community.graylog.org/t/how-to-rotate-the-active-write-index-with-rest-calls/10941)) — run against the Default index set (`id: 6638e8f72709b461a38b617b`). This correctly created a genuinely new index (`graylog_1`) and repointed the deflector alias to it. Confirmed resolved: `graylog_1` grew from 0 → 531 → 1003 documents within minutes of the cycle, confirming real ingestion flowing into a clean index with no stale mapping conflicts.

**Lesson for any future manual index deletion on a Graylog-managed cluster:** never delete a Graylog-managed index directly via OpenSearch's raw API if it might be (or become) the active write index for its index set — this breaks the `<prefix>_deflector` alias, which OpenSearch/Graylog integration doesn't self-heal correctly (it points at whatever old index it can find, not a fresh one). If deleting the *current* write index is unavoidable, immediately follow up with Graylog's own cycle endpoint (`POST /api/system/deflector/{indexSetId}/cycle`) to force a clean rotation — don't assume deletion alone is sufficient. The 35 other indices deleted in this same incident (`graylog_264`–`graylog_298`) were all *closed/inactive* (not the current write target), so they didn't trigger this — only deleting the active write index (`graylog_299`) did.

## `msg_rest_status` Graylog-side mitigation applied (2026-08-15)

**Trigger:** with the disk emergency resolved and the deflector fixed, fresh `msg_rest_status` indexer failures kept appearing on `aws_logs_52` — same mechanism as before (§ above), still traced to `concentradorService/httpClient.js:35`. Since the `(Dev)` fix isn't applied yet, decided to mitigate the symptom (document rejection) directly in Graylog rather than wait.

**Mechanism:** a Graylog Pipeline Rule, `GITIN-1854: sanitize msg_rest_status literal 'error' value`:
```
rule "GITIN-1854: sanitize msg_rest_status literal 'error' value"
when
  to_string($message.msg_rest_status) == "error"
then
  set_field("msg_rest_status_raw", "error");
  remove_field("msg_rest_status");
end
```
When `msg_rest_status` arrives as the literal string `"error"`, the rule moves it to a new string field `msg_rest_status_raw` and removes the original — avoiding the `mapper_parsing_exception` that otherwise rejects the whole document, while still preserving the fact that the request errored. Messages with a normal numeric `msg_rest_status` (the healthy case) are untouched.

**Stream targeting:** placed in a new pipeline (`GITIN-1854 msg_rest_status sanitization`, single stage) connected to `SP_Concentrador` — the stream that actually carries `concentradorService` traffic and matches the confirmed source (`httpClient.js:35`), not the Default Stream.

**Validation status:** confirmed working in the Graylog Pipelines Simulator against a synthetic message with `Stream: SP_Concentrador` selected — `msg_rest_status_raw: "error"` added, `msg_rest_status` removed, no other fields affected. A first simulator attempt produced no change because the Stream dropdown was left at "Default Stream" instead of `SP_Concentrador`; corrected and re-run successfully. **Not yet confirmed against real live traffic** — since failed documents are never actually indexed, there is no way to look one up after the fact; confirmation requires either a fresh real `msg_rest_status: "error"` occurrence indexing successfully post-fix, or a live doc-count/`_exists_` check once one occurs.

**Scope note:** this is a Graylog-side mitigation, not a fix — `concentradorService/httpClient.js:35` still sends the string `"error"` instead of a real status or `null`. The `(Dev)` fix (§ "Open questions / next steps" below) remains the actual root-cause remediation; this rule only prevents document loss in the meantime, and only for this exact field/value/stream combination — it would need to be replicated for `msg_rest_status_code` (`"unknown"`, still unmitigated) if the same urgency applies there.

**Live-traffic check (2026-08-15) — mitigation not yet confirmed effective, root cause of the gap under investigation.** Fresh `msg_rest_status`/`"error"` indexer failures on `aws_logs_52` (10 new letter IDs, timestamps within the hour after the pipeline was connected) show the exact case the rule targets still reaching OpenSearch unmodified. A document the pipeline successfully rewrites before indexing should never surface as an indexer failure — so either the rule hasn't taken effect on live traffic yet, or (more likely, on reflection) the `SP_Concentrador` stream the pipeline is attached to was never independently confirmed to be what actually routes this traffic into the `AWS_Logs` index set. That routing assumption was inferred from the source-code match (`httpClient.js:35`) alone, not verified against Graylog's own stream rules — the same class of gap flagged elsewhere in this repo's "always validate claims" guidance, now recurring specifically for stream-routing assumptions. Diagnostic plan, not yet run: (1) check for any recent `aws_logs_52` message with `msg_rest_status_raw` populated, to confirm/rule out the rule firing at all; (2) fetch `SP_Concentrador`'s own stream rules (`GET /api/streams/68f25930450228030911b8c1/rules`) and check whether they actually match `aws_logs_52`-sourced messages. If they don't, the pipeline needs to move to whichever stream really carries this traffic.
