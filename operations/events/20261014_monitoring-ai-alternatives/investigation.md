## Point raised by the user: the tools' APIs plus the codebase, in one agent
- Statement (user, 2026-10-14): for Zabbix, Graylog and Grafana the existence of APIs that an AI can consume is very valuable, and one agent can combine all that information with the codebase.
- What the work of this month shows about the combination (from this repo's own events, not a benchmark): GITIN-2221 derived the `NormalizedPath` table from the SmartFran.Cloud controllers' routes and applied it to the live Logstash config, checking results in Graylog; GITIN-2218/2209 used Graylog's API, the dashboard definition and per-day counts; GITIN-2220 joined the SmartPedidos Graylog measurements, the SmartCloud Graylog counts and the Platform source; GITIN-2223 joined service config files, Unity registrations, connection strings across environments and `Sch.Task` SQL. A vendor AI sees only the data it ingests; none of the vendor products compared here was shown to read this repo's code, the live Logstash config or the per-environment config files (not checked for each).
- Conditions for the combination to work (observations, not tested as a design): read-only credentials per tool (the Zabbix API token the 8.0 MCP server uses is scoped to its owner; Graylog and Grafana tokens, AWS/Azure CLI roles); masking before anything is stored or shown (on 2026-10-14 a masking bug let a real database credential reach an output file, see the GITIN-2223 investigation; any agent reading raw configs and APIs needs the masking tested first); the context kept in the `investigation.md`/docs files; and a trigger if the goal is unattended operation.
- Limits seen in the same events: today the loop is manual (commands run by the user, results pasted back, several "ran it" rounds per question); nothing runs outside working hours; token cost was not measured; the quality of the answers depends on what the tools collect (gaps found: fields not promoted in Graylog, Insights not onboarded, Azure resource logs not confirmed in Graylog).
- Net for the evaluation: the cheapest candidate is a single agent over the existing APIs and repos; the vendor AI products add unattended, alert-triggered investigation and vendor support. Not decided; depends on whether unattended operation is required.

## This setup (bots + the tools' APIs + the repos) vs an AI monitoring product (discussion, 2026-10-14)
- Question (user): is this project, with its integrations, better than an AI Datadog plus other apps? No benchmark exists; the assessment rests on what the sessions of 2026-10-13/14 showed, and the assistant doing the assessment is the thing assessed.
- Stronger here: depth across layers (GITIN-2223 needed service config files, Unity registrations, connection strings compared across environments, `Sch.Task`/`Etl` tables and TEST02 as a reference; none of the vendor products was shown to read these, not verified for each); the user's own code and context (GITIN-2221 from the controllers' routes, GITIN-2224 from the TaskOperator source; the investigation files and docs carry context between sessions); cost (no per-host or per-GB price); evidence discipline (every claim points to a saved output; nothing runs without the user).
- Weaker here: detection (the ETL job failed 445 of 445 runs over about 21 months with no alert; neither this setup nor an AI layer detects without a monitor); speed (GITIN-2223 took many copy-paste rounds); nothing runs unattended and the knowledge depends on one person's sessions; no dashboards, retention, access control or vendor support; and errors made in the same sessions: a masking regex that let a database credential reach an output file, two scripts with defects (a SQL type clash and escaped quotes in PowerShell), and a note saying a script had been rewritten before it was written. A fixed collector has fewer of these failure modes but reads data without the user's review.
- Reading: the two are not substitutes. Investigation and diagnosis: this setup is strong and cheap. Continuous detection, alerting and unattended triage: it does not substitute; either a vendor AI or alerts built in Zabbix/Graylog are needed. The largest gains seen in GITIN-2223 were basic observability (a monitor on `Sch.Task`, a startup configuration check, logs with the reason for each task failure: GITIN-2224), not AI.
- Suggested order (not decided): keep this setup for investigations; add cheap detection first (alerts on overdue and repeatedly failing tasks); pilot one vendor agent (for example the Azure SRE Agent) only if alert-triggered investigation outside working hours is wanted.

## Acting on systems: which agents can, and the guardrails (user points, 2026-10-14)
- User point: the vendor agents would not act against the AWS CLI, Azure CLI or Auth0 CLI, so this setup needs checks and validation (hooks). Partly right: the Azure SRE Agent can act on Azure resources (Microsoft's billing page has a "diagnose and fix the failing deployment" scenario and mentions the agent waiting for approval); the actions of Datadog's agent were not checked; none of those agents covers AWS, Auth0, SQL on the user's hosts or Logstash. Reach is also the risk; today the repo avoids it by never executing: the user runs every command.
- Existing guardrails (read from `.claude/`): one `PreToolUse` hook on `Bash`, `block-noop-commands.sh`, which only blocks placeholder `echo`/`true` calls; `settings.local.json` has a few loose allow rules (for example `Bash(git checkout *)` and an `rm -rf` on one specific folder); nothing guards mutating cloud CLI calls.
- Proposed, in order of value (nothing built or installed): (1) read-only credentials for anything an agent can run (Reader role in Azure, read-only IAM role in AWS, read-only Auth0 scopes, a `db_datareader` SQL login), with mutation credentials kept out of the agent's environment: this is the real boundary, because hooks match command text and an obfuscated command or a script that calls the CLI inside gets past them; (2) a `PreToolUse` hook on `Bash` that lets `list`/`show`/`get`/`describe` pass and asks or blocks on `delete`/`update`/`create`/`put`, `curl -X POST|PUT|DELETE` and SQL `UPDATE`/`DELETE`, inspecting the contents of scripts and the `APPLY=1` flag (this repo runs `bash scripts.sh` and `APPLY=1 python3 widgets_*.py`); (3) a hook that denies a `Write`/`Edit` under `events/` whose content has secret patterns (`Password=`, `SharedAccessKey=`, `AccountKey=`, private-key headers); (4) a masking test: fixtures run against the masking function before a script is handed to the user.
- Gap hooks cannot close: the credential leak of 2026-10-14 came from a script written for the user to run, and hooks see only the assistant's own tool calls; only (4) would have caught it. Whether a hook can rewrite a tool's output before the assistant reads it was not verified.

## Databases: the agent never executes, every command is reviewed (user, 2026-10-14)
- Constraint (user): commands are not run against databases by the agent; each command must be reviewed by a person. This matches the current practice (SQL is handed as copy-paste and run by the user) and excludes an "agent runs it" option for databases.
- What that changes for hooks: they enforce the rule instead of enabling execution: a `PreToolUse` hook on `Bash` that denies any database client (`sqlcmd`, `mongosh`, `psql`, `mysql`) and scripts importing a driver (for example `pyodbc`), with no "ask" path.
- Aids to the person who reviews (proposed, not built): a header on every SQL file (`READ-ONLY` or `STATE-CHANGING`, target database, what it should return or change; the banner on state-changing ones); a linter run before a file is handed over (flags `UPDATE`/`DELETE`/`INSERT`/`MERGE`/`DROP`/`ALTER`/`TRUNCATE`/`EXEC`/`xp_cmdshell`, an `UPDATE`/`DELETE` without `WHERE`, a missing `USE`, a read-only file containing any of those, and column types that do not match what earlier outputs showed: it would have caught `Done = 0` against a `datetimeoffset` column in GITIN-2223); a preview pattern for changes (`SET XACT_ABORT ON; BEGIN TRAN; <update>; SELECT the affected rows; ROLLBACK;` in one batch so nothing stays open, then the real change as a separate autocommit batch, given the open-transaction problem of GITIN-2223). A linter finds patterns, not intent: the person's review remains the control.

## Draft guard hooks (2026-10-14, `outputs/hooks-draft/`; drafted, tested locally, not installed)
- Files: `guard_mutating_cli.py` (PreToolUse on `Bash`), `guard_secrets_in_writes.py` (PreToolUse on `Write|Edit|MultiEdit`, and on `Bash` when the command writes into `events/`, `docs/`, `CLAUDE.md` or `.claude/`), `banner_guard.py` (`Stop`), `settings-snippet.json` (how they would be registered, not applied) and `test_hooks.py` (81 cases, all pass).
- `guard_mutating_cli.py`: denies database clients (`sqlcmd`, `mongosh`, `psql`, `mysql`, ...), remote shells (`ssh`, `scp`, `rsync`), `az`/`aws`/`auth0` calls with a mutating verb or write method, HTTP requests with `POST`/`PUT`/`PATCH`/`DELETE` or a body, git state changes (`add`, `commit`, `push`, `reset`, ...; `pull` stays allowed, matching the clone rule), service control, `docker`/`kubectl`/`terraform` writes, and any command with `APPLY=1`. It asks first for `git checkout|restore|switch|stash` and for `rm` outside `/tmp`. It scans scripts and inline/heredoc code for the same things (python code through the AST, so a string that only mentions a tool does not trigger; a script with an `APPLY` dry-run gate is allowed unless the command has `APPLY=1`). Limits: it reads command text only; obfuscation passes; the real boundary remains read-only credentials.
- `guard_secrets_in_writes.py`: denies content that looks like a real secret (password values in connection strings or JSON, Event Hub keys, private-key blocks, AWS key ids, JWTs, GitHub/Slack tokens, authorization headers, API-key assignments) and names only the pattern class, never the value; `***`, `<...>`, `$VAR` pass. It does not see what the user pastes or what is written in a script handed to the user.
- `banner_guard.py` (Stop hook): reads the last assistant turn from the transcript; if a code block holds a write command (SQL DML/DDL, mutating `az`/`aws`/`auth0`, mutating cmdlets, `APPLY=1` or `-Mode apply`, service control, HTTP writes, git state changes) and the block right before it is not the state-changing banner, it blocks the stop and asks for the banner. Limit: the original message was already shown, so it forces an immediate correction rather than holding the message back; it is pattern based.
- Calibration against this session's own transcript (read-only): the banner guard would have flagged 1 of 137 turns with code blocks (30 of them carried a banner): the `APPLY=1 ... migrate_event_layout.py undo` command handed over without a banner, a true miss. The CLI guard over 634 `Bash` calls gave 633 allowed and 3 `ask` (all `rm` of a non-`/tmp` file) and no deny, after fixing four false positives found this way (the string `APPLY=1` inside file text, `bash -n`, prose mentioning tools inside python heredocs, and documentation of the masking pattern tripping the secret scan). The secrets guard over the `Write`/`Edit` calls blocked none after the last fix. These numbers describe this session only.
- Not verified: that Claude Code accepts `permissionDecision: "ask"` and `decision: "block"` in exactly these JSON shapes (written from memory of the hook interface, not tested in a live session); that hooks run when Claude is launched from a sub-project; how a hook interacts with the classifier and permission prompts already in place.
- Next (not done): install by copying the three scripts to `.claude/hooks/` and merging `settings-snippet.json`; test live with harmless commands first (`git add` in a scratch directory, a write of a fake secret to `/tmp`, a reply with an unbannered `UPDATE`); decide whether `ask` should stay `ask` or become `deny`.
