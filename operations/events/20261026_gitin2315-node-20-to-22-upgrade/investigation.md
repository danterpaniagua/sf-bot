## Why 22.23.4
- The 2026-10-21 Node.js security release fixed v22.23.4, v24.22.1 and v26.12.1 (10 CVEs, 4 High). Line 22 is affected by 7 of them. Node 20 is end of life and the advisory says EOL lines "are always affected" with no fix. 22.23.4 is the first target on line 22 with the fixes. GITIN-2310's email proposed 24.22.1; the choice of line 22 here is the user's.
- Production is deployed from `develop` (user-reported in GITIN-2310, not independently checked); the Node version inside the running container was not checked.

## Decisions and findings
- **npm version:** npm 12.2.1 chosen by the user for both stages. It bundles the same fixed copies as 11.21.1; it needs Node `^22.22.2 || ^24.15.0 || >=26` (22.23.4 satisfies it) so a Node 20 rollback image cannot use it. Risks not tested: npm 12 blocks dependency install scripts by default (candidates: `core-js`, native or binary devDependencies); unknown flags throw (the `only` flag still exists). The final-stage install ran on npm 12 and produced the image.
- **undici in npm (CVE-2026-109869):** `undici@6.29.1` exists; no npm release bundles it yet (newest are 11.21.1 and 12.2.1, 2026-10-15). The user withdrew the Dockerfile step that overwrote npm's bundled copy ("not clean"). Status: accept and document; clears when npm ships a release with 6.29.1 or later. `undici@8` needs Node >=22.19 and is outside `node-gyp`'s `^6.25.0` range: not pursued. The bundled copies belong to npm's `node-gyp`, `minimatch` and `make-fetch-happen`, not to the service (my reading from the tarballs; whether the service ever calls them was not checked).
- **body-parser (CVE-2026-111181, fixed 1.20.9, published 2026-10-22):** resolves to 1.20.9 on a fresh install even with `^1.18.3`; the 1.20.8 in a Jenkins Trivy list points to a cached `npm install` layer or an earlier build (not checked on the agent); that list also matched the old npm 11.20.0 bundle and had no `express-jwt` 5 / `jsonwebtoken` 8, which fits concentradorService as it is on `develop` (job not stated).
- **Service dependencies still flagged:** `express-jwt` 5.3.3 -> 6.0.0 and `jsonwebtoken` 8.5.1 -> 9.0.0 are major bumps that need their own code review; `lodash.set` has no fix. Not decided.
- **AWS credentials for local runs:** the code never read a `CREDENTIALS` key; `SQSClient` and `SSMClient` used only the region (default provider chain: env vars, shared profile, ECS task role). `aws.js` now takes `AWS_ID`/`AWS_SECRET` from `config.AWS.SQS.CREDENTIALS` or `config.AWS.CREDENTIALS` when present and otherwise changes nothing (the other env files define none). Local test arrangement only; both consumers already pass `sqs: this.sqsClient`; syntax and `sqs-consumer` behaviour with a supplied client not verified by running.
- **Secrets in the repo:** `staging.js` (tracked) already holds hardcoded values for the JWT secret, Peya and Cloud client secrets, a SendGrid key and the staging MongoDB password (names only), and the user's uncommitted change adds an AWS key block. Any image built from this tree carries them in its config layer: never push such an image. Run output of the service can include request bodies (the PedidosYa token call printed a user name and password); every saved run file was masked with `sed -i` and re-running over the same file name undoes the masking.
- Observation outside the ticket: stage 1 of the Dockerfile downloads a certificate chain from `bot-security.smartfran.com` with `openssl s_client` and installs it in the final image; not analysed. `sf-devops/jenkins/SF-PEDIDOS/README.md` embeds SonarQube badge tokens (values not copied); worth a separate check.

## Jenkins `ope/platform` did not start from the push (read from `sf-devops` `main` `34a244a`, not from Jenkins)
- The pipeline `jenkins/SF-PEDIDOS/jenkinsfiles/ope/dev-src-pedidos-platform.jenkinsfile` (GITIN-2011) is triggered only by a `GenericTrigger` (no polling), `TARGET_BRANCH = "ope"`, filter `^refs/heads/ope\s*$` or a pull request to `ope`. Its token is the literal placeholder `REPLACE_WITH_NEW_GENERIC_WEBHOOK_TOKEN` ("generate a dedicated token ... before enabling"); the `ope` concentrador file has the same. The three `develop` files each have a different 64-character token (compared by hash prefix only). So a push to `ope` cannot reach this job unless a webhook carries a token the job accepts; the existing per-repo webhook (if the `develop` one) carries the develop token and its filter rejects `ope`.
- The commit `90730a6` (2026-10-26 16:24:50) is on `origin/ope`. Jenkins build #17 (16:25:31) was a manual run by the user; builds #2 (2026-09-28) and #16 (2026-10-07) show the job ran before with the `GenericTrigger` already present. The Generic Webhook Trigger Log and the GitHub webhook list have not been seen.
- Fix steps proposed, none applied: generate a token per `ope` job; set it in the jenkinsfile (plaintext, like `develop`) or in a Jenkins credential if the plugin supports `tokenCredentialId` (unchecked); run the job once; add a GitHub webhook `.../generic-webhook-trigger/invoke?token=<token>` with push and pull request events; read the trigger log after a push. The job builds `api/` of `ope` and scans with Trivy at CRITICAL,HIGH with no exit-code gate; it does not deploy.
