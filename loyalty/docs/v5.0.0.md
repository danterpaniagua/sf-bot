# Skill Reference: Fraud Detection — v5.0.0

> **Status:** Merged to `main`, 2026-07-30.
> **Change type:** Token-efficiency split + reference extraction — no new investigation capability, same behavior as v4.0.0's `fraud-points` with two pieces moved out.

---

## What changed from v4.0.0

`fraud-points.md` had grown to 6421 words, the largest skill file in the repo, by accreting a fourth workflow (member dispute) that the file itself already flagged as categorically different — single-`CustomerId` scope, no hub/relay memory update, triggered by a member complaint rather than anomaly detection. Every invocation of `fraud-points` for its actual common case (network-wide anomaly investigation) was paying for dispute-only content it never used, and vice versa.

Two changes, both mechanical (no workflow logic changed):

### 1. Member Dispute extracted to `fraud-dispute` (new skill, `.claude/commands/loyalty-fraud-dispute.md`)

Moved out of `fraud-points.md`:
- `Sml.Sale`, `Sml.SaleDetail`, `Sml.SalePromotion`, `Sml.Promotion` table definitions (their only consumer was this workflow)
- "Member dispute (single-account balance reconciliation)" investigation workflow (7 steps)
- Member dispute closure format (`ops.md` section spec)

`fraud-dispute` references back to `fraud-points` for shared material instead of duplicating it: core identity tables (`Person`, `CustomerPointsLog`, `smlst.CustomerPointsLog`), the Points accounting Axis 1/Axis 2 format, and `loyalty/docs/eventtypecode_reference.md` for the full `EventTypeCode` list.

### 2. `EventTypeCode` long tail extracted to `loyalty/docs/eventtypecode_reference.md`

Of the 36 confirmed `EventTypeCode` values, only 12 are `Confirmed` (i.e., actually come up in a typical investigation); the other ~24 are `Named only, not investigated` — pure long-tail reference, needed only on the rare occasion a query returns one of them. `fraud-points.md` now keeps just the 12 Confirmed rows inline and points to the doc for the rest, read via `Read` on demand rather than loaded on every invocation.

This doc lives in `loyalty/docs/`, not `.claude/commands/docs/` — `.claude/commands/` is the `sf-skills` submodule (a separate git repo), and putting project-specific schema data there would couple it to a repo meant to hold portable skill logic. `loyalty/docs/` already holds this kind of reference (`infrastructure.md`), and other skills already reference across this exact boundary (`ope-azure.md` → `operations/docs/...`).

## Retained from v4.0.0

Everything else — `fraud-points`'s transfer fraud / accumulation anomaly / manual assignment exploit workflows, core tables, business rules, Name & Identity Flags, Email Verification, Fraud Patterns, memory integration — unchanged.
