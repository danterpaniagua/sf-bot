### Jenkins controller: Java 21 upgrade (`GITIN-2099`)

Modern Jenkins core requires Java 21+. The box was on Java 17 (`C:\Program Files\Java\jdk-17`); after a routine reboot WinSW looped (`<onfailure action="restart"/>`, no backoff) with `Running with Java 17... older than the minimum required version (Java 21)`. Fix: Eclipse Temurin 21 (`C:\Program Files\Eclipse Adoptium\jdk-21.0.12.101-hotspot\`) installed and `jenkins.xml`'s `<executable>` repointed. Non-obvious consequences of the swap:
1. The Windows Firewall inbound-8443 rule `Jenkins` was scoped to the old `jdk-17\java.exe` path and silently stopped matching (loopback `Test-NetConnection` worked, external did not). Fix with `Set-NetFirewallApplicationFilter` to the new path; do not disable the firewall.
2. Windows caches the system environment (`JAVA_HOME`/`PATH`) at boot: `[Environment]::SetEnvironmentVariable(...,"Machine")` reaches neither running services nor new child processes until a **reboot**, not just a service restart. This hit both the Jenkins service and `SonarScanner.MSBuild.exe`, which resolves `java` through the system `PATH`, independent of `jenkins.xml`.
3. The `sonarqube-srv` agent (host `sfcg-sonarqube`, a **different VM** in the same RG, the SonarQube server itself, `operations/docs/sonarqube_upgrade_runbook.md` § 7bis) failed to reconnect over SSH Remoting with `UnsupportedClassVersionError` (class file 65 = Java 21 vs 61 = Java 17 max): its system `java` default had drifted back to 17 after that host's own Java 21 upgrade (`GITIN-1327`; cause of the drift not investigated). Fixed with `update-alternatives --set java` to the installed Temurin 21 (verified: SonarQube `/api/system/status` `26.9.0.129388` `UP`, no restart); SonarQube itself is unaffected (pinned by `SONAR_JAVA_PATH`). The Temurin MSI URL has to come from the Adoptium API (`api.adoptium.net`): a guessed GitHub `latest/download/<name>` 404s because the file names carry a version suffix.
4. Two pipeline defects found while testing builds after the swap (fixed in `sf-devops`, `origin/main`): every one of the 23 SF-LOYALTY Jenkinsfiles referenced `${LOCAL_GIT_COMMIT_MESSAGE}` in the `post { failure }` block but only defined it in `success` (mutually exclusive conditions), so a failing build crashed its own Google Chat notification with `MissingPropertyException` (SF-PEDIDOS' Jenkinsfiles re-fetch the `LOCAL_GIT_*` variables in each block); and `packProject.ps1` checked for a previous compilation with `Test-Path "<prefix>*.zip"` only, then read the paired `.build` file, which is written after the zip, so a build interrupted between the two (a Jenkins restart) left an orphaned zip and crashed the next run (it now needs both files). Out of scope there: a `GenericTrigger` webhook for the 16 SF-LOYALTY Jenkinsfiles, and the SmartPedidos BackOffice SonarJS "bridge server unresponsive" failure on `sonarqube-srv` (one physical core, no headroom, not root-caused).

## Known gap: no official housekeeping/maintenance window

None of SmartPedidos, SmartLoyalty or SmartCloud has an officially documented maintenance window (`GITIN-1981`). Every scheduling decision (e.g. `PNSSRL_MantenimientoIndices`) is derived from scratch from whatever constraints are known (POS active hours, backups, one service's traffic profile). A cross-platform gap, unresolved.

**Backup schedule (`SFCG-DB01`, `SmartFran.Solution.SmartLoyalty`)**, read from `msdb` on 2026-10-28 (`operations/events/20261027_documentation-compaction/data/`, query `operations/events/20261027_documentation-compaction/scripts/backup-full-schedule.sql`): `Operaciones_MaintenancePlan_Backups.Backup_FULL` is a weekly job (`freq_interval` 41 = Sun + Wed + Fri) at **09:00 GMT** (06:00 UTC-3), all system databases and both user databases; the backups taken 2026-09-30 to 2026-10-28 confirm those days: `SmartFran.Solution.SmartLoyalty` 7-8 min, `PNSSRL` right after it (about 09:08, under 1 min). `Backup_Log` is a daily job (sub-day interval not read). `PNSSRL_MantenimientoIndices` and `..._CustomerPointsLog` run Mon/Tue/Thu/Sat, so they never share a day with the full backup. Every Sunday there is also a second, instantaneous full backup of every database at about 11:31-11:41 GMT (0 min, not from a job named Backup; origin not identified). Avoid write-blocking maintenance (an offline index build) on Sun/Wed/Fri mornings (`loyalty/docs/task_operator_tasks.md` § 4).

## Scheduled tasks (`SFCG-TO-01`)

The exhaustive per-task inventory (schedule, query, `CustomerPointsLog` contention) is `loyalty/docs/task_operator_tasks.md`. Context kept here:

- These tasks run on `SFCG-TO-01`, **not** `SFCG-DB01`: the `Get-ScheduledTask`/`logman` output collected in `GITIN-1749` carried `\\SFCG-TO-01\...` prefixes. Besides the SQL Agent jobs on `SFCG-DB01`, `SFCG-TO-01` runs the Task Scheduler folder `\SmartFran\` with ~50 application jobs. They were found while investigating CPU peaks on `SFCG-DB01` (`events/20260803_cpu_peaks_loadtest/`); the peaks-2/3 root cause is **unconfirmed** and these tasks describe `SFCG-TO-01`'s own activity and the SQL traffic it generates, not an OS-level cause on the DB host.
- **Clustering:** on 2026-08-03 five tasks (`ReportUpdateCustomer`, `ReportErrorSurveyNoResponse`, `NotSamplesSurveyActivated`, `Promotion Vigency Advisor B` and `C`) fired within 12:00-12:30 GMT, overlapping the chronic `CustomerPointsLog` sync job (SPID 114/151, `sfsqlusr`@`SFCG-TO-01`, ~12:06-13:06 GMT), partly by coincidence (only 2 are daily). It contributed to a routine CPU peak at local business-day start (~09:00 UTC-3) seen in two consecutive load-test CPU investigations (`20260727_cpu_peaks_loadtest`, ticket unconfirmed; `GITIN-1749`). `GITIN-1753` (`20260804_reschedule_smartfran_tasks`) closed by **disabling 4 other tasks** (`ReportErrorSurveyNoResponse`, `NotSamplesSurveyActivated`, `ReportSurveyUnsatisfied`, `ReportSampleMailResponseXSurvey`), not by rescheduling those five; `ReportUpdateCustomer` stays at its original 12:00 UTC.
- Local tasks whose script CPU lands on `SFCG-TO-01`, not `SFCG-DB01`: `Check_list_SF` (every 5 min anchored at :00, so on :15/:45), `Clean Mistery` (every 30 min), `RunExportsCustomersFails`, `SendCanjesSocioCortesiaToBlobStorage`/`SendDetalleCanjesSocioCortesiaToBlobStorage` (every 30 min). ## Query hot spots and open code-side fixes on `SFCG-DB01`

- **`Query101-sql.xml` (WebServiceV2, once per sale; `GITIN-2074`, recurrence of `GITIN-1267`; `events/20260920_cpu-spikes/`):** filters `SmlSt.CustomerAdditionalInformation` (~4.9 M rows, no index on `CardNumber`/`UidCode`/`UidSerie`) with `OR`, `LOWER()` and a `TRY_CAST` in the join with `Article`: a clustered-index scan per sale (104,970 logical reads; 84.7 % of the CPU of queries touching that table; 91,704 ms in the window). Two nonclustered indexes created 2026-09-21 did nothing alone (still 104,970 reads); the rewrite `OR` → `UNION` without `LOWER()` brings it to 4-8 reads (average CPU 3,315 ms → 0.26 ms on real traffic). **The rewrite runs in production as a manual edit on both `SFCG-WSV2-01` and `-02` and was not in any branch of the repository**, so the next normal deployment would silently revert it (open at the ticket's last read; check the repository before deploying WebServiceV2). Structural fix suggested: a `FavoriteProductId INT` column with a foreign key to `Article.Id` to drop the `TRY_CAST`.
- **SQL Server 2022 Standard has no `WITH (ONLINE = ON)` (`Msg 1712`):** an index build on a big table is offline and blocks writes for its whole duration. Partitioning `SmlSt.CustomerAdditionalInformation` (hash of `CustomerId`, N=16, shadow table + double-write triggers) was fully designed and **not executed** (`GITIN-2077`, 2026-09-22): maintenance costs ~3.5 min/day, no blocking incident ever, one row per customer, high execution risk on a checkout hot path with no non-production environment. Revisit if its maintenance time exceeds ~15-20 min (`PNSSRL_DetallesEjecucionTablasModulos`, `id_tablas_modulos=479`). The new indexes need no maintenance change: that table is already enabled in `PNSSRL_TablasModulos` and the job lists indexes dynamically (manual run on 2026-09-22 rebuilt both; `GITIN-2078`).

## MobileAppService under Grido traffic: reported 503s and campaign errors (`GITIN-1909`, `GITIN-2053`)

- **"503" from Grido's load test is a transport reset, not an HTTP 503** ([GITIN-1909](https://smartit-ar.atlassian.net/browse/GITIN-1909), 2026-08-21, `events/20260821_mobileappservice_loadtest_503/`): the site has **`connectionTimeout=15s`** (identical on MOBI-01/02, against IIS' default 120 s), a deliberate hardening against idle-connection exhaustion, not a misconfiguration. A pooled HTTP client that reuses a connection IIS closed after 15 s idle gets "Unable to read data from the transport connection: An existing connection was forcibly closed by the remote host", and Grido's tool reports it as 503; IIS never sends a response, so Graylog shows nothing. `httperr.log` shows the closures as `Timer_ConnectionIdle`; a full scan of MOBI-01's `httperr.log` for 2026-08-21 11:00:00Z-12:06:37Z (969 entries) held **0** `sc-status=503`. Do not re-investigate the 15 s as a defect; the open follow-up is Grido's client retrying on a fresh connection (and which component sits behind `172.191.0.208`, an unverified source says Grido's API Management; see `docs/azure_nsg.md`). The only LB health dip of that window was 12:07-12:08 GMT (`DipAvailability` 56.52 and 62.5, then 100) and `Microsoft-Windows-WAS` showed two WAS restarts on MOBI-02 (event 5211 at 12:06:37 and 12:07:46) and none on MOBI-01 (no pool recycle in 12:04-12:11Z). The 15 s is the IIS `limits.connectionTimeout` (read with `Get-ItemProperty "IIS:\Sites\SmartLoyalty.MobileAppService" -Name limits.connectionTimeout`), **not** the LB rule's `idleTimeoutInMinutes=15` (15 minutes, a different layer: same numeral, different units). `Request_Cancelled` entries in `httperr.log` mean the client disconnected mid-request (a client-side timeout), a different mechanism from `Timer_ConnectionIdle`. The load-test path had handled 800+ requests in earlier tests without the report, consistent with a reuse-timing mechanism and not a capacity limit. **Separate, self-inflicted finding (not the original report):** `SFCG-MOBI-02` was powered on *after* Grido's report; the LB's only live probe is plain TCP 8043 with `numberOfProbes=1`, so port 8043 opened before WAS and the app pool were ready, the LB sent live traffic into the startup gap, and IIS answered **9 real HTTP 503s at 12:07:20-21** (never in Graylog, because ASP.NET never saw the requests) and the second WAS restart reset in-flight connections. The TCP-only probe is known, pre-existing tech debt (user, 2026-08-21), not a finding of GITIN-1909; whether `-02` was started deliberately or unplanned, and whether it recurs on each start, was not established (Activity Log not checked). ## `Sml.CustomerPointsLog`: structure and contention history

- **Structure** (`GITIN-2251`, `GITIN-2108`, `GITIN-2266/2267`): 404,460,588 rows, 16 yearly partitions (`sch_LogDate_Anual`); the **clustered key is `LogDate`**, the primary key `PK_dbo.CustomerPointsLog` is a separate nonclustered unique index on `Id`. Indexes read on 2026-10-19: `IX_CustomerId` (7.4 GB, keyed on `CustomerId`, no included columns), `IX_CustomerPointsLog_SaleId` (17 GB, `CustomerId` and `Points` included: the only one holding both), `IX_CustomerPointsLog_Points` (10 GB: 338 seeks, 0 scans, 1,214,569 updates in 5 days since the service start 2026-10-14; counters reset at each restart, key columns not confirmed from raw `sys.index_columns`, whether it can be dropped is open in `GITIN-2267`). The staging copy `SmlSt.CustomerPointsLog` (5.57 M rows, heap) has an index with the same name that does get reads. - **Contention history** (the same table, three confirmed incidents before the fixes of `GITIN-2060/2061`): 2026-07-23 (`GITIN-1669`, `events/20260723_bloqueo_customerpointslog_loadtest/`): an `ALTER INDEX REBUILD` waited on `LCK_M_SCH_M` behind an abandoned, uncommitted transaction under the login `zabbix` (an SSMS-like session; `KILL`ed), and a MobileAppService load test amplified it; offline rebuilds hold `Sch-M` for their whole duration and show no reliable `percent_complete`. 2026-09-21 (`GITIN-2076`, `events/20260921_customerpointslog-blocking/`): the rebuild itself sat ~4h10m at 0 % waiting for `Sch-M` behind the Etl `CustomerPointsLog` sync (it re-takes schema-stability locks batch after batch, never leaving a gap), and by lock-queue fairness 12 real sessions (MobileAppService, club site, a Zabbix check) queued behind the rebuild; `KILL` of the rebuild cleared the chain. Read a blocking chain from `sys.dm_exec_requests`/`sys.dm_tran_locks` and resolve the job from its GUID in `msdb.dbo.sysjobs`.
