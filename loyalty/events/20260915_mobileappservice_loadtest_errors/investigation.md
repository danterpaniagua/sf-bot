**Correction (2026-09-15): `connectionTimeout` downgraded as the leading theory for this ticket.** Initially assumed a likely recurrence of the GITIN-1909 mechanism since the config was never changed — but that mechanism specifically produces `CONN_RESET` (idle pooled connection force-closed near-instantly on reuse), and in today's evidence `CONN_RESET` is a minor category (189 of 9,924 failures, 1.9%). Still want the current `connectionTimeout` value confirmed (cheap check, rules out drift since 2026-08-21), but it's no longer the primary diagnostic target.

## `15:09` restart mechanism CONFIRMED (user, 2026-09-15): full `iisreset`, issued by `NT AUTHORITY\SYSTEM` — full output: `data/sfcg-mobi-02_eventlog_1505-1515.txt`

Widened event scan on `SFCG-MOBI-02` (no provider filter, `15:05`–`15:15`) shows a clean stop/start cycle:

- `15:09:15`–`15:09:19` — World Wide Web Publishing Service (W3SVC) and WAS enter **stopped** state, then **Event 3202** (`Microsoft-Windows-IIS-IISReset`): *"IIS stop command received from user `NT AUTHORITY\SYSTEM`"*.
- `15:09:39`–`15:09:40` — W3SVC/WAS enter **running** state (matches the previously-found WAS 5211 event), then **Event 3201**: *"IIS start command received from user `NT AUTHORITY\SYSTEM`"*.

This is a **full `iisreset`** (stops/restarts the entire IIS service stack — W3SVC, WAS, all app pools — not just one worker process), not an app-pool recycle and not a crash. `NT AUTHORITY\SYSTEM` as the initiating user is the signature of a **local Scheduled Task or a service running under Local System calling `iisreset.exe`** — a real person running it interactively would show their own account, and IIS's own Rapid Fail Protection / periodic-restart mechanisms recycle the app pool's worker process, not the whole service stack via `IISReset` events. This rules out VM restart, app-pool recycling settings, and crash/instability as the mechanism — **the root cause is now "what is scheduled to run `iisreset` on `SFCG-MOBI-02`, and why does it land at `15:09` (mid-campaign)."**

(Note: `Get-ItemProperty "IIS:\AppPools\..."` failed — `WebAdministration` module/IIS PowerShell drive not loaded on this host. Not yet retried with `Import-Module WebAdministration` first; lower priority now given the confirmed `IISReset` mechanism above, but still worth ruling out a coincidental app-pool-level setting layered on top.)

## ROOT CAUSE OF `15:09` BURST CONFIRMED (user, 2026-09-15): Scheduled Task `CleanCSVLogs`

No task had `iisreset.exe` as a literal action (ruling that search out), but a broadened scan for any task whose `LastRunTime` landed in `15:00–15:20` found: **`CleanCSVLogs`** (`TaskPath \`, runs as `SYSTEM`, action `powershell.exe -ExecutionPolicy Bypass -File .\cleanCsvLogs.ps1`), **`LastRunTime = 15:09:09`** — 10 seconds before the confirmed IIS stop command at `15:09:19`. Working theory (script content not yet read, not fully confirmed): a log-rotation/cleanup script for CSV log files that calls `iisreset` to release file locks before deleting/archiving them, run by `SYSTEM` — matches both the timing and the `NT AUTHORITY\SYSTEM` caller identity exactly.

This reframes the `15:09` burst as **routine scheduled maintenance colliding with the campaign**, not a crash, not capacity-driven instability, and not related to `-02`'s earlier `14:01` startup-gap issue. If this task runs on a fixed daily schedule, it will collide with any future high-traffic campaign that happens to run through the same time window — an actionable, fixable finding (reschedule the task, or have the script skip the `iisreset` step when request volume is high, or coordinate campaign scheduling to avoid it) rather than an infrastructure capacity problem.

**FULLY CONFIRMED (user, 2026-09-15) — script content and trigger schedule:**

```powershell
$AppPoolName = 'SmartLoyalty.MobileAppService'
$LogFolder = 'D:\Log\SmartLoyalty.MobileAppService\'
iisreset /stop
Start-Sleep -Seconds 10
Get-ChildItem $LogFolder -Recurse -File -ErrorAction Ignore |
    Where-Object Extension -in '.csv','.svclog' |
    Remove-Item -Verbose -ErrorAction Ignore
Start-Sleep -Seconds 10
iisreset /start
```

(`D:\Util\scripts\cleanCsvLogs.ps1`, run by task `CleanCSVLogs` at `\`.) Timing matches exactly: task starts `15:09:09` → `iisreset /stop` registers `15:09:19` → 10s sleep + file cleanup → 10s sleep → `iisreset /start` `15:09:39`. **Trigger: daily, `StartBoundary 2024-12-05T15:09:11`, `DaysInterval 1`** — this task has been resetting IIS on `SFCG-MOBI-02` every day at ~15:09 local time for close to two years. It is **routine, pre-existing, unrelated-to-campaign scheduled maintenance** that happened to land inside today's campaign window (15:00–15:20Z), producing a ~20–30s full IIS outage and the 53×503 burst.

**Root cause chain for the `15:09` burst is now closed:** daily `CleanCSVLogs` task → full `iisreset` (not app-pool recycle) → ~20s IIS downtime → real 503s to any client with in-flight/new requests during that window → amplified by today's campaign traffic volume being unusually high at that exact time.

**Ruled out (user, 2026-09-16): the `06:00–08:00` UTC SQL blocking (`PNSSRL_MantenimientoIndices`) is not a contributing cause of the `15:09` UTC burst.** The rebuild's `Sch-M` lock cleared at `07:31` UTC — ~7.5 hours before `15:09` UTC — so no rebuild was running at the time of the `CleanCSVLogs`/`iisreset` collision. **Side note (not actionable here, just observed):** the cleanup script also deletes `.svclog` files from `D:\Log\SmartLoyalty.MobileAppService\` daily — consistent with this app generating the same kind of PII-bearing trace logs flagged in the separate `wscg01`/Graylog onboarding PII incident. ## ROOT CAUSE OF THE `06:00-08:00` TIMEOUT SPIKE CONFIRMED (user, 2026-09-15): daily `PNSSRL_MantenimientoIndices` blocking, not capacity — full detail: `data/pnssrl_blocking_0646_0731.txt`

Hourly breakdown of `SmartFranCall.log` failures (requested separately) showed a real `TIMEOUT`/`CIRCUIT_OPEN` spike concentrated in hours `06` (340 timeouts) and `07` (362 timeouts) — unexplained at the time. Since `SFCG-MOBI-02` was deallocated until `14:00` (Activity Log), this had to be `SFCG-MOBI-01` alone. User suggested checking DB housekeeping (backups/blocking) — correct call.

**`PNSSRL_AuditSysprocesses` for `05:45`–`08:15`Z shows a SQL Agent job (`0x9B0BD93393BA1846BE961FADF915AE66`) running:**
```sql
ALTER INDEX [IX_CustomerId] ON [SmartFran.Solution.SmartLoyalty].[Sml].[CustomerPointsLog] REBUILD;
```
continuously from **at least `06:46` through `07:31`** (cumulative CPU climbing steadily across every 5-min snapshot, 443,636 → 1,939,573 ms — one continuous rebuild, not several short ones). A non-`ONLINE` `REBUILD` holds a schema-modification lock (`Sch-M`) on the whole table for its full duration.

**Direct, not inferred:** every `SFCG-MOBI-01` session running the EF query behind `Customer/GetCustomerProfile`/`Benefits/GetCustomerStatus` (`SELECT ... FROM [Sml].[CustomerPointsLog] WHERE [CustomerId] = @EntityKeyValue1`) sits `suspended`, `cpu=0` (no progress), `lastwaittype=LCK_M_SCH_S` at every single capture in the window — queued behind the lock, not slow on its own merits. Same for `SFCG-CLUB-01` (Club Grido website) and Zabbix's own health-check queries against the same table. This directly explains the client-side `TIMEOUT`s (Grido's client times out at ~4s; the lock held for 45+ minutes).

**Immediately after the lock clears (~07:31–07:36):** the already-known chronically-slow `Etl.CustomerPointsLog` sync job (root-caused separately in `events/20260715_cpu_spikes/`, non-sargable `OR` + `COUNT(*) OVER()`) starts its own long query, visible through at least `08:11`. It uses `NOLOCK` and doesn't block others — consistent with zero `TIMEOUT`/`CIRCUIT_OPEN` records in hour `08` despite this job still running. Contributes DB load, not the client-visible blocking pattern.

**Job identity resolved — this is NOT a one-off, it's a daily recurrence:**
```
job_name: PNSSRL_MantenimientoIndices, enabled=1, freq_type=4 (Daily), freq_interval=1,
active_start_time=06:15:00, next_run_date=2026-09-16, next_run_time=06:15:00
```
**This job runs every single day at ~06:15 UTC and blocks `Sml.CustomerPointsLog` for 45+ minutes.** Today's campaign happening to run through this window is what surfaced it, but the underlying blocking window exists independent of any campaign — any real traffic (or a future campaign) landing in `06:15`–`~07:00`Z on any day will hit the same pattern. This is the single most consequential finding in this investigation: not a campaign-specific artifact, an ongoing daily production blocking window that will hit real customer traffic on any day, campaign or not.
