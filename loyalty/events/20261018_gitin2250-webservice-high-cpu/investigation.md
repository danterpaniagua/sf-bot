## What `healthcheck.ashx` checks (data/webs02-healthcheck-ashx-1738.txt; `C:\SmartFran\SmartLoyalty.WebService\healthcheck.ashx`, 2,268 B, modified 2025-11-06, read on WEBS-02 only)

- A plain `.ashx` handler. It reads **CPU** as `Processor(_Total)\% Processor Time` sampled over **500 ms** (one `NextValue`, `Sleep(500)`, a second `NextValue`), and **memory** as `Memory\Committed Bytes / Commit Limit × 100` (commit charge against the commit limit, not physical RAM). If either is **above 80** it answers **HTTP 400** (`"status":"Warning"`); otherwise HTTP 200. Any exception returns 500; a failed counter read returns 0. The body is JSON with the `cpu` and `memory` values.
- The balancer probe (HTTP 8080, every 15 s, 1 failure = unhealthy) therefore marks a host unhealthy when a single 500 ms CPU sample, or the commit ratio, exceeds 80. This fits the morning's local result (HTTP 400 while saturated, 200 after the reboot) and the 0 % probe success from about 14:34. Which of the two values exceeded 80 at 15:24 was not recorded (the body of the 400 was not captured; open question 3, partly answered).
- Consequence for the CPU alert design: the probe reacts to instantaneous samples, while the new Zabbix tiers use a 10-minute average. The sampler (17:20-17:23) shows 0-100 % swings between samples on a 28 % average, so a host with a modest average can still fail probes. This would also be a candidate explanation for WEBS-03 losing probes at about 33 % average CPU (question 4); not tested.
- The memory input is commit charge / commit limit. The Zabbix memory trigger (`{$MEMORY.UTIL.MAX}`=90) measures a different quantity (utilization reported by the agent item) and does not mirror the probe. The Zabbix item that mirrors it would be the counter `\Memory\% Committed Bytes In Use`; whether such an item exists on these hosts was not checked.
- Local calls to the endpoint, 5 per host, 3-4 s apart, about 20:40-20:43 UTC (17:40-17:43), data/webs-healthcheck-body-1740.txt, -1741.txt, -1742.txt: all 15 answered HTTP 200 `Healthy`. `memory` (commit ratio) was 32 % on WEBS-01, 34 % on WEBS-02 and 24 % on WEBS-03, far from 80. `cpu` swung within seconds: WEBS-01 1.5-8 %; WEBS-02 1.8, 6.9, 5.9, 11.7, then 47 %; WEBS-03 69, 54, 55, 64, then 0.7 %. All three files are 2,268 bytes (same size; content not compared). These are present-moment readings only; they do not show which value was over 80 at 15:24, but they show commit ratio is not close to the limit now and CPU samples are very variable.
- Healthcheck coverage in Zabbix: web scenarios `Healthcheck [PROD] MobileApp` and `WebServiceV2` exist on `sfcg-monitoreo` (HTTP not 200, slow response); none exists for the WEBS hosts.
