## Architecture fact, 2026-09-29 (user) — TaskOperatorService and its SQL Server database run on the same machine, for both `test02` and `preprod`

**Real, load-bearing correction to the mental model this investigation had been using.** Unlike production (`SFCG-TO-01` app server, separate `SFCG-DB01` DB host, per `loyalty/docs/infrastructure.md`), **`test02` and `preprod` both run TaskOperatorService and SQL Server on the same VM** — `sfdev02`, in this environment's case (confirmed via the `<Computer>SFDEV02</Computer>` log header and the connection string's `Server=SFDEV02` pointing at the same box the service itself runs on).

**This directly connects H2 and H5, which were previously flagged as possibly-unrelated separate episodes.** If the VM itself experienced a restart/reboot event (consistent with H2 — stuck in "Deallocating" for 10+ minutes), that would take the local SQL Server engine down *at the same time* as the app, not just disrupt a network path to a remote DB host. That's a clean, direct explanation for "Physical connection is not usable" (H5) — not an independent SQL-side problem, the same underlying VM event hitting both the app and its database simultaneously.

**CONFIRMED, 2026-09-29 — H2 and H5 are the same event; correction on why the storm actually stopped.** `SELECT sqlserver_start_time FROM sys.dm_os_sys_info` returned `2026-09-29 14:22:07.717`, landing right at the tail end of the 13:41-14:04 file-rotation-collapse window and matching the last log file's own timestamp (`_13214.svclog`, 14:22). This confirms the VM (hosting both TaskOperatorService and its local SQL Server instance) was down/restarting through the retry-storm window, and SQL Server itself came back online at 14:22 — a real, independently-queried fact.

**But the storm's activity stopping at that point is not "the app recovered naturally once SQL came back."** User clarified: **they manually stopped the TaskOperator Windows service themselves** around this time (the mitigation already recorded as H3) — that's what actually silenced the retry loop, not a graceful self-recovery once the DB became reachable again. The two events (SQL Server's restart completing, and the manual service stop) likely happened close together, but the causal claim is narrower than first stated: SQL Server restarting explains *why the connection was broken* during 13:41-14:04 (confirming H2=H5), not *why the log activity specifically ends* at 14:22 — that's the manual intervention. Don't read this as "if left alone, it would have self-resolved."

**Root cause — mostly confirmed, 2026-09-29, with one real gap identified during a consistency re-check (see the "Major finding" sections below for full detail):**
- **Cycle 1 (2026-09-28) = `sfdev02`'s routine, currently-enabled nightly Auto-shutdown schedule (`shutdown-computevm-sfdev02`, `19:00 ART` = `22:00 UTC`), confirmed via `az resource show` matching the observed `22:01:54` trigger within ~2 minutes.** Because TaskOperatorService and its SQL Server run on this one shared VM, this nightly scheduled stop kills the local DB every night. **This recurs nightly, not just as a one-off** — materially raises the priority of hardening TaskOperatorService against it (Acción 6, ordered shutdown).
- **Job `8432`'s mass-email mechanism (H4) is not tied to either restart specifically** — corrected: it ran on its own normal hourly schedule continuously from `23:00:03` (9/28) through `14:04:58` (9/29), spanning both cycles and the time between them (see the hourly-cadence correction above). So Cycle 1 isn't "the trigger" for the mass-email in the way earlier framed — it's one of several VM/DB disruptions that occurred somewhere within the same ~15-hour window job 8432 kept firing in.
- **Cycle 2's "stuck in Deallocating" *symptom* is fully explained**, via Azure's Activity Log: two engineers' overlapping/conflicting manual VM actions (`deallocate` at `14:07:03`, a failed `powerOff` attempted mid-flight at `14:12:46`, then a second `deallocate` at `14:14:58` that finally succeeded at `14:18:54` — an ~11-12 minute gap matching the original ticket's "stuck >10 min" almost exactly). `wvchelper` is confirmed as the guest-side Azure Guest Agent component that carries out an Azure-issued Stop/Deallocate as a clean OS shutdown.
- **Real remaining gap, found during this consistency re-check: Cycle 2's *origin* is still unexplained.** Preprod crashed unexpectedly at `13:36:33`, and the SQL exception storm (H5) ran `13:41`-`14:04` — both **~30 minutes before** the first manual `deallocate` call (`14:07:03`). The two engineers' actions are a *response* to an already-broken VM/connection, not its cause. What actually broke the connection/crashed Preprod starting at `13:36:33` (with the `12:14:53` alert as an even earlier possible warning sign) is **not yet identified** — this is now the one open root-cause item, narrower than the original "why did sfdev02 get stuck" framing.

## Root mechanism found, 2026-09-29 — the exact code path for H12's flood, and confirmation there is no email backlog

**User asked whether emails were still queued to send after the stop.** Traced the exact source: `ThreadOperator()` in `Front/TaskOperatorService/TaskOperatorService.cs`:

```
while (!shutdownEvent.WaitOne(0))
{
  try { scheduleSvc.RunSchedule(...); }
  catch (Exception e)
  {
    // subject = "ERROR!! on TaskOperatorService [hostname]"
    // sends to customerSupportEmail AND itServicesEmail (2 emails per iteration)
    // body includes "Requires support attention." + footerBody with UtcNow/MachineName/BaseDirectory
    continue;   // loops straight back to RunSchedule() — ZERO delay
  }
  Thread.Sleep(sleepServiceSeconds * 1000);   // only reached on the SUCCESS path
}
```

**This resolves multiple open items at once:**
- **H12's mechanism, fully confirmed**: not a queue or batch process — a synchronous `while` loop that sends 2 emails per failed iteration with **no backoff on the exception path** (only the success path sleeps). A persistent connection failure turns this into a tight loop (~8+ iterations/sec), which is exactly consistent with 1000+ emails in under 2 minutes.
- **H10's mystery alert source, resolved**: the three "Requires support attention" watchdog alerts are this exact same code path — the body text (`"Requires support attention." + footerBody`) matches verbatim (the inner `if (!string.IsNullOrWhiteSpace(customerSupportEmail))` branch, line ~376-386). Not a separate monitoring system — it's TaskOperatorService emailing itself on every unhandled exception from `RunSchedule`.
- **The app itself holds no queue** — confirmed by code: every email is generated and *submitted* synchronously as a direct side effect of the loop iterating; the app cannot enqueue new sends once the service is stopped. This is different from `AutoAcceptAccountRecovery`, which *is* DB-queue-backed (`Sml.CustomerAccountRecovery`) — that queue is unaffected by this and remains a separate, still-open question (real customer-facing email volume, per the SendGrid follow-up action).

**RETRACTED, 2026-09-29 (user pushed back, correctly) — "no backlog" was wrong once the message reaches SendGrid.** The app not having its own queue does not mean nothing is left in flight — **SendGrid's own delivery pipeline holds and retries messages independently of the app's runtime state once they've been handed off.** Checked directly, paging through SendGrid's Email Activity API for `subject="ERROR!! on TaskOperatorService [SFDEV02]"` from `14:30Z` onward (`data/sendgrid_queue_check_summary_20260929.txt`, 7 sequential calls): found **1183 messages** still showing activity between `18:29:25Z` and `18:51:57Z` — roughly **4.5 hours after** the exception storm itself (`13:41-14:04Z`) and after `test02` was stopped/disabled. 387 of those were still in `processing` state as late as `18:48:04Z`; the last four consecutive pages in that check showed zero `processing` entries. **Corrected further, same session**: this `~18:52Z` point was *not* actually the full drain — subsequent rechecks kept finding more finalized activity in later windows (`18:54Z`-`19:15Z`: 724 delivered/276 not_delivered, still zero `processing`; `19:15Z`-`19:29:21Z`: growing batches, 589 messages, still 100% `delivered`, zero `processing`). At no point was anything ever found stuck/actively retrying past `18:48Z` — but the true end of activity is not pinned to `18:52Z` specifically, just "still resolving cleanly, no later than `19:29:21Z`" (the last point actually checked via API). **User-confirmed, 2026-09-29**: no new email arrivals observed since `17:22 ART` (`20:22 UTC`) — the storm is confirmed quiet through this later point too, consistent with (and extending) the API-based confirmation. **This was SendGrid finishing delivery/retry of messages already submitted before the shutdown — not the app generating anything new** (confirmed separately: no new activity for this subject before `14:30Z` cutoff was queried, and the app process is stopped). The distinction that matters operationally: stopping `test02` guarantees no *new* messages are submitted, but does not immediately guarantee no *more* deliveries occur — that depends on SendGrid's own queue state, which needed to be checked directly rather than assumed from the app's architecture alone.

**Confirmed code-level bug, worth a concrete fix recommendation**: the missing backoff/delay on the exception path (`continue` with no `Thread.Sleep`) is what allows a single persistent connection problem to amplify into an email flood large enough to trigger G Suite rate-limiting on internal mailboxes. Fixing this (add a sleep/backoff in the `catch` block, and/or deduplicate repeated identical exceptions before emailing) directly prevents recurrence — more specific and actionable than the general "add throttling" action already recorded.

**Timezone note, 2026-09-29 (user) — the alert timestamps are definitively UTC, not inferred.** The bracketed timestamp in every one of these alert emails comes from `DateTime.UtcNow:s` in the code above — confirmed by source, not by the earlier SCM-timestamp-correlation inference alone. This retroactively confirms all four alert timestamps recorded in this investigation (`12:14:53`, `13:51:36`, `13:54:46`, and a fourth below) are UTC.

**Fourth alert instance, `2026-09-29T14:07:07`** — user-provided. This lands only **~3 seconds after** the colleague's `deallocate` call was accepted (`14:07:03.9-04.0Z`, H9/Activity Log).
