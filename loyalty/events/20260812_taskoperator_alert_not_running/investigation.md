# Investigation — 20260812_taskoperator_alert_not_running

**Status:** open (minor follow-ups only — main issue resolved)

## Confirmed facts

**The alert:** TaskOperatorService (`SFCG-TO-01`) warning that a task had not run for ~15h. Jira: [GITIN-1828](https://smartit-ar.atlassian.net/browse/GITIN-1828). Alert mechanism source-confirmed from `Front/SmlBackScript/ReportWarningsTaskOperator.ps1` + `Query052-sql.xml`: connects to `SmartFran.Solution.SmartLoyalty` (`[Sch].[Task]`, `[Sch].[TaskEvent]`, `[Sch].[Job]`). Separate from `GITIN-1753`/`20260804_reschedule_smartfran_tasks` (which addressed *when* tasks fire relative to each other, not whether they complete) — no overlap in affected tasks.

**Root cause — confirmed via Windows Event Log (System log, Service Control Manager provider) on `SFCG-TO-01`, real service name `SmartLoyalty.TaskOperator.Service`:**
- 2026-08-11 12:20:25 — service stopped; 12:20:30 start type flipped Auto→Disabled; 12:31:24 flipped back Disabled→Auto; 12:31:32 service running again. Reads as a deliberate manual intervention, not a crash — cause not yet confirmed, may be an earlier undocumented remediation attempt.
- 2026-08-11 20:06:02 — service stopped again.
- 2026-08-11 20:09:34 — **genuine failed restart**: Event 7009 (30000ms timeout) + Event 7000 ("did not respond to the start or control request in a timely fashion"). No Application-log "shut down"/"started" entry between 20:06:02 and the eventual 2026-08-12 11:25:11 start — the service was genuinely down for the entire gap, not just slow.
- 2026-08-12 11:25:11 — service enters `Running` (user's manual start this session). **Gap: ~15h19m — matches the ticket's "not running from 15 hs ago" almost exactly.** This is what the original alert was actually about.
- **Why nothing caught it automatically:** the `Check_list_SF` scheduled task (`Front/SmlBackScript/ServicesAndTaskStatus.ps1`, every 5 min, supposed to detect the service down and auto-restart + email) checked for service name `Solution.SmartLoyalty.TaskOperatorService` — but the real name (confirmed via `Get-Service` wildcard search) is `SmartLoyalty.TaskOperator.Service`. Mismatch meant the health-check was silently non-functional for the full outage.
- `TaskOperatorService.OnStart()` calls `ServiceCrashed()` *synchronously* before the background polling thread starts — SCM doesn't consider the service started until `OnStart()` returns. `ServiceCrashed()` processes pending/invalid/started-not-finished tasks **sequentially**, each with multiple DB round-trips — plausible contributor to why the manual start "took a long time," on top of the outage itself.

**Fixed 2026-08-12:** `Check_list_SF`'s deployed script at `E:\SmartLoyalty.SmlBackScript\ServicesAndTaskStatus.ps1` on `SFCG-TO-01` (path confirmed via the scheduled task's action). Backed up to `ServicesAndTaskStatus.ps1.bak_20260812`, then `Solution.SmartLoyalty.TaskOperatorService` → `SmartLoyalty.TaskOperator.Service` corrected on both the service-lookup and `Start-Service` lines. Verified via `Get-Content | Select-String "TaskOperator"`. The local `repo/dev-src-sol-smartloyalty/` clone was intentionally left untouched (read-only, not a deploy target, per root `CLAUDE.md`) — **the equivalent fix still needs to land in whatever real source control owns this script**, or it'll be lost on next deploy.

**The "27 stuck `Rerun` tasks" — investigated and resolved as a non-issue:**
- Query #2 found 27 tasks whose last `TaskEvent` was `Rerun` with no further progress, in two clusters (2026-08-10/08-11 early-morning batch windows). Query #7 (`Sch.Task` directly) showed all had `Done` populated the whole time — they had genuinely completed. `Rerun` is not a failure marker; it's an audit note the `[dbo].[ReRunTask]` stored procedure logs on an already-completed task, pointing at whatever new task it spawned.
- User provided the actual production stored procedures `[dbo].[ReRunTask]`/`[dbo].[RescheduleTask]` (author "Services IT", 2020-06-01 — standing admin tooling). `ReRunTask(@TaskId, @DateTime)` requires `Done`/`CanceledDate`/`DeactivatedDate` already set; creates a new `Sch.Task` row with its own `Created` event. `RescheduleTask` is the opposite (only valid when nothing has started) and would have rejected all 12.
- Attempted `EXEC [dbo].[ReRunTask]` on the 12 latest-instance tasks (after canceling 15 older duplicates via direct `UPDATE ... CanceledDate = GETDATE()`, 15 rows affected, harmless either way). **All 12 calls failed** with the procedure's own duplicate-check: `"Ya existe una tarea a fecha futuro de la actual, sin ejecución para el mismo job"`.
- Query #9 (read-only) found that blocking task per job: in every case a **clean, correctly-scheduled next occurrence** — fresh `Created` event, `ExecutionStarted`/`Done` both `NULL`, `ExecuteOn` mostly 2026-08-13 (tomorrow's normal run), one at 2026-08-12 15:00 GMT (`AutoAcceptAccountRecovery`, hourly). **The system's own recurrence generation had already moved every one of these jobs forward normally — nothing was actually stuck.**
- Root cause of the misdiagnosis: query #2 excluded only `Ended`/`Canceled`/`Disabled` as terminal last-events, missing that `Rerun` is also non-actionable (logged on a row that's already `Done`). Should have filtered on `Done IS NULL` directly. The earlier raw `UPDATE Sch.Task SET ExecuteOn=...` (which appeared to "silently fail") wasn't exposing a real bug — it was simply the wrong operation on tasks that needed no further action. No cleanup needed: the 15 canceled duplicates are inert (canceling an already-completed, already-superseded row has no operational effect).

## Ticket status

The 27-task "stuck" thread was a false alarm from an imprecise diagnostic query, not a second live problem — all 27 completed successfully and their jobs are already correctly queued for their next run.
