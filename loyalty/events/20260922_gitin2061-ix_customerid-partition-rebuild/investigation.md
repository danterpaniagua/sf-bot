## Context (carried forward, not re-derived)

`Sml.CustomerPointsLog` is partitioned by year (`sch_LogDate_Anual`, `RANGE LEFT`, 16 partitions; partition 11 = 2026, current year, ~51M of the table's ~397M rows). `PNSSRL_MantenimientoIndices`'s daily encrypted sweep currently rebuilds `IX_CustomerId` as a full-table operation (confirmed via `PNSSRL_DetallesEjecucionTablasModulos`: 396,999,055 rows processed on 2026-09-14, 2h52m25s) — this single index is the largest contributor to the job's overall multi-hour, highly variable duration (1h53m–6h14m, unexplained variability, still open per GITIN-1981/H4). Scoping the rebuild to only the active partition (`REBUILD PARTITION = 11`, computed dynamically via `$PARTITION.fn_partition_LogDate_Anual`, not hardcoded) would cut the rows processed for this index from ~397M to ~51M.

**Why this can't be a config tweak**: the control table `PNSSRL_TablasModulos` (which drives the encrypted `PNSSRL_MantenimientoModulos` procedure) has no partition-scope column — only whole-table on/off switches (`indexado`, `defragmentacion`, `habilitado`). Applying this requires (1) excluding `Sml.CustomerPointsLog` from the daily sweep (`indexado=0`, `defragmentacion=0` on `id_tablas_modulos=292`) and (2) a new, separate, non-encrypted job that does the partition-scoped rebuild directly.

**Risk of exclusion evaluated and ruled out (H11, GITIN-2036)**: of the table's 5 indexes, only `IX_CustomerId` receives real rebuild activity from the daily sweep — the other 4 (clustered index, PK, `IX_CustomerPointsLog_SaleId`, `IX_CustomerPointsLog_Points`) show near-zero rebuild/reorganize activity and consistently low fragmentation (0–5%) across ~20 sampled nights. Excluding the table doesn't abandon meaningful maintenance on those.

**Companion, not a substitute**: this doesn't replace [GITIN-2060](https://smartit-ar.atlassian.net/browse/GITIN-2060) (reschedule to 08:00 UTC, applied 2026-09-22, `events/20260922_gitin2060-mantenimientoindices-reschedule/`) — the two attack the same recurring-blocking problem from different angles (duration of the blocking lock vs. time-of-day it lands). GITIN-2060 no longer touches this table's timing question directly once this exclusion lands, since `PNSSRL_MantenimientoIndices`'s remaining table sweep won't include `CustomerPointsLog` at all.

## Design decisions made this session (2026-09-22)

- **New job name**: `PNSSRL_MantenimientoIndices_CustomerPointsLog` — mirrors the existing job's naming, scoped to this one table.
- **Two steps**: (1) partition-scoped `ALTER INDEX IX_CustomerId ... REBUILD PARTITION = @PartitionNumber` (dynamic, same statement drafted under GITIN-2036), (2) `UPDATE STATISTICS` on the same index — replicates the encrypted job's `fin_ue` step for this table, per GITIN-2036's own recommended follow-on (H11).
- **Not included yet**: periodic light-touch reorganize checks for the other 3 partition-aligned indexes (GITIN-2036's H11 "follow-on addition", not required immediately given their near-zero real-world need) — left as a future addition, not blocking this ticket.
- **Schedule: 08:15 UTC, daily** — 15 minutes after `PNSSRL_MantenimientoIndices`'s own new 08:00 UTC start (GITIN-2060), inside the same vetted low-traffic window (GITIN-1981's analysis). Staggered rather than simultaneous to avoid two heavy DDL operations starting at the exact same instant and competing for I/O, even though they no longer share a locked object. **This exact offset is a judgment call, not measured data** — no non-prod environment exists to test actual duration beforehand, so the first live run doubles as the validation. Owner login and server name for the new job are read from the existing job/server context at execution time, not assumed.
- **Sequencing of the two state changes**: the new job + schedule is created first (inert until its scheduled time), then the exclusion `UPDATE` on `PNSSRL_TablasModulos` is applied — so at no point is the table left with neither the old sweep nor the new job covering it.
