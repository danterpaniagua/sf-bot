## Working Theory

`Query101-sql.xml` (`SmartLoyalty.WebServiceV2`, `SaleProviderApplicationServiceV2.GetCustomerAdditionalInformation`, backing `SaleProviderController.GetCustomerAdditionalInformationInternal`) queries `SmlSt.CustomerAdditionalInformation` (~4.9M rows) filtering by `CardNumber OR (UidCode + UidSerie)`. **Reachable from 3 separate HTTP GET endpoints**, not a single call site as originally noted: `GET /GetCustomerAdditionalInformation` (dedicated), `GET /GetCustomerByCardNumber`, and `GET /GetCustomerByUidSerie` (both embed it while building the full customer response). All three are `[Authorize]`-protected on `SaleProviderController`. **Checked for other consumers**: `CustomerApplicationService.GetFavoriteProductAndAverageWeight` wraps the same underlying `CustomerService` call, but no controller anywhere in this repo clone (MobileAppService, ClubSiteG2, WebSite, WebServiceCG) calls it — appears dead/unreachable in this codebase, not a real 4th consumer. `MobileAppService.AdditionalInformationController` (name is a false alarm) only touches `Sml.CustomerPointsLog`, unrelated. These 3 endpoints on `SaleProviderController` remain the complete picture. No index exists on any of those three columns — only `Id` (clustered PK) and `CustomerId` (nonclustered) are indexed — so every execution forces a scan across the table. Under elevated call volume this produces sustained concurrent CPU pressure, matching the exact mechanism (`OR` blocking index use, `LOWER()` on `UidCode`, `TRY_CAST` on `FavoriteProduct` in the `Article` join) documented in GITIN-1267 four months ago.

## Remediation — Indexes Created

Immediate DB-side mitigation (SRE-executable, no release needed): the two indexes proposed in GITIN-1267. Saved to `remediation_indexes.sql`. **Post-creation testing (2026-09-21 ~12:08 GMT) found the fix is NOT even partial** — the `OR`/`LOWER()` structure in Query101's WHERE clause prevents the optimizer from using either index at all, not just the UidCode branch. Confirmed two ways: (1) a manual test query (real `CardNumber` value, `UidCode`/`UidSerie` explicitly NULL) via `STATISTICS IO` showed 104,970 logical reads — same magnitude as the pre-index ~100,946 baseline; (2) plan-cache entries created *after* the index existed (ruling out stale caching) show the identical pattern across dozens of cached-plan variants. Likely mechanism: because the `UidCode` branch can't seek (blocked by `LOWER()`), the optimizer can't build a clean seek+seek concatenation plan for the `OR`, and falls back to scanning the whole table regardless of which branch's parameters are actually supplied at runtime. → `data/09_post_index_plancache_check.txt`. The Query101 rewrite (Dev-owned, WSV2 app-side XML resource file, not a DB object) is therefore required for the index to have *any* effect, not just to help the UidCode branch specifically.

**Critical: the deployed fix does not exist in source control on any branch (checked 2026-09-21).** `Core/Domain.Query/Domain/Query/Query101-sql.xml` in this repo clone still has the old `OR`-based query (local `main` confirmed in sync with `origin/main`, 0 ahead/0 behind). Searched every remote branch for a `UNION`-based version — none found. (A candidate lead, `GITSML-5055`, touches this file but is an ancient, long-since-merged branch — its diff against `main` for this file is empty; unrelated history from Feb 2026, not this fix.) **The version running in production right now exists only as an unmanaged edit on the server file(s)** — not committed anywhere. Real risk: the next legitimate deployment from source control would silently overwrite it back to the broken `OR` query, since every branch still has that version. Recommend whoever applied the hotfix also commits it properly (branch + PR) before any other deploy touches `SmartLoyalty.WebServiceV2`.

Top-50 CPU-delta-per-SPID identified the largest contributors (SPID 126: 49,475ms; SPID 173: 37,350ms; SPID 132: 28,733ms; SPID 71: 13,673ms; SPID 109: 9,132ms; SPID 120: 6,326ms; SPID 107: 3,028ms). Instead, the dominant pattern across SPIDs 126, 132, 71, 107 (and the `suspended`/`ASYNC_NETWORK_IO` snapshot for 173) is the **same EF-generated unbounded-paging anti-pattern already noted as a secondary/unclassified contributor in this investigation's original step 2** (2026-09-20, "EF Product/Article ForSale list, unbounded OFFSET/FETCH") — but today it's the *dominant* contributor, not a footnote:

```sql
SELECT [Project1].[C1], ... FROM (
    SELECT ... , '0X0X' AS [C1]
    FROM [Sml].[Article] AS [Extent1]
    INNER JOIN [Sml].[Product] AS [Extent2] ON [Extent1].[Id] = [Extent2].[Id]
    WHERE (@p__linq__0 = 1) AND ([Extent1].[ForSale] = 1)
) AS [Project1]
ORDER BY row_number() OVER (ORDER BY [Project1].[Id] ASC)
OFFSET 0 ROWS FETCH NEXT 2147483647 ROWS ONLY
```

`OFFSET 0 ROWS FETCH NEXT 2147483647 ROWS ONLY` is not real paging — it fetches the entire `ForSale` product catalog every call. Same shape recurs against `Sml.Promotion` (SPID 173 at 20:16, SPID 109 at 20:31 — with an added `CustomerPromotionQuantity` correlated subquery per row) and `Sml.ExchangeOption` (SPID 173 at 20:01). All observed on `SmartFran.Solution.SmartLoyalty`, hosts `SFCG-WEBS-01/02/03`, `SFCG-MOBI-01/02`, `SFCG-CLUB-02` — i.e. fired from ordinary web/mobile/club traffic, not a batch job. SPID 120's peak (6,326ms, 20:06–20:11) is the one exception — captured mid-`Query077-sql.xml` (BranchOffice/Promotion XML-param lookup with 4-way `NOLOCK` join), a different, unrelated query shape; not yet deep-dived.

**Working theory:** these three EF LINQ call sites (product catalog, active promotions, exchange options) use a paging helper that defaults to "no limit" instead of an actual page size, so every request re-scans and returns the full table. Under concurrent traffic across 6 hosts this reproduces sustained CPU pressure the same way Query101 did, but via a different root cause (missing/broken application-level paging, not a missing index).

**Next steps:** (1) aggregate CPU by this query signature across the full 19:55–20:35 window the way step 3 did for Query101, to size total contribution vs. other traffic; (2) check `Sml.Article`/`Sml.Product`, `Sml.Promotion`, `Sml.ExchangeOption` row counts to confirm these are non-trivial scans, not small tables; (3) grep `loyalty/repo/dev-src-sol-smartloyalty/` for the LINQ call sites generating this OFFSET/FETCH shape (likely a shared paging extension method) before concluding it's app-code-owned vs. some SmartLoyalty-side default.

**Step 1 result** (`data/17_...txt`): of 161,915ms total CPU across classified deltas in the 19:55–20:35 window, Article/Product = 101,331ms (62.6%, 17 samples/13 SPIDs), Promotion = 46,482ms (28.7%, 2 samples/2 SPIDs), ExchangeOption = 15ms. 91.3% combined, zero Query101. Confirms this window's spike is dominated by the unbounded-fetch pattern, not Query101.

**Step 2 result** (row counts): `Sml.Article` 761, `Sml.Product` 745, `Sml.Promotion` 17,607, `Sml.ExchangeOption` 210. Article/Product and ExchangeOption are trivially small — a plain join/scan should cost low single-digit ms, not the ~5,961ms/sample implied by step 1's aggregate. This ruled out "expensive individual scan" as the mechanism and pointed toward call *frequency* instead.

**Plan-cache verification** (`data/19_followup_plancache_execution_frequency.txt`, `sys.dm_exec_query_stats` filtered to the `2147483647` OFFSET/FETCH signature): confirmed. The top Article/Product ForSale plan alone: **8,107,553 executions**, avg 1.298ms CPU / 5.564ms elapsed / 19 logical reads per exec — genuinely cheap per call — but `creation_time` 2026-09-20 08:09:19 to `last_execution_time` 2026-09-22 01:39:43 (~41.5h) means this single plan is running at a sustained **~54 executions/second, continuously, for 41+ hours**. The top Promotion variant shows the same shape: 778,982 executions (4.97ms avg CPU, created 2026-09-19 12:17), plus dozens of smaller cached-plan variants for Promotion going back to 2026-09-09 — total volume across all Promotion plans is well into the millions too.

**Revised root cause: this is a caching/throttling gap, not a slow-query problem.** No single execution is expensive; the call sites for "active for-sale product catalog," "active promotions," and "exchange options" are being hit continuously at a rate (~54/s sustained for the top plan alone) inconsistent with organic per-request browsing traffic for catalog data that should change infrequently. This reads like a client/service with no client-side or server-side caching, polling these three endpoints in a tight loop — possibly a background sync job, a misconfigured retry, or a per-request re-fetch that should be cached at app-server or CDN level.

**Next step:** grep `loyalty/repo/dev-src-sol-smartloyalty/` for the call sites generating this OFFSET/FETCH shape (product/promotion/exchange-option "get all for sale/active" LINQ queries) and check (a) whether there's supposed to be app-level caching that isn't hitting, and (b) which consumer(s) call these endpoints — the `program_name`/hostname spread (`SFCG-WEBS-01/02/03`, `SFCG-MOBI-01/02`, `SFCG-CLUB-02`) suggests it's core web/mobile traffic, not one rogue service, so the fix is more likely "add caching at these 3 call sites" than "throttle one caller."

**Source confirmation.** `PageSize = int.MaxValue` (the deliberate source of the `OFFSET 0 ROWS FETCH NEXT 2147483647 ROWS ONLY` shape) is used at 8 call sites: `Front/MobileAppService/Controllers/BenefitsController.cs:345`, `Front/MobileAppService/Controllers/CatalogController.cs:128`, `Front/ClubSiteG2/Controllers/HomeController.cs:1416,1486`, `Front/WebSite/Controllers/ExchangeController.cs:394,780,855`, `Front/WebSite/Controllers/PromotionController.cs:2878` — spanning `MobileAppService`, `ClubSiteG2`, and `WebSite`. This is intentional app design ("fetch the full list, no real pagination"), not an accidental bug — those screens legitimately want the whole catalog/promotion/benefits list per load.

**No caching layer exists anywhere in the relevant domain services** — grepped `Core/Domain/Domain/ProductContext/`, `Core/Domain/Domain/PromotionContext/`, `Core/Domain/Domain/ExchangeOptionContext/`, and every controller in `Front/` for `MemoryCache`/`IMemoryCache`/`CacheItemPolicy`/`[OutputCache]`/`HttpRuntime.Cache` — zero hits. So every single page load, on every host, re-executes the full uncached fetch against the DB. Given `Sml.Article`=761 rows, `Sml.Product`=745, `Sml.ExchangeOption`=210 — this is close-to-static reference data (catalog/promotions change on an operational cadence, not per-request) being fetched from scratch ~54 times/second sustained.

**Conclusion: the fix is an application-level caching gap, not a DB-side index or query problem.** Recommend (Dev-owned): add a short-TTL (e.g. 1–5 min) in-memory or distributed cache at the `ProductContext`/`PromotionContext`/`ExchangeOptionContext` service layer (or `[OutputCache]` at the controller actions) for these "get all for sale/active" reads, invalidated on write (product/promotion/exchange-option create/update/deactivate). No DB schema change needed — the query itself already costs <2ms per call; there is simply too much of it.

**Consumer identified — this is POS traffic, not website traffic.** Traced the dominant call sites for this window's top CPU-delta SPIDs (126, 173, 132, 71 — all on `SFCG-WEBS-01/02/03`) to `Front/WebService/Service/SaleProvider.svc.cs` and `SaleManagementProvider.svc.cs` (WCF services, "WebService" project = `SFCG-WEBS-01/02/03`):

## DB-Side Mitigation Options (given app-side pagination fix is deferred)

Checked what's available without touching `SaleProviderApplicationService`'s query methods.

**Index inventory** (`data/20_index_inventory_and_resource_governor.txt`): `Sml.Article`/`Sml.Product`/`Sml.ExchangeOption` have only PK clustered indexes (plus a couple of unrelated nonclustered ones on Product) — all three tables are tiny (761/745/210 rows), so observed logical reads (19/10 per call) are already near the floor for a full scan. **No indexing win available here** — there's no supporting index that beats "just scan the whole table" at this size.

`Sml.Promotion` has 6 nonclustered indexes, but 5 of them are near-duplicates differing only by a single day-of-week key column (`Monday`/`Tuesday`/`Wednesday`/`Thursday`/`Sunday` — no Friday/Saturday). **None cover the query** — it selects nearly every column on `Promotion` — so the pricier plan-cache variants (648–880 logical reads, from `data/19_...txt`) are consistent with a clustered-index scan of the ~17,607-row/~660-page table, not an efficient seek. These 5 redundant indexes add write overhead on every `Promotion` insert/update with no measurable read benefit for this query shape. Flagged as separate low-priority index-cleanup hygiene, not this incident's fix.

**Resource Governor** — currently disabled (`is_enabled = 0`, no classifier function, only default `internal`/`default` pools). Since `Front/WebService/Service/` hosts *only* `SaleProvider.svc` and `SaleManagementProvider.svc` (confirmed — no other `.svc` files in that project), a `HOST_NAME()`-based classifier for `SFCG-WEBS-01/02/03` would cleanly isolate exactly this POS-integration workload with zero app-code changes. **Caveat: this caps the whole POS service's CPU (real sale submissions included, not just the wasteful catalog refetch)** — it protects other services (WebServiceV2, Mobile, WebSite) from being starved by this traffic, but does not reduce the POS service's own CPU consumption, and an aggressive cap risks slowing real checkout transactions. Containment, not remediation.

**IIS/ASP.NET output caching — checked, doesn't apply cleanly.** `SaleProvider.svc`/`SaleManagementProvider.svc` use `customBinding` with WS-SecureConversation over `httpTransport` (classic SOAP, per `Config/ServiceModel.Bindings-Template.config` / `Services-Template.config` — the real deployed configs are gitignored, templates confirm the binding shape). All calls are HTTP POST to a single URL; method name and parameters (e.g. `branchOfficeId`) live inside the SOAP body, not the URL/querystring. IIS output caching and ASP.NET's `OutputCache` module key on URL/querystring and only cache GET by default — they can't see into the POST body, so they can't distinguish one branch office's request from another's. Turning on generic IIS caching here would either cache nothing or risk serving one branch office's catalog to another. A working cache would require a custom WCF message-inspector/behavior keyed on the parsed SOAP body — smaller in scope than reworking the LINQ paging logic, but still a code change, not a config flip.

**Net assessment:** DB-side query tuning has hit its ceiling (tables too small, no covering index gap for Article/Product/ExchangeOption). Resource Governor can contain the blast radius but not the root cause. IIS caching doesn't apply without custom SOAP-aware caching code. The only real reduction in call volume/CPU still requires an app-side change at the `SaleProvider.svc` catalog endpoints — either the deferred pagination fix or a custom message-level cache.
