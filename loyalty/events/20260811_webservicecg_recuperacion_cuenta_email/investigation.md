# Investigation — 20260811_webservicecg_recuperacion_cuenta_email

**Status:** blocked — need additional occurrences before root cause can converge; `ops.md` drafted reflecting this blocked state per explicit request, not as a converged closure report

**Jira:** GITIN-1816 — https://smartit-ar.atlassian.net/browse/GITIN-1816

## Confirmed facts
- Reported symptom: "Account Recovering" requests made through WebServiceCG are not sending the recovery email to the requester.
- Specific reported case: `Sofilualbornoz@icloud.com`, request around `2026-08-10T02:08:20.58776+00:00`.
- hMailServer application log (host not yet confirmed — pending) shows, for this exact case: message 5669021 from `info@clubgrido.com.ar` to `Sofilualbornoz@icloud.com`, accepted at `2026-08-10 02:08:18.385`, relayed to `smtp.sendgrid.net` at the same timestamp, delivery thread completed at `02:08:18.432`. This confirms the app's own mail submission (hMailServer as local relay) succeeded and handed the message off to SendGrid — it does **not** confirm SendGrid accepted/delivered it, or that it reached iCloud's inbox. "Delivery thread completed" only means the local relay thread finished, not a final-delivery confirmation.
- New infra fact (not previously documented): loyalty/WebServiceCG's outbound mail path is app → hMailServer (local SMTP relay) → `smtp.sendgrid.net` → recipient. Previously only `cloud/`'s SendGrid resource (`sf-cloud-sendgrid`) was documented in this repo — this is the first confirmed evidence that loyalty also relays through SendGrid, via an intermediate hMailServer hop not previously known.
- Q3 result confirms `SendEmailError IS NULL` for this exact row (Id 746836, `SendEmailAttemptedAt` `2026-08-10 02:08:18.390`, matching the hMailServer accept timestamp `02:08:18.385`). **App-level send did not throw for this case** — rules out the `ExecuteRecovery` return-value bug as the cause of this specific instance (there was no exception for it to swallow). `FinishedDate` is NULL, but that's expected — it reflects the customer never completing the recovery flow via the link, consistent with them never receiving the email.
- WebServiceCG belongs to the loyalty/SmartLoyalty project — tag `WebserviceCG` (`docs/tags.md`), hosted on `SFCG-WSCG-01` (`loyalty/docs/infrastructure.md`).
- No existing infra documentation for WebServiceCG's email-sending mechanism (SMTP/provider) in this repo — undocumented territory prior to this investigation.
- Email/SMTP infra documented elsewhere in the monorepo (SendGrid, `sf-cloud-sendgrid`) belongs to `cloud/` (SmartCloud), a separate platform — not confirmed to be shared with loyalty/WebServiceCG.

- Traced the full code path in the local source clone (`loyalty/repo/dev-src-sol-smartloyalty/`), each hop verified directly (not taken on trust from the search agent):
  - `POST api/Account/AccountRecovery` → `AccountController.AccountRecovery` (`Front/WebServiceCG/Controllers/AccountController.cs:57`) → `CustomerApplicationService.ExecuteRecovery` (`Core/Application/Service/CustomerContext/CustomerApplicationService.cs:1867`).
  - `ExecuteRecovery` calls `this.SendMailConfirmation(...)` at line 1938, then **unconditionally returns `RecoveryResponse.Ok(...)`** at line 1939 — the boolean result of `SendMailConfirmation` is discarded. The HTTP caller always sees success regardless of whether the email actually sent.
  - `SendMailConfirmation` (line 2152) wraps the send in its own try/catch (lines 2181-2211): on exception from `LoyaltyEmailNotifier.RecoverAccount(...)` it sets `HasError = true` / `MessageError = ex.Message` and persists via `SetSendEmailCustomerAccountRecovery`, then returns `false` (swallowed at this level too — no rethrow, no log write here beyond the DB row).
  - `SetSendEmailCustomerAccountRecovery` (`Core/Domain/Domain/CustomerContext/CustomerService.cs:1719`) writes `car.SendEmailError` (message or null) and `car.SendEmail` (UTC timestamp) onto the `Sml.CustomerAccountRecovery` row for that request (table confirmed via EF migration `Core/Data/Migrations/201602241827471_CustomerAccountRecoveryCreate.cs`).
  - `LoyaltyEmailNotifier.RecoverAccount` (`Core/Shared/Notification/LoyaltyEmailNotifier.cs:291`, called with `withThrow=true`) first reads three local HTML template files (`recover-account.htm`, `Header.html`, `Footer.html`) via `StreamReader` from a `Server.MapPath`-resolved path, builds the email body, then calls `EmailNotifier.SendEmailHtmlCustom` (`Extend/Notification/EmailNotifier.cs:89`).
  - `SendEmailHtmlCustom` calls `mailSender.SendHtmlEmail(...)` (`IMailSender`, external `SmartFran.Seed.Comm` assembly — implementation not in this source tree, presumably SMTP-based). On exception it logs via `Logg.Error(ex)` and rethrows — that's what the outer `SendMailConfirmation` catch swallows.
  - So a failure can originate either in the **file read** (missing/misconfigured `pathToPublic`) or in the **actual mail send** (`IMailSender`) — both funnel through the same swallowed exception path and would look identical from the API response (always 200 "¡Listo!...").
- SMTP config keys (`SmtpMailPort`, `SmtpUser`, `SmtpPassword`, `SmtpServerHost`, `SmtpEnableSsl`) live in `Front/WebServiceCG/Config/AppSettings-Template.config`, consumed via `Core/Shared/Notification/Settings.cs`. Template values are placeholders — no real credentials in this repo, per CLAUDE.md rule (never write secret values into the repo).
- Mail relay hop identified: two hMailServer relay VMs, `192.168.50.161` and `192.168.50.162`, tagged `SF-SMTPRL` Cardinality `01`/`02` respectively in the NXLog config that ships their logs to Graylog. Both relay to `smtp.sendgrid.net`. Hostnames confirmed via `$env:COMPUTERNAME`: `.161` = `SFCG-SMTP-01`, `.162` = `SFCG-SMTP-02`.
- **Observability improvement attempted and rolled back (2026-08-11, outside this event, in the `cloud-graylog` repo conversation):** tried adding `$MessageId`/`$Thread` field extraction and removing the over-broad `drop()` that discarded every "delivery thread completed" line, specifically to enable the message-ID/domain correlation described below. This caused both relay VMs to silently stop shipping to Graylog entirely (confirmed via `nxlog.log` — no errors, but ingestion stopped for tens of minutes despite hMailServer actively writing new lines). Root cause was never pinned down (never got to a `DEBUG`-level nxlog log before rolling back) — could be any of: the `$MessageId` regex, the `$Thread` regex, removing the "thread completed" drop, or removing an unrelated DNI-extraction block that was also cleaned up in the same pass. Reverted to the original NXLog config on both VMs and confirmed ingestion resumed. **Net effect: the `$MessageId`/`$Thread` correlation capability described in the next section does not exist yet** — this ticket is still blocked on getting comparable multi-occurrence data by any means, not just by waiting for more organic reports.

## Current working theory
For this specific case, the failure is confirmed to be **downstream of the application and the local mail relay** — the app called `IMailSender` without exception, hMailServer accepted the message and relayed it to `smtp.sendgrid.net` successfully. The email never reached the requester between SendGrid accepting the relay and the inbox. Two unconfirmed candidates remain, and **iCloud-domain-specific filtering should be weighted as a leading candidate**, not just one of two equally-likely options: SendGrid rejected/dropped/deferred the message after accepting the relay hand-off, or iCloud's inbound filtering blocked/silently discarded it (iCloud is known for aggressive filtering of unfamiliar/low-reputation senders, and the one confirmed case so far is `@icloud.com`). Still unconfirmed either way — need SendGrid-side delivery status, and ideally more occurrences across different recipient domains to see if the pattern is domain-specific or spread evenly (which would point back toward SendGrid/relay-wide).

## Ruled out
- App-level exception in `ExecuteRecovery`/`SendMailConfirmation`/`IMailSender` as the cause of this specific case — confirmed via DB (`SendEmailError IS NULL`, Id 746836) and corroborated by the hMailServer log showing successful local relay.
