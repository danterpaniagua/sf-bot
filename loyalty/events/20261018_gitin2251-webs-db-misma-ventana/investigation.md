- **Indexes (Q8, 2026-10-19 12:40 GMT, `data/q8-indices-customerpointslog.txt`; service up since 2026-10-14 07:28 GMT, so usage counters cover ~5 days):** `Sml.CustomerPointsLog` has 404,460,588 rows (clustered 64 GB on `LogDate`, name `ClusteredIndex_sch_LogDate_Anual`, so probably partitioned by year, not confirmed). `IX_CustomerId` (7.4 GB) is keyed on `CustomerId` alone (Q9 raw rows: `key_ordinal` 1; `LogDate` is only the implicit partitioning column, `key_ordinal` 0, `partition_ordinal` 1; Q8's "LogDate, CustomerId" was an artifact of sorting by `key_ordinal` and was wrong) and has **no included columns**, so `Points` is not in it; the only index that holds `CustomerId` and `Points` together is `IX_CustomerPointsLog_SaleId` (17 GB, keyed on `SaleId`, with `CustomerId` and `Points` included). The table and these indexes sit on partition scheme `sch_LogDate_Anual`: 16 partitions, the largest 76,133,878 rows, the smallest 0 (`data/q9-indices-columnas-reales-y-particiones.txt`). A `CustomerId` lookup with no date therefore probes every partition. Reading the trigger's `SUM(Points) WHERE CustomerId` against this: each execution has to read the customer's rows through `IX_CustomerId` and fetch `Points` from the clustered index by key lookup (3,788,089 seeks on `IX_CustomerId` against 3,794,292 clustered lookups, and only 6 scans, are consistent with that), so its cost grows with the customer's number of log rows. `SmlSt.CustomerPointsLog` (MERGE target) is a heap of 5,571,426 rows with an index on `CustomerId`, 278 MB: small. `user_updates` is 1,214,569 on every index of both tables, i.e. about 1.2 M inserts since the restart (each firing the trigger and one `SmlSt` update). `IX_CustomerPointsLog_Points` on the big table has 338 seeks and 0 scans against 1,214,569 updates (write cost for almost no reads; a side observation, not analysed).

- **Possible defect in the trigger's join (2026-10-20, from reading the deployed definition `data/trigger-CustomerPointsLogAfterInsert-definicion.sql`; not tested):** `PointsSummary` joins `inserted i` to `Sml.CustomerPointsLog` on `CustomerId` and groups by `i.CustomerId` without first collapsing `inserted` to one row per customer. If one INSERT statement adds k rows for the same customer, every log row of that customer matches k times, so `SUM(cpl.Points)` is k times the real total and the join reads k times the customer's history. Q12 saw one customer with 26 rows sharing one `LogDate` (17:22:16 GMT), which fits a multi-row statement (a shared `LogDate` is not proof of one statement). Two consequences if it holds: `SmlSt.CustomerPointsLog.Points` can be wrong until something recomputes it (a nightly refresh of `SmlSt.CustomerPointsLog` was seen in the plan cache, Q14; what it does was not read), and the CPU cost per firing grows with k as well as with the history size. Whether this explains the 97.5 s is unknown (Q18: histories are small, so even k times 1,171 rows is not obviously 97 s). Q19 in `scripts/scripts.sql` compares SmlSt points with the real sum for the customers with multi-row groups in 17:11-17:16 GMT; not run. A fix would aggregate `inserted` per customer before the join; no change was made or proposed in `ops.md`.
