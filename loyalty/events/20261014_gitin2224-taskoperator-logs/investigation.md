## Why the problem was hard to detect (evidence from GITIN-2223, `loyalty/events/20261014_gitin2223_taskoperator-preprod-appsettings-xml/`)
- The ETL job `EtlDwGridoPointsTransferenceProcessor` (job 7965) failed in 445 of 445 runs in PREPROD, from 2025-01-21 to 2026-10-14, each lasting about a minute, and nothing visible said why: `Sch.Task` only has `Failed = 1`, `Sch.TaskEvent` has no message, and no `Etl.EtlOperationExecution` row is created for the failing operation (the failure happens in `GetActiveOperation`, before it). The cause was a missing connection string for `EtlContext` in `Config\ConnectionStrings.config`.
- The same SQL error text reached the investigation only as a paste from the user (source not stated); the format `--Exception-- / --Message-- / --StackTrace--` and the dotted separator line look like the body of the error emails sent by the service (see below), which is a hypothesis, not verified.
- The first fault of 2026-10-13/14 (an invalid XML comment, `<!-- 13/10/2026 --- v13.01.00 -->`, in `AppSettings.config`) stopped the service from starting; the message the user pasted begins "Service cannot be started." (the wording of Windows' service host when `OnStart` throws; inferred).
- "Service crashed, task being reprogrammed." appears as the deactivation note of tasks on every Monday at about 09:03 UTC (09-07 … 10-12) and on 20 tasks between 02:06 and 12:04 UTC on 10-14; the cause of those service starts is not recorded anywhere that was found.
- Finding the missing connection string took about ten read-only rounds against the host and the databases (config files, Unity registrations, connection-string names, `Sch.Task`, `Etl` tables).

## What the source does today (read-only; `loyalty/repo/dev-src-sol-smartloyalty`, branch `main`, HEAD aef06a72a of 2026-09-29, working tree; the version deployed in PREPROD was not verified; the libraries `SmartFran.Business.Schedule` (`RunSchedule`), `SmartFran.Seed.*` and the mail sender are not in this repo, so what they log was not read)
- `Front/TaskOperatorService/TaskOperatorService.cs`:
  - Only three plain log lines in the service itself: "Instancing Service", "Starting Service" and "Stopping Service" (`Logg.Info`).
  - `OnStart` calls `ServiceCrashed()` synchronously, without `try/catch`. It resolves `IScheduleApplicationService` from the DI container (this is where the XML-configuration error and Unity's `ResolutionFailedException` surfaced). It reads the executable, started-not-finished and invalid tasks, cancels or deactivates them with the note "Service crashed, task being reprogrammed." and reprograms them; it logs nothing about how many it found or what it did to each (the only traces are the DB note, a `TaskEvent` in some paths, and an email to IT).
  - `ThreadOperator` loops `RunSchedule(callback, totalThreads, sleepSeconds)` and then sleeps; no heartbeat, no per-iteration or "idle" line. Errors from tasks reach the callback `(string logg, Exception ex)`, which only sends emails (`customerSupportEmail`, `itServicesEmail`; subject "ERROR!! on RunSchedule [machine]") with `ex.AsText()`; an exception that escapes `RunSchedule` is logged with `Logg.Error(e)` and also emailed. If the mail settings or SMTP are wrong, nothing is seen; the code logs neither "email sent" nor "email failed". `ThreadAbortException` is swallowed silently.
  - The settings template (`Config/AppSettings-Template.config`) sets `SleepThreadSeconds` 60, `TotalThreads` 3, and the support/IT e-mail keys to internal addresses; what PREPROD actually has was not read for those keys.
- `Front/TaskOperatorService/Program.cs`: if startup throws, it writes `Log.txt` in the base directory with `FileMode.Create` (each failure overwrites the previous one), encoded UTF-16, with the message and stack trace of the exception and only one level of inner exception. Exceptions thrown inside `OnStart` after the service host started are not covered by that `catch`.
- `Extend/Diagnostic/Common/Logg.cs`: every call is `LoggerFactory.MainLogger?...`, i.e. it silently does nothing if the logger was not initialized; where `MainLogger` writes (file, event log, trace listener) is decided by the logger provider and `Config\SystemDiagnostics.config`, which was not read in this task (C1 reads it).
- `Core/Application.TaskBridge/TaskProcess/*.cs`: 44 task-processor files, 27 with no `Logg.` call at all. `EtlDwGridoPointsTransferenceProcessor` logs only a warning when the operation is not active ("Etl process: …, not active."); a failure inside `GetActiveOperation` or `ExecuteOperation` propagates to `RunSchedule` and its e-mail callback.
- Not in the repo: how the ETL context picks its connection string (`SmartFran.Business.Etl`), so the exact lookup rule behind the missing-entry failure was not read; it is inferred from the behavior seen (TEST02 has the `EtlContext` entry and works).

## Recommendations (draft; each is tied to something that was hard to see)
| # | Recommendation | Would have shown |
|---|---|---|
| R1 | At start, log a fingerprint: assembly version and build date, host, base directory, and for every file in `Config\` its name, last write time and a short hash; parse each `.config` and log which one fails and at which line. Wrap `OnStart` in `try/catch`: log the full exception chain to the logger and the Windows Event Log, then rethrow. | The XML comment fault at once, with its file and line, and what changed at the 13-10 deploy |
| R2 | In `ServiceCrashed()`, log how many tasks were found in each group (executable, valid started-not-finished, invalid started-not-finished) and, per task, `JTS[job-task-step]`, job name, the action taken (cancel / deactivate / reprogram) and the new `ExecuteOn`; log a warning when a task could not be reprogrammed. | Why 20 tasks were deactivated today, and the Monday pattern |
| R3 | Heartbeat every N minutes (for example 5): service alive, number of tasks running, number due and not started, time of the last task start. Warning when tasks are overdue and none has started for M minutes. | The "TO is not running tasks" suspicion could be answered from the log in one look |
| R4 | Per task: one `Info` line when it starts (`JTS`, job name) and one when it ends (duration, result), and an `Error` with the full exception chain (type, message, inner exceptions, stack) when it fails, with the task id on every line. Also store the error text in the database (a message on the `TaskEvent` or a column on `Sch.Task`) so `Failed = 1` carries a reason. | The 445 failures of job 7965, one explicit message each time |
| R5 | When an EF context is created or resolved, log which named connection string it uses and its server and database (never the user or password); if no connection string exists with that context's name, fail with an explicit message ("no connection string named X") instead of falling through to the driver's error. At start, compare the contexts registered in `Unity.config` with the names in `ConnectionStrings.config` and warn on any missing. | The missing `EtlContext` entry on day one (2025-01-21) |
| R6 | `Log.txt` in `Program.cs`: append instead of overwrite, write the full inner-exception chain, use UTF-8, and rotate. | Repeated startup failures would not erase each other |
| R7 | Do not rely on e-mail alone: log "mail sent" / "mail failed" for each notification, and send the same events to the central log (Graylog) with host and environment fields. | A PREPROD where mail is not delivered would still show the error |
| R8 | Never write connection strings or credentials to any log (log server and database only). | Avoids what happened in the GITIN-2223 diagnostics (a credential reached a diagnostic output) |
| R9 | Outside the code (no developer needed): a monitor on `Sch.Task` for tasks due for more than N minutes without `ExecutionStarted`, and for a job with `Failed = 1` several runs in a row, plus an alert when the service has no heartbeat. | 445 consecutive failures would have raised an alert in the first week |
