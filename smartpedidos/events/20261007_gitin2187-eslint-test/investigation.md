# GITIN-2187 — [SP] ESLint test en SmartPedidos

- Jira: https://smartit-ar.atlassian.net/browse/GITIN-2187
- Opened: 2026-10-07
- Status: converged for ticket purposes (2026-10-08): repo changes pushed to `develop` in all three app repos; Jenkins builds, migration of the jobs to "Pipeline script from SCM" and alignment of the `ope` branches still pending.
- Scope as understood: run ESLint over the SmartPedidos services (Platform and Concentrador) and feed the result to SonarQube via the JavaScript/TypeScript external analyzer property (`sonar.eslint.reportPaths`). Exact ticket scope not yet confirmed with the user.

## What is known

- Platform (`dev-src-pedidos-platform`, `api/`, 121 files), run on the SonarQube/Jenkins host `sonarqube-srv` (Ubuntu 22.04, Node 12.22.9, npm 8.5.1); evidence in `data/eslint-platform-6x-vs-8x-summary.txt`.
- The project's ESLint is 6.x (reported as 6.4.0 from `./node_modules/.bin/eslint`; a different ESLint reported 6.8.0 when launched through `npx`). It cannot parse optional chaining, `??` or class fields: 37 of 121 files had a fatal parse error (29 `Unexpected token .`, 5 `=`, 3 `?`), so they were not linted. The syntax attribution is an inference from the token messages.
- ESLint 8.57.1 (run with `--parser-options=ecmaVersion:2022`) parses all 121 files: 4 errors (all `new-cap`), 1971 warnings (890 `function-paren-newline`, 619 `quotes`, 249 `max-len`, 119 `semi`, 94 `no-unused-vars`). The existing config is essentially style rules; only `no-unused-vars` and `new-cap` are defect-ish. Whether defect rules like `no-undef` are enabled was not checked. The 4 `new-cap` and 94 `no-unused-vars` locations were not reviewed.
- `npx eslint@8` / `npx -p eslint@8.57.1 eslint` ran an older ESLint (v6.8.0, found earlier on PATH) instead of the downloaded one; running the cached `eslint.js` with `node` gave the real 8.57.1. In the Jenkins stage ESLint 8 is installed with `npm install --prefix <tmpdir>` and its `.bin/eslint` is called by path.
- SonarQube scanner runs in Docker with `-v ./api:/usr/src`, so ESLint's absolute host paths must be rewritten to `/usr/src/...` (done with `jq` in the stage) or the issues won't attach to files. Not yet verified on a real build.
- Jenkinsfile edits (local `sf-devops` clone, `main` at 71a24f3, uncommitted, files already had other uncommitted edits): `develop/dev-src-pedidos-platform.jenkinsfile` and `develop/dev-src-pedidos-concentrador.jenkinsfile` (and Backoffice, below) got an `ESLint Report` stage before `Sonarqube Analisys` plus `-Dsonar.eslint.reportPaths=eslint-report.json`. The `ope` Concentrador/Platform Jenkinsfiles have no Sonar stage and were not changed.
- Where `sonar.eslint.reportPaths` lives (checked 2026-10-08): only as a scanner argument (`-Dsonar.eslint.reportPaths=eslint-report.json`) in the Docker scan command of the three `develop` Jenkinsfiles in `sf-devops` (`main`; Platform L161, Concentrador L177, Backoffice L175; commits 2800cc8, 1a26376 and 9a7926f). No `sonar-project.properties` in the app repos carries it and it is not a SonarQube project setting, so it will not appear in the SonarQube UI. While the jobs run an inline pipeline script (not "Pipeline script from SCM"), what runs is the script stored in the job, not these files; the job configuration was not inspected.
- Concentrador first Jenkins run failed: its `api/.eslintrc.json` extends `google` (`eslint-config-google`), which was not resolvable, ESLint exited 2 with no report, `jq` then failed on the missing file and failed the whole pipeline. Stage then changed to install `eslint-config-google` in the temp prefix, run with a copy of the config there (`--no-eslintrc -c`), and fall back to an empty report with a WARNING if ESLint produces nothing. This fix is untested.
- Platform's stage uses the project's config in place plus the same fallback; also untested in Jenkins.
- Backoffice (`develop/dev-src-pedidos-backoffice.jenkinsfile`, code in `app/`, not `api/`): same `ESLint Report` stage and `-Dsonar.eslint.reportPaths`, with `app/` paths and the `/app/` → `/usr/src/` rewrite (matches its `-v ./app:/usr/src` mount) and the same empty-report fallback. The Backoffice repo and its ESLint config were not seen: an absent `.eslintrc*`, TypeScript/Vue/React sources (default ESLint only lints `.js`; would need `--ext`/parser plugins), or generated folders such as `dist/` could affect the first run. Untested. No `ope`/`stg` Backoffice Jenkinsfile exists.
- `RUN_BUGS_REPORT` (boolean, default `false`, guards the `Bugs Report` stage, GITIN-1858): already present in the Platform, Concentrador and Backoffice `develop` Jenkinsfiles. `develop/pruebas.jenkinsfile` had the stage with no parameter and always ran it; the parameter (default `false`) and the `when` guard were added. Only `sf-devops/jenkins` was searched; the `ope` Platform/Concentrador Jenkinsfiles have no `Bugs Report` stage. All `sf-devops` edits are uncommitted.
- Pipelines from SCM: the SmartPedidos jobs currently run with an inline pipeline script. Jenkinsfiles live in `sf-devops` (`smartit-ar/sf-devops`, branch `main` only — `develop`/`ope` are branches of the application repos, not of `sf-devops`). Added `options { skipDefaultCheckout(true) }` to the six SF-PEDIDOS Jenkinsfiles (`develop/` platform, concentrador, backoffice, `pruebas`; `ope/` platform, concentrador) because each pipeline clones its application repo into the workspace itself and Jenkins' implicit `checkout scm` of `sf-devops` (declarative agents) could otherwise collide with it (documented default behavior, not tested here). Pushed to `origin/main` (ESLint commit and `skipDefaultCheckout` commit; the ESLint change appears twice in history with the same message — not investigated). Job switch (Definition → Pipeline script from SCM, repo `git@github.com:smartit-ar/sf-devops.git`, branch `*/main`, Script Path per job, SSH credential with read access) is a Jenkins UI change not yet done; no job has been migrated. Whether Jenkins already has a credential for `sf-devops` is unknown. `jenkins/SF-PEDIDOS/README.md` embeds SonarQube badge URLs containing tokens (`sqb_...`, in repo history) — noticed in passing, not handled.
- READMEs: Platform (`README.md`), Concentrador (`README.md`, previously `Readme.md`) and Backoffice (root `README.md`, moved from `app/README.md`) got an "Operaciones — Documentación" section (build/run the image locally, `NODE_ENV`/`environment` = `<ENVIRON>` placeholder with `testing|staging`, never `production`; `develop` is not a valid `NODE_ENV` — config files are `development`, `testing`, `staging`, `production`, `performance`) and a footer with SonarQube badges (quality gate, lines of code, bugs, vulnerabilities, code smells, technical debt) for `DEVELOP.SmartPedidos.{Platform,Concentrador,BackOffice}`. Not tested by building the images.
- SonarQube badges: the three projects exist, are public, and had analyses on 2026-10-07 (`data/sonar-smartpedidos-projects.tsv`). An anonymous call to the SonarQube API returns 401 (authentication is enforced), and the badge endpoint without a valid token returns an SVG "Project has not been found"; so the badges need each project's badge token, which is embedded in plaintext in the READMEs (and now in repo history). Reachability of the SonarQube host from GitHub's image proxy was not verified.
- Lines of code per language, from SonarQube (`data/sonar-ncloc-by-language.txt`): Platform 14,549 (JavaScript 99.9%), Concentrador 12,984 (JavaScript 99.9%), BackOffice 19,773 (TypeScript 63.4%, web/HTML 33.6%, CSS 2.7%, JavaScript 0.3%). Backoffice is an Angular/TSLint project with no `.eslintrc*`, so its `ESLint Report` stage likely produces an empty report (not verified in Jenkins).
