## The escalation chain, read (2026-10-05, `scripts_read_escalation_lambda.sh`; files `data/lambda_IntegrationLambdaEcsTaskProd_*`, `data/sns_Pedidos_Production_*`, `data/lambda_role_*`, `data/alarm_sendMailOldestMessage_history_oct2_on.json`)

**Chain confirmed:** alarm `sendMailOldestMessage` → SNS `Pedidos_Production` (6 confirmed subscriptions: this Lambda, 2 e-mail, 3 SMS; endpoints masked in the file) → `IntegrationLambdaEcsTaskProd`. The Lambda's resource policy allows `sns.amazonaws.com` from that topic only; no event source mappings.

**What the code does (`data/lambda_IntegrationLambdaEcsTaskProd_code_masked.txt`, python3.12, handler `lambda_function.lambda_handler`, timeout **3 s**, 128 MB):** hard-coded cluster `smartfran-pedidos-production`, service `platform-service-production-service`, `limite_tareas = 15`. It calls `describe_services`, reads `runningCount`/`desiredCount`/`pendingCount`, and if `runningCount < 15` calls `update_service(desiredCount = 15)`; otherwise returns "No se aumentaron tareas". It never reads the SNS message (alarm name, `NewStateValue`, queue age); it has **no tiers, no scale-down, and no logging of the update** (the log prints counts before the call, nothing after). Leftovers: unused `numero_tareas = 12` and `desired_tareas = 1`, a debug `print("Holas")`.

**Behaviour seen in the evidence:**
- **It also fires on the OK transition.** The alarm has `OKActions` → the same topic and the code ignores the state. Timestamps match: alarm OK→ALARM 2026-10-02 14:13:25 ART and Lambda `INIT_START` 17:13:25Z (= 14:13:25 ART); ALARM→OK 14:21:25 ART and Lambda `START` 17:21:26Z. At the OK invocation the log shows `Tareas Actuales: 14` / `Tareas Deseadas antes: 14` (< 15), so by the code it calls `update_service` to 15 **when the alarm has already recovered**. The log lines show the count checks, not the `update_service` call itself (nothing is printed after it), so the scale-up on OK is inferred from code + counts, not seen directly.
- Nine ALARM→OK cycles since Fri 2026-10-02 14:13 ART (`data/alarm_sendMailOldestMessage_history_oct2_on.json`), each ALARM lasting 7–8 min (e.g. 14:13→14:21, 20:16→20:23, Sat 13:12→13:19, 21:46→21:54, 22:48→22:56, Sun 11:23→11:31, 19:12→19:20, 20:18→20:26, Mon 09:00→09:07) — the same episodes recorded in GITIN-2162. Lambda Invocations 1–3 per hour in those hours (31 invocations over the last 8 days listed; `data/..._Invocations_hourly_8d.json`) and **Errors ≥ 1 in 10 of those hourly buckets** (`..._Errors_hourly_8d.json`; cause: the 3 s timeout, see the next bullets).
- **Full log since Fri 2026-10-02 00:00 ART** (`scripts_lambda_logs_full.sh`; `data/lambda_IntegrationLambdaEcsTaskProd_logs_full_since_oct2.tsv`, per-invocation lines in `..._logs_summary_since_oct2.txt`): **23 invocations** (matches the 23 in the hourly Invocations metric; the earlier 2-invocation extract was a pagination artifact). **7 of the 23 ended with `Duration: 3000.00 ms … Status: timeout`**, and the Errors metric for the same window is 7 (11 over the 8 days) — so the Lambda's errors are its 3 s timeout, not an exception (no `Traceback`/`Error` lines). Every invocation is a cold start (`INIT_START`) with the remaining runs at 2.6–3.0 s, i.e. the function routinely finishes within a fraction of a second of its limit (128 MB, `describe_services` + `update_service` over boto3).
- **Per-invocation view (running/desired seen at start):** ALARM-time invocations see 5 (or 10 when a previous scale-up is still unwinding); **all nine OK-time invocations see 9–14 running (< 15)** (14, 14, 13, 13, 12, 9, 13, 13, 13), so by the code each one calls `update_service(desiredCount=15)` after the queue has recovered. Evidence the update does land even when the invocation times out: five timed-out invocations are followed ~1 min later by an invocation that sees **running 15 / desired 15** (23:16:26Z 5→15 at 23:17:31Z; 16:19:26Z 13→15 at 16:20:24Z; 00:46:26Z 5→15 at 00:47:24Z; 22:12:26Z 10→15 at 22:13:31Z; plus the 14:23:26Z one, which saw desired 5 / running 11 at the retry) — consistent with Lambda's automatic async retry after a function error, which the code makes harmless (it only acts if `running < 15`). Two timeouts (01:56:26Z, 14:31:26Z) show no follow-up invocation in the log; why was not checked.
- Scale-in is not done by the Lambda: only the two target-tracking policies (scale-in cooldown 120 s) and MinCapacity 5 bring the service back down, consistent with the 3-minute unwinding steps in GITIN-2162.

**Role (`data/lambda_role_*`):** managed policies `AmazonECS_FullAccess`, `AmazonSNSFullAccess`, `AmazonECSTaskExecutionRolePolicy` and the basic-execution logging policy; no inline policies. The code needs only `ecs:DescribeServices` and `ecs:UpdateService` on one service. (Secondary finding about this system: the role is far broader than the function's needs; boundaries/SCPs not checked.)

**Side finding:** `sendMailOldestMessage100` is a dead alarm (see above); `data/sns_Pedidos_Production_subscriptions.json` held three SMS numbers unmasked on first write (the script's mask only covered e-mail); they were masked in place afterwards and the script's mask now covers them.

## Graylog integration — decision and design inputs (user: "let's integrate it with Graylog", 2026-10-05)

**Tracked as [GITIN-2171](https://smartit-ar.atlassian.net/browse/GITIN-2171) (child of this ticket); the monitoring-specific record is `../20261005_gitin2171-lambda-monitoring/investigation.md`, scripts and evidence for it stay in this folder.**

**Decision:** the redesigned Lambda will log to Graylog (`sf-monitoreo.smartfran.com`, the SmartPedidos/SmartLoyalty Graylog 5.2.12 stack, distinct from the SmartCloud `sfcloud-monitoreo`/`cloud-graylog` instance — `docs/graylog_infrastructure.md`). Not yet designed.

**Inputs known (docs/graylog_infrastructure.md, 2026-08-12; the doc says GELF is on `12201`/`12202`, transport (UDP/TCP) not stated; `11514` is the AWS-WAF raw-UDP input; `1514` TXT_UDP):**
- The existing Lambda `waf-to-graylog` (`us-east-1`, python3.13, last modified 2025-10-17, no environment variables, role `waf-to-graylog-lambda-role`) is the in-account precedent for Lambda → Graylog; its code/transport/VPC has **not been read** (`scripts_graylog_integration_recon.sh` reads it).
- The escalation Lambda has **no VPC config** (`VpcConfig: null`), so it egresses over the public internet; whether `sf-monitoreo.smartfran.com` (and which port) is reachable from AWS Lambda is **unknown** — from the user's machine `http://…:9000` answers (`/api/system/lbstatus` 200) and `https://…:9000` timed out, which says nothing about reachability from AWS.
- **UDP is lossy and silent**: the stack's own doc records messages sent over UDP being lost with no error on the sender during OpenSearch restarts; a Lambda that freezes right after returning can also drop datagrams if sent without confirmation. TCP GELF (if the input supports it) or an HTTP GELF input would give delivery feedback — which inputs exist is unknown.
- **Index capacity risk:** `sp_platform__50` (platform-service) and `graylog_299` (Default Stream) were at the 1000-field mapping limit as of 2026-08-12 (GITIN-1827/1854, status of the fix not rechecked here): a message with a field name not already mapped is rejected there. Sending the Lambda's new fields into either index set risks indexer failures; a dedicated stream + index set (or restricting to already-mapped fields) needs to be decided. Creating inputs/streams/index sets is a Graylog change for the user to make.
- **Field/log shape to follow:** the concentrador's JSON logs (seen in `../20261005_gitin2117-concentrador-npm-update/data/container_logs_ope-20.20_20261005.txt`) use `timestamp`, `service`, `level`, `category`, `message` (`[CATEGORY/LEVEL] event_name`) and a nested `rest` object; the platform standard (`sp-log-improvements`) was not re-read here. Nested `rest.*` becomes flattened new fields in Graylog, which matters for the field cap above.
- Lambda cannot be changed without care: it currently scales production (`platform-service-production-service`); any new code must be tested outside production first (staging counterpart `platform-service-staging-service` exists in `us-east-2`).

**Next evidence (read-only):** `scripts_graylog_integration_recon.sh <profile>` — `waf-to-graylog` config/code, and Graylog inputs, streams and index sets via the REST API.
