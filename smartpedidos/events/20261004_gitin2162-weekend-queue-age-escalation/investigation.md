## Confirmed facts

### Queue behavior (`PRD_BranchMessages.fifo`, `us-east-1`)

The user-reported escalation times (Oct 3: ~13h, ~21h, ~22h; Oct 4: ~11h and two on Sunday night) match episodes 4–9; Thu 22:54, Fri 14:09 and Fri 20:14 were not among the reported ones. A further user note, "saw since 14" (Oct 4), is ambiguous; no bucket exceeds 9s from Sun 13:00 to 16:04 (`data/sqs_branchmessages_*_72h.json`, `data/*_oct4pm_oct5.json`, `data/spikes_vs_scaling_ART.txt`, `data/oct4pm_oct5_analysis_ART.txt`, `data/age_over20_and_sun_afternoon_ART.txt`).

### Queue configuration and consumer code

9. **Queue configuration** (`data/sqs_branchmessages_attributes.json`): FIFO, `VisibilityTimeout` 30s, `ReceiveMessageWaitTimeSeconds` 0, `RedrivePolicy` → `MainDeadLetter.fifo` with `maxReceiveCount` 2, `FifoThroughputLimit` perQueue, `DeduplicationScope` queue, `ContentBasedDeduplication` true, retention 4 days.
10. **Consumer code** (`smartpedidos/repo/dev-scr-smartPedidos-platformsService`). The user states production runs the latest GitHub `develop`; `smartpedidos/CLAUDE.md` also records `develop` as the production reference. After a fetch on 2026-10-04 16:26, GitHub `develop` is `ded57a5` (2026-09-24); `ope` (`b8d57be`, 2026-09-30) is 7 commits ahead of it, touching only `api/Dockerfile` and `api/package.json` (Node 22.20 image, npm, axios `~1.20.0`, overrides), and `api/src/platforms` + `api/src/config` are identical on both (`data/git_origin_develop_state_after_fetch.txt`). The image-tag-to-commit link (`10.9.12` → `develop`) is not verified; `:268` was registered before the `ope` runtime commits (2026-09-28 11:41 onward).
   - `api/src/platforms/provider/aws.js:66-` `pollFromQueue()` uses `sqs-consumer ^11` with `batchSize: 10` and `handleMessageBatch`. Per batch it calls `GetQueueAttributes`, then processes messages per order id sequentially via `SetNews.setNews()` (`api/src/platforms/management/strategies/set-news.js`).
   - Per news type the strategies (e.g. `confirmStrategy.js:43-`) do a Mongo `findNew`, an outbound platform call (`this.platform.confirmOrder(...)` and equivalents), then a Mongo `updateNew`. Platform clients import `axios`; `api/src/index.js:21` sets `axios.defaults.timeout = 10000` (axios `~1.13.5`, mongoose `~7.8.7`).
   - Handler errors are caught and logged (`[ORDER/ERROR] setNews_processing failed consumer=parent`), so a failing message does not make the handler throw. No timeout wraps the handler, the Mongo calls or the SQS calls. `sqs-consumer` takes one batch at a time per consumer, so a handler that never returns blocks that consumer's polling.
   - Reading of the code, not tested: a platform API that is slow or down costs up to ≈10s per call but the handler still returns, so deletions would continue; a stall with ≈0 deletions for minutes requires a call that never returns, i.e. one not covered by the axios default (MongoDB operations, SQS calls) or a per-call axios override that was not checked.
   - The message group id of this queue's messages is set by the producer (SmartCloud side), not in this repo.

## Current working theory

All consumers of the queue stop deleting at the same time for ~5–10 minutes, then drain the backlog quickly, repeatedly, independently of message volume and task count (5 or 10), while the same tasks keep answering HTTP normally (fact 11) and no task is restarted or marked unhealthy. That points to a stall confined to the consumer path and common to all tasks, not to whole-process saturation or per-task capacity. Candidates, none tested: (a) a shared outbound dependency used only by the consumer path — the SQS receive/`GetQueueAttributes` calls (called before every batch, no timeout) or the MongoDB calls in `setNews`; a network/endpoint blip between the tasks and SQS or MongoDB would hit all tasks at once; (b) FIFO message-group blocking, which the 30s visibility timeout alone does not explain for stalls of ≈5 min (fact 9); (c) the consumer code path itself blocking on something shared. CPU Max of 44–100% in several episode buckets (fact 4) could be a consequence of the catch-up burst or of a retry loop rather than the cause; not established. More tasks is not expected to help if the cause is a shared dependency (fact 3).

## Ruled out

- **Plain capacity shortfall caused by volume** — episodes occur at very low volume and with 10 tasks (fact 3), and the queue drains within minutes once the stall ends.
- **ECS task churn / health-check kills as the trigger** — no service events before the Sun 11:19 stall (fact 7), `UnHealthyHostCount` max 0 and `HealthyHostCount` min 5 over the first 72 h (fact 11), and the health check is a lenient `GET /`. Not examined for the Sun 19:05/20:15 episodes beyond fact 7's buffer.
- **Whole-process freeze or event-loop blockage on all tasks** — HTTP latency and request rate stay normal in the episode buckets of all 9 episodes (fact 11). A single slow task is not excluded by service-level averages (Max reached 2.1s).
- **Poison/repeatedly failing messages** — nothing in `MainDeadLetter.fifo` (fact 12).
- **The Node 22 / axios 1.20 runtime change on `ope` as the cause** — the same pattern was seen on 2026-09-25 (GITIN-2110), before `:268` was registered, and `:268` was registered before those commits (fact 8). Image-tag-to-commit mapping unverified.
