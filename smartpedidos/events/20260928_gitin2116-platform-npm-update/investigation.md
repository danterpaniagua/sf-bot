## Registry data collected (2026-09-25)

35 full packuments fetched (`scripts.sh`, `curl https://registry.npmjs.org/<pkg>` per package) — all landed successfully, none empty. `Compat.Dockerfile` computed as: highest **stable** (non-prerelease) version whose `engines.node` range is satisfied by Node major 20, or the package's own `latest` if no `engines.node` is declared at all.

**Parser bug found and fixed mid-run**: the first pass wrongly flagged several packages (`cookie-parser`, `cors`, `express-jwt`, `winston`, `morgan`) as Node-20-incompatible. Root cause: their `engines.node` strings have a space after the operator (e.g. `">= 8.0.0"`), and a naive `.split()` on whitespace separated the operator from the version number, then mis-evaluated the bare number as an exact-match requirement instead of combining it back with `>=`. Fixed by normalizing (`re.sub(r'(>=|<=|>|<|=|\^|~)\s+', r'\1', spec)`) before splitting on remaining whitespace (which correctly separates true AND-clauses like `>=14 <=20`). Recomputed all 35 after the fix.

**Result: only 3 of 35 packages are actually capped below their own `latest` by Node 20** — `@babel/core`/`@babel/node` (latest 8.0.6 needs Node 22+, capped at 7.29.7) and `mongoose-unique-validator` (latest 6.1.1 needs Node 22+, capped at 5.0.2). `sqs-consumer` is capped by one patch version only (15.0.3→15.0.0). Everything else, including `axios` and `mongoose`, can already reach its true global latest with no Node bump needed.

## Platform impact — upgrading `axios` to 1.20.x (2026-09-28)

`ops.md` already exists (written 2026-09-28) so this section is investigation-only — not promoted back into the ticket.

**Source-level survey, both service clones (`repo/dev-scr-smartPedidos-platformsService`, `repo/dev-src-smartPedidos-concentradorService`), re-fetched to `origin/develop` earlier this event.** Full grep output persisted to `data/axios_usage_survey_20260928.txt`.

**Usage shape — plain, low-surface:**
- All 68 call sites use the plain `axios.get/post/put/delete(url, body, config)` form, or a config-object `axios(config)` form (2 sites — see below). No `axios.create()` instance anywhere in `platforms-service`.
- `concentrador-service` has exactly one shared instance: `smartpedidos/repo/dev-src-smartPedidos-concentradorService/api/src/utils/httpClient.js` — `const httpClient = axios` (mutates the **default** axios module, not a `.create()` instance) with a request interceptor that stamps `config._t0` and a response/error interceptor that logs duration off `response.config`/`error.config`. Every `httpClient.*` call site in `concentrador-service` (branch.js, statusManager.js, token.js, checkUTC.js, initialData.js, thirdParty.js — ~80 call sites) goes through this shared instance.
- No usage anywhere of `baseURL`, `proxy`, `maxRedirects`, `socketPath`, `allowAbsoluteUrls`, `paramsSerializer`, `CancelToken`/`AbortController signal`, `validateStatus`, or `responseType` in either service (confirmed by grep, zero hits). This matters because the bulk of axios's 1.14.0→1.20.0 security-hardening changelog entries (fetched: `data/axios_changelog_v1.20.0_20260928.md`, `data/axios_release_v1.20.0_20260928.json`) target exactly those features — proxy/`NO_PROXY` bypass hardening, `allowAbsoluteUrls`/`baseURL` path-security clarifications, `socketPath` SSRF allowlisting. None of it applies here since none of those options are set.

**Two real regression-test targets identified:**
1. **UberEats OAuth login (both services)** — `platforms/management/platform/uberEats.js` (platforms) and `controllers/branch.js:loginCountryUber` (concentrador) both build a Node `form-data` `FormData` instance, spread `dataSend.getHeaders()`, and POST via `axios(config)` with `data: dataSend`. This is the one non-trivial multipart usage in the codebase and the highest-value smoke-test target — a UberEats auth break would take down the UberEats integration for every country. `form-data` is already pinned `^4.0.6` in both `package.json`s (matches axios 1.19.0's own raised security floor for that dependency, so no additional exposure either direction), and the `getHeaders()`-into-`headers` + `data: FormData-instance` pattern is the standard documented Node axios+form-data integration — changelog gives no indication this call shape changed. Still: manually exercise the UberEats login path post-upgrade before calling this closed, since it's an auth flow and multipart handling was touched in the 1.15.0/1.17.0/1.19.0 security fixes (depth handling, CRLF floor) even though none of those entries describe a call-shape change.
2. **`concentrador-service`'s shared `httpClient` interceptor** — v1.20.0's own release notes explicitly call out "hardened... normalized unsafe interceptor replacement objects" and "clarifies... custom implementation behavior" for runtime option handling (`data/axios_release_v1.20.0_20260928.json`). `httpClient.js`'s pattern (mutating the default `axios` export in place, not `.create()`) is unusual and worth an explicit post-upgrade check that `config._t0`/`response.config`/`error.config` still round-trip through the interceptor chain and the `[PERF/INFO] http_response` log lines still populate `duration_ms`/`status`/`method`/`url` correctly — a silent break here wouldn't throw, it would just start logging `duration_ms: NaN` or `unknown` fields.

**Lower-risk, still worth a config-source check:** v1.17.0 added `ERR_INVALID_URL` rejection for malformed `http`/`https` URLs missing `//`. Every URL in both services is built from runtime config (`settings.smlParams.url`, `settings.cloudParams.url`, per-platform `credentials.data.baseUrl`, etc.) rather than hardcoded — can't verify statically that none of those config values are malformed, but if any are, this upgrade is what would first surface it as a hard `ERR_INVALID_URL` throw instead of the request just going out (previous behavior). Not a code change item — a runtime-config sanity check.

**No breaking change found at the call-shape level itself.** `axios.get/post/put/delete(url, data, config)`, `.then()`/`await` resolution, and `error.response`/`error.config` error shape are untouched across every changelog entry reviewed from 1.13.5 through 1.20.0 — this is a same-major (1.x) jump and axios's own changelog treats it as backward-compatible aside from the hardening items above.

## `tar` override not actually resolving to `latest` — real Trivy evidence (2026-09-28)

User asked why `tar` (pinned via `overrides: {"tar": "latest"}`) didn't resolve to the true npm `latest` (`7.5.22`, confirmed via registry fetch this session) when tested against a Node 22.20 build. Real Trivy HTML report obtained and persisted: `data/trivy_report_ope_tar_stale_20260928.html` (scan timestamp 2026-09-28T18:39:32Z — today).

**Finding: the report shows two different `tar` versions installed simultaneously — `6.2.1` and `7.4.3` — neither is `latest`.** This is a more specific and more concerning result than "just old" — two distinct stale copies existing at once means `overrides.tar: "latest"` is **not** forcing every instance of `tar` in the dependency tree to the same resolved version, which is the entire point of npm's `overrides` field (as opposed to older per-instance-only resolution behavior). Two live hypotheses, not yet distinguished:

1. **Stale Docker build cache** — the scanned image's `npm install` layer was never actually re-run against the current `package.json` (which does have the override, confirmed present in both services' `package.json` this session) despite today's scan date; the report only timestamps when Trivy *ran*, not when the underlying image's dependencies were last installed.
2. **`overrides` genuinely isn't propagating to all instances** — possible if some package bundles/vendors its own copy of `tar` outside the normal resolvable dependency graph (rare but not unheard of), or an npm-version-specific override-resolution gap.

**Not yet confirmed which service/branch this report is for** — the custom Trivy HTML template used by the `ope` pipeline (`operations/events/20260908_gitin2011-ope-jenkins-scope/`) has no target/image-name field, only a generic "Node.js - Trivy Report" header. Placed in this (platform) folder by the user, but unverified from the file content itself.

**Resolved, 2026-09-28 — hypothesis 1 confirmed (stale build cache), not an override-propagation bug.** Container-level inspection of a local `platform-service:ope` image (`docker inspect --format '{{.Created}}'` → `2026-09-28T15:47:29-03:00`, i.e. built only ~8 minutes *after* the Trivy scan ran, `15:39:32 ART`) found **zero occurrences of `tar` anywhere** — no `node_modules/tar` directory at any depth, no `"tar"` in `package-lock.json`, no package with `name: "tar"` — despite 214 real top-level `node_modules` packages present (a genuine, populated install, not a broken one). This image is demonstrably a *different build* than whatever Jenkins built and Trivy scanned for the report above: a fresh local build resolves cleanly, while the Jenkins-pipeline image had `tar@6.2.1`/`7.4.3` baked in. Full diagnostic trail: `data/tar_installed_versions_ope_container_20260928.txt`, `data/tar_image_created_date_20260928.txt`.

**Ruled out:** the user had briefly set `overrides.tar` to `"~7.5.4"` in an intermediate local edit, then reverted it back to `"latest"` before this final build — confirmed via `data/tar_overrides_check_20260928.txt` (this image's actual `package.json` shows `"tar": "latest"`). So the zero-`tar` result isn't from a leftover experimental override value; it's consistent with `overrides.tar: "latest"` being correctly in place and simply having nothing to attach to — most likely `@sendgrid/client`'s currently-resolved version no longer depends on `tar` at all, making the override a benign no-op today.

**Persisted, 2026-09-28 — user ran `docker builder prune -af` (host not confirmed) and re-checked; still `tar@6.2.1`/`7.4.3`, CVE-2026-59874 HIGH (fixed in 7.5.18).** Two Trivy reports now on file, 47 minutes apart (`18:39:32Z` and `19:26:32Z`), showing **identical** stale `tar` versions both times — persisted as `data/trivy_report_ope_tar_stale_20260928.html` and `data/trivy_report_ope_tar_stale_2_20260928.html`. A bare top-level `overrides: {"tar": "latest"}` is npm-documented to apply globally to every instance of a package in the tree, at any depth — so this persistence, combined with the local rebuild coming back completely clean, is now well-explained: **these two reports almost certainly come from Jenkins/`sonarqube-srv`, not the user's local machine.** A local `docker builder prune` only clears the local Docker daemon's build cache — it has no effect on `sonarqube-srv`'s separate Docker daemon, and the Jenkinsfile's `docker.build()` step (`-f ./api/Dockerfile ./api/`, no `--no-cache`/`--cache-from` flags) would keep reusing whatever's cached there across pipeline runs regardless of what gets pruned locally.

## CORRECTED root cause, 2026-09-29 — `tar@6.2.1`/`7.4.3` is npm's own bundled internals, not the application's dependency tree at all

Ran Trivy directly against the local `platform-service:ope` image (`docker run --rm -v /var/run/docker.sock:/var/run/docker.sock aquasec/trivy image ...`, bypassing Jenkins entirely — `data/trivy_local_scan_ope_20260929.txt`) to settle the "is this really fixed" question with a fully controlled test. **It still shows `tar@6.2.1` and `tar@7.4.3`, both real, both reproducible, not a caching artifact.**

**The actual paths Trivy flags:**
```
usr/local/lib/node_modules/npm/node_modules/cacache/node_modules/tar   → 6.2.1
usr/local/lib/node_modules/npm/node_modules/node-gyp/node_modules/tar  → 7.4.3
```

**These are not under `/usr/src/app/node_modules` — they're under `/usr/local/lib/node_modules/npm/`, i.e. npm's own internal CLI installation, bundled inside the `node:20.20-alpine` base image itself.** `cacache` and `node-gyp` are npm's *own* internal dependencies (its package cache and native-addon-build tooling) — completely outside `platforms-service`'s `package.json`/`node_modules`/`overrides` reach. This resolves every open thread cleanly:

- **Why `overrides.tar: "latest"` never touched these**: `overrides` only governs the resolvable dependency tree rooted at the project's own `package.json` — it has no mechanism to reach into npm's own bundled internals, which are a separate, pre-existing installation baked into the base image, not resolved by the project's `npm install` at all.
- **Why every "clean" check was also correct**: `find /usr/src/app/node_modules -name tar` (zero results), the lockfile checks (zero `tar` entries), the Jenkins `package-lock.json` capture (zero entries) — all genuinely correct for `/usr/src/app`. They just weren't looking in `/usr/local/lib/node_modules/npm/`, so "clean at the application level" and "vulnerable at the npm-internals level" were both true at the same time, not contradictory.
- **Why the two Jenkins Trivy reports and this local scan agree**: they were never inconsistent with each other — all three scans (both Jenkins runs + this local one) are seeing the same real, persistent `tar` instances. The "stale build cache" theory was wrong; there was no caching artifact to begin with, just an incomplete search location in every diagnostic run before this one.

**Not fixable via `package.json`.** The actual fix has to happen at the Docker base image / npm-CLI level, not the application dependency level — two options, neither yet applied:
1. Bump `node:20.20-alpine` to a newer Node patch that ships a newer bundled npm (carrying newer `cacache`/`node-gyp`/`tar` internally) — simplest, but tied to whenever a new Node patch image is published upstream.
2. Explicitly upgrade npm itself in the `Dockerfile`: `RUN npm install -g npm@latest` right after `FROM node:20.20-alpine` (both build and final stages) — replaces npm's bundled internals immediately, independent of the base image's own release cycle. Preferred if a fix is needed before the next Node patch release.

**Not yet done:** confirm whether these two CVEs (in npm's own internal tooling, present only inside the container image, never invoked by the running application itself — `platforms-service` doesn't shell out to `npm`/`node-gyp`/`cacache` at runtime, they're build-time-only tools baked into an image that also happens to run the app) represent real runtime risk or are effectively dead code in the shipped container — worth clarifying before treating this as equally urgent to a real runtime dependency CVE. Either way, options 1/2 above are cheap enough to just apply regardless.

## `Log.save failed` / "Path message is required" seen on `ope` (2026-10-05) — not caused by the CVE changes

**Evidence:** a document pasted by the user (`data/logerror_log_save_failed_20261005.txt`, `createdAt` 2026-10-05T18:09:30Z): `message: '[INFRA/ERROR] Log.save failed'`, `level: 'FATAL'`, `error.error: 'ValidationError: message: Path message is required.'`.

**Where it comes from (read in `api/src/utils/log.js`, clone `dev-scr-smartPedidos-platformsService`, local checkout on `develop` @ `ded57a5`; `origin/ope` @ `b8d57be`):** that exact document is what the **outer `catch (dbError)` of `Log.save`** writes. It runs only when `configs.mongoLogEnabled` is true. In that path the code does `let customDataAfter = customData;` and then `delete customDataAfter.message / .level / .category` — an **alias, not a copy**, so those deletes also remove `message` from `customData`; the next call `logErrorModel.create({ message: customData.message, ... })` then has `message: undefined`, which the Mongo model rejects (`message` is required); the fallback `create` inside the inner `catch` also uses `customData.message` (still undefined) and throws again; the outer `catch` finally writes the FATAL document with a literal message. Result: with Mongo logging enabled, **every** `Log.save` call produces only this FATAL record and the real log data is lost from Mongo (console/stdout logging still works because `_stdout` runs before the deletes).

**Origin of the alias:** commit `b5f1053` (2026-09-21, "fix: update save method to use raw customData and improve error serialization") changed `let customDataAfter = { ...sanitizedCustomData };` (a copy) to `let customDataAfter = customData;`. `api/src/utils/log.js` is **identical on `origin/develop`**, and `git diff develop ope` lists only `api/Dockerfile` and `api/package.json`, so the bug is in `develop` (the production branch) too and **is not introduced by the axios / npm-pin / `apk upgrade` changes of this ticket**.

**Why it appears only in some runs:** `Log.configure({ mongoLogEnabled })` is driven at runtime by a flag read from a database document (`index.js`, `orderRejClosedTime.mongoLogEnabled` / `consoleLogEnabled`). The default in code is `mongoLogEnabled: false`, and an earlier note (project memory, not re-verified) records the flag as false in production. So the failure shows up wherever that flag is true in the database the running container uses (which database the user's `ope` run connected to was not checked).

**Candidate fix (not applied — the clone is read-only here; belongs in a separate change, not in this CVE ticket):** restore the copy (`let customDataAfter = { ...customData };`) before the deletes, or read `customData.message` into a local constant before them; optionally give `message` a fallback so the model never receives `undefined`. Not tested.
**Update 2026-10-05 16:2x ART — commit `765b5b4` ("fix: logs mongo") is now on `ope` (HEAD).** Compared with `origin/develop` it changes only `api/src/utils/log.js` (3 lines): the three `create` calls now use `message: customData.message || error?.message || 'Unknown error 1'` (and `… 2`, `… 3` in the two fallback creates). **The root cause is not fixed:** line 54 still reads `let customDataAfter = customData;` followed by the `delete` lines, so `customData.message` is still gone when it is read — the stored `message` is now always `error?.message` or `'Unknown error 1'` (the real log message is lost) and `customData.category` (line 61) is still always undefined (category lost). The commit makes the `Path message is required` / FATAL `Log.save failed` documents disappear, which hides the symptom while Mongo records keep a wrong `message` and no category. The one-line copy fix at line 54 (`{ ...customData }`) keeps the new fallbacks and restores `message` and `category`. The earlier diff file for the one-line fix (`data/log_save_alias_fix_diff_20261005.txt`) does not exist, i.e. that command was not run. No test of either version was run.

**Update 2026-10-05 16:5x ART — commit `84c7efd` ("fix: clone log", 16:49:51 ART) on `ope`:** one line in `api/src/utils/log.js` (line 54): `let customDataAfter = customData;` → `let customDataAfter = structuredClone(customData);`. This removes the alias, so `customData.message` and `customData.category` survive the following `delete` lines; the `765b5b4` fallbacks stay as a safety net. Differences from the shallow copy `{ ...customData }`: it is a deep clone (more work per call, only when Mongo logging is on), and `structuredClone` **throws `DataCloneError` for values it cannot clone** (functions, some host/native objects). That line sits inside the outer `try` but outside the inner one, so such a throw would skip the inner fallback and end in the FATAL `Log.save failed` document, losing that record; `{ ...customData }` would not throw (and tolerates a `null` customData, which `structuredClone` + `delete` would not). A grep of the callers found no call passing functions/sockets in `customData` and none passing `null` as third argument (grep only, not exhaustive). Node is 20.20 in the Dockerfile (`structuredClone` available since Node 17); the ESLint config says `ecmaVersion: 2018` and its `env`/`globals` were not fully read, so `no-undef` on `structuredClone` is possible. **Not tested** by us: the check is the marker test (`Log.saveError(new Error('boom'), { message: '[TEST/ERROR] marker', category: 'INFRA' })` → document with that `message` and `category: INFRA`).
