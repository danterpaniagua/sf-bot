## Mapping scope to what exists (2026-10-07)

- Built so far: see "Apply done" (stg) and "tst environment added". Not built: dev or prod vaults, developer/group access, write access, and any change to the apps.
- Deploy scripts (`deploy-staging.sh`, `deploy-prod.sh`, `deploy-testing.sh`, plus `deployCrossAccount.sh` in Concentrador and Backoffice) use one AWS CLI profile name, `smartfran`, for every environment (`PROFILE=smartfran` in both the staging and the production script of Platform), with `aws ecr get-login` (the deprecated v1 command). This is the "generic key" of point 2. One account (`382381053403`) hosts all environments. The identity used to run the Terraform work on 2026-10-07 is an IAM user; the permissions of that user were not listed.
- "Salt keys" (user, 2026-10-07: secrets meant to sign tokens): in both services the only signing key is `token.secret` (HS256). Platform signs in `controllers/_helpers.js` and verifies in `middlewares/route-permissions.js` and `app.js` (`express-jwt`); Concentrador signs in `controllers/_helpers.js`, `management.js` and `branch.js` and verifies in `app.js`, `middlewares/route-permissions.js` and `controllers/user.js`. In staging the value is identical in both services (hash comparison, nothing printed), and it is 15 characters long, short for an HS256 key (32 random bytes is the usual floor). `token.noexpires` (4 characters, shaped like a duration) is an `expiresIn` setting and is never read in `src`, so it is not a credential and is not migrated. `tokenStatic` (Platform only, 128 characters, not a JWT) is an API token used for an outbound call (`newsTypeStrategy.js`), not a signing key. The per-user password salts in MongoDB are unrelated data.
- Layout change from this: `shared/token-signing` (one secret for the key both services share) and `platforms-service/static-token` replace the two per-service `token` secrets; still 19 secrets. The loader refuses to load `shared/token-signing` if the two services' values differ. Rotation (not built): keep one `AWSCURRENT` and one `AWSPREVIOUS` version, sign with the current key and verify against both; needs a key-set/`kid` approach in the apps (`jsonwebtoken` and `express-jwt` accept a function as the secret; Platform runs `jsonwebtoken ^8.3.0` / `express-jwt ^5.3.1`, Concentrador `^9.0.3` / `^8.5.1`). "Created the first time they are used": the app roles stay read-only, so creation belongs to the deploy script (generate a random value if the secret has none), which also matches point 2 of the scope.
- "Frontend" in "production vault only from Fargate and the frontend" (user, 2026-10-07): the AWS console (people operating it), not the Backoffice app. The production vault therefore needs two principals only: the Fargate task/execution roles and a console-access role or group for people.
- Library requirements, superseded by the July design (inject through ECS, no new library; see 'Prior work found'): (Platform `develop` @ 373144e and Concentrador `develop` @ 01494650, `api/package.json`): both are CommonJS on `node:20.20-alpine` with Babel, and both already depend on `@aws-sdk/client-sqs` and `@aws-sdk/client-ssm` (`^3.0.0`). Neither has `@aws-sdk/client-secrets-manager` (needed to read the secrets built here), and neither has `@aws-sdk/credential-providers` (needed only if the code must pick a named profile locally; on ECS the default provider chain uses the task role). No v2 `aws-sdk` import was found in `src`. Each already has one `SSMClient` wrapper (`retriveKey`) with no callers.
