- **ARQ-009 PoC validated 2026-07-28.** `POST /{branchId}` on API Gateway REST API (v1), native `AWS` (non-proxy) integration to `arn:aws:apigateway:{region}:sqs:action/SendMessage`, VTL-constructed `QueueUrl` server-side from the path parameter — confirmed working end-to-end: `branchA` → `poc-arq009-branchA.fifo` (`MessageId 516c0182-...`), `branchB` → `poc-arq009-branchB.fifo` (`MessageId f3b34ecf-...`), each verified by matching the curl response `MessageId` against the message actually sitting in the correct queue. Account ID never appears in any client-facing URL. Three real implementation gotchas surfaced during the build (all fixed, worth carrying into ARQ-001's write-up so a real implementation doesn't rediscover them):
  - **`Action=SendMessage` via the `sqs:action/...` ARN requires an explicit `Version=2012-11-05` parameter in the request body.** Without it, SQS returns `AWS.SimpleQueueService.NonExistentQueue: The specified queue does not exist for this wsdl version` for FIFO queues specifically (a legacy-API-version routing quirk), even though the queue and QueueUrl are correct.
  - **`aws apigateway put-integration` fully replaces the integration object, silently wiping any previously configured `put-integration-response`.** Every time the integration (URI/template/credentials) is updated, `put-integration-response` must be reissued afterward, or the client gets a generic `Internal server error` (`No match for output mapping and no default output mapping configured`) even though the backend call actually succeeded — only visible via CloudWatch execution logs (`API-Gateway-Execution-Logs_{api-id}/{stage}`), which are off by default and require an account-level `cloudwatchRoleArn` (`apigateway update-account`) plus per-stage `loglevel`/`dataTrace` (`apigateway update-stage`) to inspect.
  - **VTL formal-reference syntax (`${...}`) is required whenever a literal-text suffix immediately follows a reference.** `$input.params('branchId').fifo` parses `.fifo` as a chained property access on the reference (silently resolving to empty) rather than literal text — it must be written `${input.params('branchId')}.fifo`. This directly affects ARQ-001's real template: even though the production suffix `_PlatformMessages.fifo` starts with `_` (which likely doesn't trigger the same chaining bug), the safe rule for any future VTL template touching this queue-naming convention is to always use `${...}` around the reference.
  - Also observed (not a code bug, just a process note): `create-deployment` called immediately after a `put-integration-response`/`put-integration` write can snapshot stale state (control-plane propagation lag) — redeploying again a few seconds later resolves it without any config change.
  - Stray artifact from this session: a duplicate empty REST API `5t5c2si3s3` (created by an accidental double-run of `create-rest-api`) — **deleted 2026-07-28**, tracked in [20260728_recursos-aws-poc-arq009](../20260728_recursos-aws-poc-arq009/20260728_recursos-aws-poc-arq009.md) (INFRA-001).
- **`GET /{branchId}` (ReceiveMessage) added and validated 2026-07-28**, same resource (`468mau`), same role (extended with `sqs:ReceiveMessage` on the same 2 queue ARNs, nothing broader). Applied the `${input.params(...)}` and `Version=2012-11-05` fixes from the start this time — worked on the first deploy, no debugging needed. `GET /poc/branchA` and `GET /poc/branchB` each returned the correct branch-scoped message (`MessageId`s matching the earlier `SendMessage` test exactly). Full read/write round trip through the Account-ID-free proxy is now proven, both directions.

## Current working theory

API Gateway REST API (v1), native SQS integration, custom domain `colas.smartpedidos.com`, single parametrized resource `/{branchId}` (not one resource per queue — queues follow `{branchId}_PlatformMessages.fifo`), fronted by a Lambda TOKEN authorizer that validates the existing branch JWT with mandatory `branchId` binding. This design also lets the POS agent drop its embedded static AWS credentials entirely (resolves SEC-006 Option B as a side effect).

Still open: whether to build the data path as REST API only (Option A, no Lambda, ~$517/mo, simpler) or HTTP API + light Lambda (Option A', ~$180/mo, cheaper but adds a Lambda component) — ARQ-008.

## Ruled out

- **VPC endpoint / PrivateLink** — POS agents connect over public internet, not from inside the AWS VPC. Doesn't apply.
- **Lambda Function URL as proxy** — same custom-domain setup work as API Gateway, without native SQS request mapping. More complexity, no benefit.
- **Reusing CloudFront `EN17DHYYWUZ8X`** — wrong origin (S3 static frontend), no `POST` support.
- **CloudFront in front of API Gateway (Option B)** — SQS responses aren't cacheable, so CloudFront adds no value; +$147.76/mo over Option A for nothing.
- **"No CNAME" as a stated requirement** — not a real security criterion; no AWS custom-domain mechanism (API Gateway, CloudFront, Route 53 ALIAS) exposes the Account ID via DNS or reverse resolution regardless of record type.
