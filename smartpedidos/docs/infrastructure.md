## Data stores

| Store | Detail |
|---|---|
| MongoDB Atlas cluster | `PedidosSmartfran`, `us-east-1` |
| Database | `smartfran` |
| Key collections | `orders`, `news`, `logerrors`, `deadletters`, `branches`, `chains`, `platforms`, `newsStates`, `newsTypes`, `configs` |

`news` is the internal event/notification model; each document has a `traces` array tracking state transitions. **Retention on `news` is 15 days** (`GITIN-1965`, 2026-08-31): a `createdAt` query reaching further back returns nothing for the older part because the documents are gone: they are removed by the daily Atlas App Services trigger `clearCollection` (`mongodb_indexes.md`, `GITIN-2013`), not by a TTL index, so the document count peaks just before 08:10 UTC. Any analysis using `news` as a volume signal is capped at a ~15-day lookback (a week-over-week check has ~2 clean prior weeks).

## Message flow (AWS SQS)

```
PedidosYa / Rappi / UberEats / MercadoPago / PediGrido
        ↓  webhook
  platforms-service
        ↓  pushNewToQueue
  {branchId}_PlatformMessages.fifo  (per branch; production: {branchId}PRD_PlatformMessages.fifo, us-east-1)
        ↓  SmartCloud MessageProcessor polls it (see cloud/docs/infrastructure.md → "SmartPedidos Bridge"), delivers to the branch POS, acks back through a second queue
  PRD_BranchMessages.fifo  (one shared queue, all branches)
        ↓  platforms-service pollFromQueue (parent consumer) + up to 3 child consumers (auto-scale at 200 / 400 / 600 depth)
        ↓  setNews → news state transition in MongoDB

  On failure → DeadLetter.fifo / MainDeadLetter.fifo
        ↓  concentrador-service deadLetterSave() on startup
  smartfran.deadletters  (MongoDB)
```

**Who consumes `PRD_BranchMessages.fifo` (read from source, `GITIN-2110`, 2026-09-25):** `platforms-service` (`api/src/platforms/provider/aws.js:56-115`, `pollFromQueue()` creates an `sqs-consumer` on `config.AWS.SQS.ORDER_CONSUMER.NAME`, calls `setNews()` per batch; error log `[ORDER/ERROR] setNews_processing failed consumer=parent`). `concentrador-service` only echoes the queue name in an API response (`controllers/branch.js:3016`) and never consumes it. So the queue is the ack leg back from SmartCloud, not the final POS delivery hop, and a stall there delays order-state updates (delivered, ready, rejected), not new orders reaching the POS. The older diagram and `smartpedidos/CLAUDE.md` describe concentrador as owning the consumer path: that is not what the source shows.

- **Region:** **production queues are in `us-east-1`** (with the Atlas cluster): CloudWatch `AWS/SQS` there returns `{branchId}PRD_PlatformMessages.fifo` (no underscore before `PRD`, e.g. `5713PRD_PlatformMessages.fifo`), `PRD_BranchMessages.fifo`, `MainDeadLetter.fifo`, `DeadLetter.fifo` with live traffic (`GITIN-2211`). `us-east-2` holds test and staging (user-stated); the testing URLs below are from earlier work. The auto-scaling note was not re-verified against production.
- **Consumer auto-scaling (platforms-service):** on `ApproximateNumberOfMessages`: > 200 spawns a 2nd consumer, > 400 a 3rd, > 600 a 4th.
- **Dead letters:** `MessageRetentionPeriod: 259200` (3 days): act within that window. `configs.saveDeadLetterbol` = `false` makes concentrador-service skip dead-letter recovery silently.
- **Stray queues in `us-west-2`** (e.g. `1025PER_PlatformMessages.fifo`, created 2020-12-29, account `382381053403`): created and unused (no POS consumer), leftover from early provisioning; infra hygiene, not investigated.

Testing queue URLs (`us-east-2`, account `382381053403`): producer `https://sqs.us-east-2.amazonaws.com/382381053403/{branchId}_TST_PlatformMessages.fifo`; consumer `.../TST_BranchMessages.fifo`; dead letter `.../DeadLetter.fifo`; main dead letter `.../MainDeadLetter.fifo`.

### Production queue signals (`GITIN-2211`, `GITIN-2162`)

CloudWatch `AWS/SQS`, `us-east-1`, queue `PRD_BranchMessages.fifo` (1-minute data; `Maximum` for age and visible messages, `Sum` for sent/received/deleted):

- **Normal:** ~380-620 messages sent per minute in the evening, received and deleted within a few messages of sent, oldest-message age 0-4 s. The daily 5-minute peak of sent is 1361-3534 at the usual ~22:45 local (weekday evenings 1361-1882, Friday-Sunday 2800-3534), so a fixed volume threshold would fire daily.
- **Stall pattern:** consumption stops for 2-5 minutes (received and deleted 0 while sends continue), visible messages and oldest-message age climb, then a catch-up burst (e.g. 2879 received / 2880 deleted in one minute) drains it. 12 stalls in 2026-10-03..10-12; all reached age > 200 s (238-324 s), 10 reached ≥ 250 s, 5 reached ≥ 300 s. Each coincides with a run of ≥ 2 minutes of zero deletions with sends > 0, and no other such run occurred in the 10 days. Cause undetermined (same pattern as `GITIN-2162` / `GITIN-2110`). Triage: `ops-aws` skill, F-007. Example: 2026-10-11 21:58-22:02, age 306 s at 22:03.
- **Dead letters:** `MainDeadLetter.fifo` holds a stock of 30-77 visible messages and received 0 in the 10 days; `DeadLetter.fifo` visible 0-3. Neither moves during stalls.
- **Queue configuration** (`GITIN-2162`, `get-queue-attributes`): FIFO, `VisibilityTimeout` 30 s, `ReceiveMessageWaitTimeSeconds` 0, redrive to `MainDeadLetter.fifo` after `maxReceiveCount` 2, `ContentBasedDeduplication` true, `DeduplicationScope` queue, `FifoThroughputLimit` perQueue, retention 4 days. Because of the 30 s visibility timeout, a received-but-not-deleted message is visible again within 30 s, so a low in-flight count does not tell "consumers not polling" from "handlers hung". The message group id is set by the producer (SmartCloud side), not in the platforms-service repo.
- **Consumer code** (`develop`, `ded57a5`, read 2026-10-04; `api/src/platforms` and `api/src/config` identical on the `ope` branch): `sqs-consumer ^11`, `batchSize: 10`; per batch `GetQueueAttributes` (its `sizeMessageSQS` only decides whether to start the 2nd-4th consumer and is **never logged**), then messages per order id sequentially through `SetNews.setNews()` (`management/strategies/set-news.js`): per news type a Mongo `findNew`, an outbound platform call, a Mongo `updateNew`. Handler errors are caught and logged, so a failing message does not throw. **No timeout wraps the handler, the Mongo calls or the SQS calls**; one consumer takes one batch at a time, so a call that never returns blocks that consumer's polling. A slow platform API costs up to the axios default (`10000` ms in the `GITIN-2162` read, `20000` in `GITIN-1783`'s: check `api/src/index.js`) per call but the handler still returns.
- **No success-path logging exists in this consumer** (`GITIN-2110`): every `Log.save` in `pollFromQueue()` and both `handleMessageBatch` blocks is `ERROR` or `WARN`; no batch received/processed line, no batch size, no duration. A silent backlog-then-burst-drain therefore produces **zero log lines**: an empty Graylog result for `sqs_consumer` / `batch_processing` in a stall window (0 results in both 2026-09-25 windows, while a control term returned 29,318 messages) is not evidence of a healthy consumer. Observability gap, candidate `sp-log-improvements` finding: log `sizeMessageSQS` and batch size/duration per `handleMessageBatch`.
- **What a stall looks like in MongoDB** (`GITIN-2110`, Sun 2026-09-27 21:05 -03:00): `news.updatedAt` is bumped exactly when `setNews` processes a dequeued message, so 843 docs across 405 branches in 12 minutes, **292 of them in an 11-second burst** (21:06:23-21:06:34), against a 1-7/s background, is the drain. 94 % were `typeId` 14 (`deliv_ord`); `ready_ord` (15) was 9 of 843. `updatedAt - createdAt` is a whole-lifecycle gap (median ~14 min), **not** time stuck in the queue.
- **Volume and capacity do not explain the stalls** (`GITIN-2110`, `GITIN-2162`): `NumberOfMessagesReceived` weekends (Fri-Sun) 655k, 606k, 573k (2026-08-28, 09-04, 09-11) then 814k and 824k (09-18, 09-25); the 09-27 21:00 hour (24.3k) matched 09-20 (24.1k) and is well below the 14:00-16:00 peak (37-44k). A task-definition CPU doubling (`:266` 512/2048 → `:267` 1024/2048, 2026-09-25 21:33 -03:00 to 2026-09-28 08:18, 58.75 h) did not stop them: the worst episode (374 s) came after it with CPU Max 49 %. `:268` (512/1024) followed. Episodes also occurred at 10 tasks and at ~210 messages per 5 min (Sun 2026-10-04 11:19, 324 s).
- **Platform-service state during the episodes** (`GITIN-2162`, nine episodes 2026-10-01..10-05): ALB target group `platform-service-production-tg` normal (13.5M requests, mean 3-8 ms, no 5XX datapoints, `UnHealthyHostCount` max 0); service CPU Max 44-100 % with Average 5-15 %; no ECS service event, task stop or health-check kill before the stall; `MainDeadLetter.fifo` received 0 (raw check: `NumberOfMessagesSent` is 0 anyway, see the dead-letter gotcha in `smartpedidos/CLAUDE.md`); autoscaling reacted 2-12 min after each episode (5 → 14 and back to 5; 10 → 14 on 2026-10-04 19:15 and 20:23 by the request policy), never before. **No Zabbix event for SmartPedidos fired for any of the nine** (the only `AWS ELB ALB` 4XX/5XX problems sit on host `Zabbix server`, ALB not identified).
- **Working theory (undetermined, `GITIN-2162`):** all consumers stop deleting together for 5-10 min and drain fast, independent of volume and task count, while the same tasks answer HTTP normally: a stall confined to the consumer path and common to all tasks. Candidates, none tested: a shared outbound dependency without timeout (SQS `GetQueueAttributes`/receive, MongoDB in `setNews`), FIFO message-group blocking, the consumer code blocking on something shared. CPU Max spikes may be a consequence of the burst. Ruled out: plain volume capacity, task churn/health-check kills, whole-process freeze, poison messages, the Node 22 / axios 1.20 `ope` runtime change (same pattern on 2026-09-25, before it). **Redeploy candidate (`GITIN-2110`, only 2 of 6 spikes checkable):** the two full-fleet replacements visible in `describe-services` (2026-09-27 16:03 and 21:05:59) coincided with a mild and the worst spike; a rolling deploy runs ~20 tasks for 10-15 min. The other four spikes were outside the 100-event buffer; the trigger of the same-revision redeploys was not identified (CloudTrail `ecs:UpdateService` not pulled).
- **Pull limits:** `describe-services` keeps only the latest 100 events whatever `--query` says (16.3 of 58.75 h visible in one pull); Cost Explorer's finest granularity is hourly. Cost of the `:267` escalation (not billing-confirmed, list price): ≈ $5.95-11.89 incremental, depending on 5 vs 10 running tasks; Cost Explorer daily deltas implied ~5 tasks while `describe-services` showed 10 (not reconciled).
- **Pull limit:** a CloudWatch `SEARCH` over all SQS queues is cut at 500 series (`MaxMetricsExceeded`): request the queue by name or split by branch range.
- **Alerting chain:** CloudWatch alarm `sendMailOldestMessage` (`ApproximateAgeOfOldestMessage`, Average, 300 s period, threshold > 25 s) → SNS `Pedidos_Production` (Lambda, email and SMS subscriptions). The Lambda `IntegrationLambdaEcsTaskProd` (`us-east-1`, python3.12, timeout 3 s, ~2.9 s per run) sets `platform-service-production-service` (cluster `smartfran-pedidos-production`) to 15 desired tasks whenever fewer than 15 run; Application Auto Scaling then scales back in (3-minute steps). It fired in all 12 stalls. Alarm detail: `Average` over 300 s, 1 evaluation/1 datapoint (a 1-2 minute spike is diluted), `TreatMissingData: missing`, `OKActions` go to the same topic. Topic `Pedidos_Production` has 6 subscriptions (the Lambda, 2 email, 3 SMS). **Lambda code (`GITIN-2170`, `events/20261005_gitin2170-platform-mejorar-escalado/`):** hard-coded cluster/service and `limite_tareas = 15`; `describe_services`, then `update_service(desiredCount=15)` only if `runningCount < 15`; it never reads the SNS message, so it **also fires on the OK transition** (all nine OK-time invocations saw 9-14 running and by the code scaled to 15 after the queue had recovered; inferred, nothing is logged after the update). No tiers, no scale-down, no logging beyond `print` counts; 128 MB, **3 s timeout: 7 of 23 invocations since 2026-10-02 ended in `Status: timeout`** (every run is a cold start at 2.6-3.0 s; the update still lands, and Lambda's async retry is harmless because of the `< 15` guard). Role: `AmazonECS_FullAccess`, `AmazonSNSFullAccess`, `AmazonECSTaskExecutionRolePolicy` (needs only `ecs:DescribeServices`/`UpdateService` on one service). Scale-in is not the Lambda's: only the two target-tracking policies bring it down. Its log group had no subscription filter and no Graylog ingestion until `GITIN-2171` (Kinesis → stream `SP_Lambdas`); the redesign (tiers 5-10 / 15 / 20) was waiting on the unit of the thresholds and the scale-down rule. Staging counterparts (unverified): `EscaladoECSUp`, `IntegrationLambdaEcsTask` in `us-east-2`. A second alarm, `sendMailOldestMessage100`, has been `INSUFFICIENT_DATA` since 2025-02-22. Reported by the team, not checked: Grafana shows these metrics and alerts above 250 s of oldest-message age (an order can be cancelled when no news arrives within 10 minutes).

### Incident patterns (confirmed in solved events)

- **PediGrido outage pins `concentrador-service` (`GITIN-1783`, 2026-08-05, `events/20260805_concentrador-platforms-high-cpu-healthcheck/`):** `checkOfflinePOSpedigrido()` runs every minute (`branch.js`, cron `*/1 * * * *`) and fans out a `PUT v1/locals/status` per branch needing a sync through the shared `utils/httpClient.js`, an `axios.create()` with **no timeout** (axios default `0` = forever), with no concurrency cap and no overlap guard. When `app.pedigrido.com` degraded (19:28-21:02 UTC: calls of 125-218 s, status `524` 248×, `502` 78×, `503` 25×), each tick stacked a new batch of hung requests: sustained CPU/event-loop pressure for ~90 minutes, and the dead-letter stock roughly doubled (55 → 109, corroborating only). The two task-size changes did not fix it. Dev fixes proposed, not implemented: timeout on `httpClient`, overlap guard, fan-out cap. `platform-service` sets `axios.defaults.timeout = 20000` in `api/src/index.js`, yet 24 of 8,420 PediGrido calls exceeded it (max 34 s, all `200`; mechanism unidentified): the same window had 1.8 % of calls above 20 s vs 0.16 % outside.
- **PediGrido open/close timeouts, 2026-10-09 (`GITIN-2208`, `events/20261009_gitin2208-graylog-error-spikes/`):** three bursts of `openClosedBranchesGrido` (concentrador) at 08:00, 09:00 and 09:30 -03:00 (1,581, 990, 1,543 messages per 5 minutes, `timeout of 20000ms exceeded`, ~500-600 branches, one error per branch inside one minute), none in the same hours of the day before and none after 10:00; each failing branch also logs a `[PERF/INFO] http_response` line, which doubles the free-text `ERROR` count. Cause not investigated (Grido availability, a concentrador restart re-triggering the job). One empty minute of concentrador logs at 09:34 after the 09:32-09:33 burst (no restart confirmed; the startup-word searches returned HTTP 500 from Graylog). Every day from 10:00 `enviarEstadoPedidosYa` returns HTTP 400 for ~570 branches every half hour (1,123 / 1,052 / 769 / 577 / 308 against 1,129 / 1,061 / 801 / 604 the day before): recurring, cause open (`todo.md` item 8). Steady background: `No authorization token was found` / `Platform Auth Error: TOKEN_MISSING GET /api/branches/news` (40 per 5 minutes) and MercadoPago token failures. A `checkOfflinePOS` series needs a wildcard (`checkOfflinePOS*`): the real messages are `checkOfflinePOSpeya`, `...mercadopago`, `...rappi`.
- **MercadoPago `token_fetch` loop against Cloud `WalletCredentials` (`GITIN-2220`, with `GITIN-2209`/`GITIN-2211`/`GITIN-2218`, `events/20261013_gitin2220-platform-walletcredentials-hits/`):** on 2026-10-11 21:50-22:10 platforms-service logged `[PERF/INFO] http_response platform=MercadoPago action=token_fetch` ~957 times per minute (16/s), 98 % status 204, two `user_id` at 96 % (55 distinct ids); the Cloud Business API shows `GET /api/v1/WalletCredentials/{id}` at 504,921 (10-08), 1,898,817 (10-09), 1.17-1.51 M/day after (callers not traced). Cloud side: for at least two wallet accounts MercadoPago answers `invalid_grant` (HTTP 400) on the refresh, Cloud returns null and leaves the credential Active, so every request retries. Platform side (`api/src/utils/tokensCloud.js` on `develop` `a762c1a`, 2026-10-09): `getTokenMercadoPagoCloud` stores nothing on failure, so every event of that merchant calls Cloud again; no throttle, negative cache, in-flight de-duplication or backoff; the 204 check reads `.response.status` (a successful axios response has `.status`), so an empty 204 body ends as `[INTEGRATION/ERROR] token_fetch failed` and `null`; `TraceKey` hardcoded `'1234'`; callers `controllers/mercadoPago.js:70,102` and `platforms/management/platform/mercadoPago.js:119,161,265,294,365,400`. Hypothesis (unconfirmed): the two dominant `user_id` are the two failing accounts (credentials 31 and 66). The proposal (per-`user_id` negative cache with doubling TTL, in-flight sharing, fixed 204 check, once-per-window log) reduces load but gives those merchants no token (needs re-authorization or a Cloud fix). The user stated on 2026-10-14 that the fix was deployed in SmartPedidos; which part, the commit and the effect were not stated or measured. Cloud-side view: `cloud/docs/infrastructure.md` ("wallet-credentials retry loop"). Concentrador's own rate was not measured.
- **`platform-service` kill-and-replace loop:** during that incident ECS stopped one or more tasks every 2-3 minutes for 46+ minutes (17:15-18:01 -03:00); `concentrador-service` was never stopped. The literal `stoppedReason` was not recovered: ECS service events keep only ~100 entries (burned in about an hour) and `describe-tasks` returns empty for stopped tasks after roughly an hour (CloudTrail `lookup-events` was not tried). The health-check as trigger is "consistent with", not confirmed. The health endpoint (`api/src/controllers/metrics.js`) returns 400 when `os.loadavg()[0] > maxCpuLoad` (0.7); its memory guard is dead code (`usedMem` is a 0-1 ratio, `maxMemUsage` is `"2"`); in force since April 2025, not a regression. Stops caused by a deployment carry `Scaling activity initiated by (deployment ...)`.

- **Node export Lambda, operating facts (`GITIN-1970`, `GITIN-1983`, `GITIN-1973`; `events/20260831_lambda-s3-export-utc3/`, `20260902_export-s3-update/`):**

The connection string was reported (not verified) to have been plaintext in the source before moving to env vars (`GITIN-1973`).
  - It never writes day 0: only yesterday and earlier, so a file for date X exists only from the run on X+1. A 10-15 day run takes 76-158 s and 2.3-2.5 GB; steady state is `DAYSBEFORE=2`, so **an outage longer than 2 days leaves a permanent gap that the next run does not heal**; after any wide manual run set it back to 2 (it stayed at 15 once, 2026-09-02).
  - Bugs fixed 2026-09-01 (check these first if exports go silent): the connection string lacked the `${}` interpolation (connected to the literal `HOST`), `DAYSBEFORE` was a string so `daysBefore + 1` concatenated and the day loop ran zero times with no error (empty prefix without any failure), `run()` built all days in memory (`Runtime.OutOfMemory` at 4096 MB; now one day at a time, a day's file reaches ~180 MB), and `orderMapper()` returned the raw object. The runtime moved `nodejs12.x` → `nodejs18.x` → `nodejs24.x` on 2026-08-31.

  - **`-3` re-bucketing (`GITIN-1980`):** the Argentina day D is the UTC files D and D+1 (D covers local 00:00-21:00, D+1 the local 21:00-24:00 spillover), matched on `updatedAt` (raw files) or `updatedat` (mapped files, from 2026-08-17); no field value is converted. About 0.56 min per day with `--resume`; the oldest buildable day is 2025-08-17 (older files are `DEEP_ARCHIVE`), the newest is two days short of today.
- **`smartfranbkp` bucket:** multi-purpose (many unrelated prefixes: `activeSoftware/`, `branches/`, `orders/`, ...). **Lifecycle: `news/` goes to `DEEP_ARCHIVE` after 365 days from `LastModified`** (2026-09-01): older data needs `restore-object` (~12+ h); "hot" storage is always roughly the trailing 365 days.
